## 归属切片
S1（AT-0106）

## 来源需求
MUST-05（本地存档）、09 M-06（写入耗时）、M-07（单档 ≤300KB）

## 来源方案
`packages/game-core/src/save/schema.ts`（`SaveFile` / `sealSave` / `verifySave`）、`client/assets/scripts/services/save/**`（占位）

## 目标
把 `SaveFile` 接到平台 storage 上：能写、能读、能校验、被篡改能识别、杀进程后能恢复。

## 输入
- 规则：`game-core/save/schema.ts`（**只调用，不修改**）
- 平台：`platform/wechat/WechatPlatform.ts` 的 `storage` 能力（已有）
- 前置任务：无（可与 AT-0104 并行）

## 输出路径
- `client/assets/scripts/services/save/**`（实现 `SaveService`）
- `packages/game-core/src/save/**` 仅在需要补纯函数时改动（如 `serialize/deserialize`）

## 执行步骤
1. 实现 `SaveService.save(file)`：`sealSave` → `JSON.stringify` → 写入平台 storage（键名固定，如 `wdf.save.v1`）。
2. 实现 `SaveService.load()`：读出 → `JSON.parse` → `verifySave`；失败返回明确的错误枚举（`'empty' | 'corrupt' | 'too-new'`）。
3. 损坏处理：**不静默覆盖**，把损坏内容另存 `wdf.save.corrupt.<ts>`，再走云端档（S5 完善）。
4. 写入后记录耗时（供 M-06 埋点 `save.push` 的 `ms` 字段）。
5. 单元测试：同一份内存对象两次 `sealSave` 的 checksum 必须相等；改 1 位后 `verifySave` 必须为 false。

## 验收标准
1. 写入后重启（同一 storage）能读回同一 `revision` 与 `modules` 内容；
2. 篡改 1 个字符 → `load()` 返回 `'corrupt'`；
3. 单档体积记录（JSON 字节数），控制在 300KB 内；
4. 纯函数部分可在 Node 下测试（不依赖 `cc`、不依赖 `wx`）。
