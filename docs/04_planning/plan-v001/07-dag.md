# 07 依赖与并行

## 7.1 并行四判据（全部满足才算可并行）

| 判据 | 含义 | 检验方法 |
|---|---|---|
| P1 无共享可变状态 | 两个 AT 不改同一个运行时状态（同一张表、同一个存档字段、同一个单例） | 对照修改文件清单 + 表名 |
| P2 依赖的契约已冻结 | 两个 AT 所需的契约都已在本规划冻结（03） | 逐条比对 03 的动作/类型 |
| P3 文件所有权不相交 | 按 08 所有权矩阵，两 AT 的"允许修改"路径无交集 | 路径前缀比对 |
| P4 不共用同一迁移编号 | 两 AT 都不新增/不修改同一个 `NNNN_*.sql` | 迁移编号串行编排 |

## 7.3 可并行组（逐条给出满足的判据）

| 组 | 并行成员 | P1 | P2 | P3 | P4 | 结论 |
|---|---|---|---|---|---|---|
| G1 | AT-0103 ∥ AT-0106 | ✅ 契约文件 vs 客户端 services | ✅ 都基于已冻结类型 | ✅ `packages/contracts` vs `client/services` | ✅ 不涉迁移 | **可并行** |
| G2 | AT-0104 ∥ AT-0105 | ✅ 不同 service | ✅ | ✅ 不同模块目录 | ✅ 都用 0001（只读） | **可并行** |
| G3 | AT-0301 ∥ AT-0401 | ✅ 背包 vs 配方 | ✅ | ✅ inventory vs crafting | ✅ | **可并行**（S3/S4） |
| G4 | AT-0601 ∥ AT-0701 | ✅ 服务端经济 vs core 开锁 | ✅ | ✅ server vs game-core | ✅ | **可并行** |
| G5 | AT-0901 ∥ AT-1101 | ✅ 榜单 vs 塔防模拟 | ✅ | ❌ **都在 game-core/server 交叉** | ✅ | **不可并行**（P3 失败，core 归我独占） |
| G6 | AT-1601 ∥ AT-1602 | ✅ 不同测试 | ✅ | ✅ | ✅ | **可并行**（但按用户要求暂不实施） |
| G7 | AT-1701 ∥ AT-1702 | ✅ 不同文档 | ✅ | ✅ 不同文档 | ✅ | **可并行** |

> **结论**：真正可并行的组只有 **G1、G2、G3、G4、G7**；G5 因 `game-core` 由我独占而**不能**并行。

## 7.4 串行链（不可打破）

| 链 | 路径 | 原因 |
|---|---|---|
| L1 骨架链 | S0 → AT-0106/0107/0108 → S1 完成 | 没有工程无法建场景；没有存档无法验证"重启还在" |
| L2 手感触感链 | S1 → AT-0201 → AT-0202 → AT-0203 → AT-0204 | C1 闸门：不达标不扩展 |
| L3 玩法链（v1.0） | S2 → S3 → S4 → S7；S6 另起 → S9 | 数量关系：背包→合成→开锁；总收益榜只依赖商人回收 |
| L3' 赶海链（**v1.1**） | S7 → S8 → 0902（赶海分组榜）→ 21:05 结算发奖 | 12:27 已定：S8 整片移入 v1.1 |
| L4 上线链 | S9 → S10 | 真机验收要完整玩法（不等 S8） |
| L5 数据链 | AT-1501 → S3/S4/S6 | 无数值则规则无输入 |

## 7.5 关键路径

**最长路径**（决定总工期）：

```
S0(0.5) → S1(2.0) → S2(2.0) → S3(1.5) → S4(2.0) → S7(1.5) → S9(1.5) → S10(2.0)
= 13.0 人日（不含 S5/S6/S8/S11/S12/S13/S14；S8 已移 v1.1，减少 2.0 人日）
```

**含全部 v1.0 范围的路径**：

```
S0 → S1 → S2 → S3 → S4 → S5/S6(并行) → S7 → S9 → S10 ≈ 15.5 人日（S8 移出后）
```

> 5 周 = 25 工作日，**看似有余量**；但历史事实是"单人 + 未测代码 + 未初始化工程"，且 S10 真机与合规可能一次不通过。**判定：排期风险仍高，不得乐观压缩**。

## 7.6 环检测

| 检查 | 结果 |
|---|---|
| 图是否无环 | **无环**（对 46 个 AT 做拓扑排序，全部可排） |
| 潜在环 1 | `save.push` 依赖存档 schema，`save/schema` 又依赖 `modules` 结构，而 `modules` 由各玩法定义 → 若把"模块序列化"写进 schema 会成环 | **已排除**：`save` 只负责封套与校验和，`modules` 由各玩法自行序列化（D-06 保持"开放式容器"） |
| 潜在环 2 | 赶海结算依赖榜单，榜单又依赖赶海奖池 | **已排除**：09 把"奖池"归入 `event` 而非 `leaderboard` |
| 潜在环 3 | 数值生成依赖 items，items 的 `unlock_level` 又依赖等级表 | **已排除**：方向固定为 `levels` → `items`，不反向 |

## 7.7 阶段 B 的推荐并发度

| 时段 | 同时写入方 | 说明 |
|---|---|---|
| S0–S1 | 我（Core）+ Client + Server = **3** | 已达上限 |
| S2 | 我（Core）单独 | Client 只改表现层，可算第二方 |
| S3–S4 | Core + Client + Data = **3** | 上限 |
| S5–S9 | Server + Client + Data = **3**（Core 我在做 S7/S8） | 需轮换 |
| Contract / Guard | **不得**与实现并行改（用户规则） | 单独窗口 |

> 规则：**同一时刻最多 3 个写入方**；`Agent-Contract` 与 `Agent-Guard` 只在"实现暂停"窗口改动。
