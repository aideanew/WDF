# 垂直切片

> 切片的定义：**能被独立观察、独立收口的一段工作**（不是"一个阶段"，也不是"一张卡"）。
> 每个切片必须回答三个问题：**谁需要它 / 没有它会怎样 / 做完之后能看到什么不同的东西。**

---

## 0. 为什么本版只有 5 个切片，而不是按模块切 19 个

**因为本版的命题不是"做功能"，是"让治理产物自洽"。** 按模块切会立刻重复 `plan-v012` 的 18 张卡。

| 如果按模块切 | 后果 |
|---|---|
| 再写 9 张"`PD8-08` 的 replay"类卡 | 与既有 18 张重复 → 就是 `C-01` 的病 |
| 按 `game-core` 19 模块切 | 8 个模块是空壳且已在 `D-50` 登记 v1.1 延期 → **做了等于白做** |
| **按"缺陷到修复可观察"切** | 每个切片的出口是**一条命令从红变绿**，不可含糊 |

→ **切片的主轴是「红 → 绿」，不是「模块 A → 模块 B」。** 这是本版与 v008~v012 的根本差别。

## S1 · 一致性止血（让矛盾变红灯）

| 项 | 内容 |
|---|---|
| **谁需要** | 下一个被派工的执行者（他会在 26 张待办卡里挑错） |
| **没有会怎样** | 派到 `PD7-02`（僵尸卡），与 `PD8-02` 撞同一批文件 → 覆盖 |
| **卡** | `PD9-01`（新增第 11 项守卫）→ `PD9-02`（清 11 张僵尸卡） |
| **入口判据** | `npm run guard` 现在**不检查**索引一致性（10 项已实测，见 `03 §4`） |
| **出口判据（命令）** | ① `npm run pd:consistency` 退出码 **0**；② 该脚本对**当前**索引必须**先红**（至少 11 条 `C-01` + 15 条 `C-13` + 44 条 `C-10`）；③ 修完后二次运行 **0 条** |
| **做完能看到什么** | 一个"11 → 0"的差异；`npm run guard` 从 10 项变 11 项 |
| **不做什么** | 不改任何业务代码；不重写 11 张僵尸卡的卡面（只改 `status` / `superseded_by` / `superseded_reason`）；不碰 `pd.mjs` |

### 排序理由（为什么必须是第一个）

1. **它是唯一能防复发的**。其余切片都是一次性修复；没有守卫，下一代会重演。
   - 凭据：`replans[0]` 的 FIX-25 已经记录过同型事故（"索引内 v1.1 卡被当作就绪，`next` 会误派工"）——
     **同一个坑，第二次**。
2. **它的收益可量化**：冲突对 **44 → 7**（`02 §4` 实测）。
3. **它必须先于 S2**：不先清僵尸卡，`D-57` 的裁决会被记到 `PD7-02/03` 两张已死的卡上，
   而真相是它要记到 `PD8-02/03`。**先清场，再裁决，否则裁完还得再改一遍。**

### 反证与自否定

| 反驳 | 我的回应 |
|---|---|
| "先修守卫是过度工程，11 张卡手动改改就行" | 改 11 张卡 **10 分钟**，但改完之后**没有任何东西阻止第 12 张**。而 `C-13` 的 15 处单向链接、`C-02` 的缺 replan 记录，都是同一种"没人查" |
| "守卫会不会一上线就满屏红，没法推进" | 会。所以 `PD9-01` 必须带 **两级**：`error`（P0/P1）+ `warn`（P2/C-11 的 29 张历史卡），且 `warn` 不阻断。已写进卡面 |
| "44 → 7 这个数是不是我算错了" | 命令在 `02 §4`，可复跑。且**纯 PD8 的 7 对我单独列出**，可逐对人工核 |

## S2 · 决策消解（把 4 个 PROPOSED 变成有归属的状态）

| 项 | 内容 |
|---|---|
| **谁需要** | `PD8-02 / 03 / 04 / 11`（被 D-57 挡）、`PD8-14`（被 D-58 挡）、`PD8-10/12/13/15/16`（范围受 D-59 影响） |
| **没有会怎样** | 执行者只能二选一：要么停下等（= 现在的状态，已挂两代），要么自己编一条规则（违反 N-04 禁止自造数值） |
| **卡** | `PD9-04`（D-57 + D-58 合并裁）→ `PD9-05`（D-59）→ `PD9-06`（D-60） |
| **入口判据** | `decision-index.json` 里 `PROPOSED = 4`（实测） |
| **出口判据（命令）** | ① `node -e "...filter(x=>x.status!=='DECIDED').length"` → **0**；② 每条裁完的决策 `decided_by` / `decided_at` 非空；③ `applies_to` 与对应卡的 `decisions` **双向对称**（否则仍是 C-13） |
| **做完能看到什么** | `PD8-02` 从"note 里写着被挡"变成"依赖满足、可开工"；4 张卡解锁 |
| **不做什么** | 不代替用户拍板数值（`D-57` 的消耗品、`D-60` 的公式系数），只准备选项与后果；不改 `mvp-scope.md` 正文（K-01 建议用加限定语的方式，不是改范围） |

### 为什么 D-57 与 D-58 合并成一张卡（`PD9-04`）

两者都是**产品数值/口径裁决**，同一个人在一次会议里能一起定。
拆成两张 = 两次等待。**合并的理由是"同一个决策人可以一次裁完"，不是"技术上耦合"。**

而 `D-59`（v1.0 判据）必须**单独一张**（`PD9-05`）：它要改的是 `glossary.md`（术语定义），
属于**治理文档**，改动面与 D-57/58 完全不同（后者只改 `decision-index.json` + 卡状态）。

### 排序理由（为什么在 S1 之后、S3 之前）

- **必须在 S1 之后**：见上（裁决要记到对的那张卡上）。
- **必须在 S3 之前**：`D-59` 的结论决定"v1.0 完成"意味着什么，
  而 `D-61`（仓库身份）决定"完成的东西推到哪"。**先定意义，再定位置。**

### 反证与自否定

| 反驳 | 我的回应 |
|---|---|
| "决策是用户的事，规划不该排期" | 对。所以 `PD9-04~06` 的角色是 `planner`，交付物是**选项表 + 后果 + 推荐**，不是"我已决定"。卡面不写结论 |
| "D-58 已收敛为 A′，等于裁完了" | 不成立。`status` 仍是 `PROPOSED`、`decided_by` 是 `null`。**收敛方向 ≠ 裁决**。但在选项表里 A′ 列为推荐项，一次确认即可 |
| "D-60 是 COULD，为什么也建卡" | 因为 C-13 显示 `D-60.applies_to = ["PD8-08"]` 而 `PD8-08.decisions` 没有它。**只要这条不对称存在，守卫就永远红**。所以必须给它一个终态（裁或撤），不能留悬空 |

## S3 · 身份与推送（让"双端一致"有定义）

| 项 | 内容 |
|---|---|
| **谁需要** | 用户（"推送到 GitHub 保证双端一致"是本轮明令）；下一个接手的人（clone 下来要能跑） |
| **没有会怎样** | 现在有 **4 个提交卡在本地**（`a8b7ac9 / 39efe36 / 7b476c0 / 45111c3`），远端停在 `11c7427`。双端**不一致**，且已尝试过失败 |
| **卡** | `PD9-07`（裁 `D-61`：哪个远端 + 哪个分支名）→ `PD9-08`（推送 + 校验） |
| **入口判据** | `git rev-list --count origin/master..HEAD` = **4**；`git ls-remote https://github.com/nevermeetagain/WDF.git` 返回 `4e572fa`（祖先） |
| **出口判据（命令）** | ① `git rev-list --count <target>/<branch>..HEAD` = **0**；② `git ls-remote <target> refs/heads/<branch>` 的首列 = `git rev-parse HEAD`；③ `git branch -a` 只有一条本地分支（**不得新增分支**，N-01） |
| **做完能看到什么** | 两个 SHA 相等；GitHub 页面上能看到 `plan-v013/` 目录 |
| **不做什么** | 不新建分支（N-01）；不擅自改 `origin`（N-02）；不重签 token；不强推 |

### 为什么排在 S2 之后

因为 `PD9-04~06` 会改 `decision-index.json`，`PD9-02` 会改 `task-index.json`。
**先改完再推，一次推干净**；否则要推两轮，多冒一次凭据风险（凭据已经 403 过两次）。

### 为什么必须显式裁 `D-61` 而不是"随便挑一个能推的"

用户本轮指定 `nevermeetagain/WDF`，实测不可写且落后两天。
若我**默默**改推 `aideanew/WDF`（唯一可写且与本地一致），会造出一个**用户不知道的事实**：
他以为在 `nevermeetagain`，实际在 `aideanew`。
→ **这比推失败更糟**。所以必须先裁（`08 §3 D-61` 四选项），裁完再动手。

### 反证与自否定

| 反驳 | 我的回应 |
|---|---|
| "先推上去再说，用户事后能改" | 违反 `D-61` 的存在理由。且 push 是**不可逆的公开动作**（仓库公开） |
| "`nevermeetagain` 可能只是 PAT 权限不对，换个 token 就行" | 可能（`U-7`）。但**换 token 是用户的动作**，不是我的。我只能在卡面写明"需要什么权限" |
| "4 个提交是不是应该合成 1 个再推" | **不要**。`a8b7ac9`(PD8-06) / `39efe36`(PD8-18) / `7b476c0`(PD8-01) 对应 3 张不同卡，合成会破坏"一卡一提交"的可追溯性（`config.json.git.auto_commit_each_task = true`） |

### 排在 S3 之前还是之后？

**必须在 S1 之后、S3 之前**：

- 在 S1 之后：`PD9-01` 的守卫可能引入新红，先有守卫再修红，顺序才顺。
- 在 S3 之前：**把红修完再推**。否则推上去的 HEAD 自带一条红测试，
  下一个 clone 的人第一件事就是看到失败——**这是最贵的坏印象**。

### 反证与自否定

| 反驳 | 我的回应 |
|---|---|
| "既然是假红，改测试豁免 `EVD-8101` 更快" | **拒绝**。测试的意图是"每个 EVD 都要有说明"，`EVD-8101` 确实缺说明。改测试是**放宽标准来掩盖问题**，与 `v009`（`verify` 里没 `tsc`）同构 |

| "只跑 2 个文件够吗" | 按用户纪律（`config.json.testing.executor_scope = targeted`）够。**全量在发版前统一跑一次**（`final_regression_by = tester`） |

## 6. 切片依赖与并行可能

```
S1 ──→ S2 ──→ S3
 │              ↑
 └──→ S4 ───────┘
       │
       └──→ S5（必须最后）
```

| 关系 | 判定 | 依据 |
|---|---|---|
| S1 → S2 | **硬串行** | 裁决必须记到 `PD8-02/03`（S1 清场后 `PD7-02/03` 不再可派） |
| S1 → S4 | **硬串行** | S4 的出口判据用 `PD9-01` 的守卫作为"没引入新红"的证明 |
| S2 → S3 | **硬串行** | S2 改 `decision-index.json`，S3 要推的是 S2 之后的状态 |
| S4 → S3 | **硬串行** | 不把红测试推上去（见 S4 排序理由） |
| S2 ∥ S4 | **可并行** | 无共享可变状态：S2 改 `decision-index.json` + 卡状态；S4 改 `EVD-8101/README.md` + `document-index.md`。**文件所有权不相交**（`07 §2` 验证） |
| S5 | **必须最后** | 只改指针 |

**唯一可并行的窗口**：`S2 ∥ S4`。其余全串行。

→ **这解释了本版为什么"慢"**：5 个切片只有 1 个并行窗口。但这个"慢"是**结构性的**，
不是排期不努力——因为治理是一致的，一致性无法并行生产。

## 7. 每切片的"退出即停止"判据（防继续蔓延）

| 切片 | 做完就停，不许多做 |
|---|---|
| S1 | 守卫跑绿即停。**不要**顺手去修 `C-11` 的 29 张历史卡 |
| S2 | `PROPOSED = 0` 即停。**不要**顺手去改 `mvp-scope.md` 的 16 项清单 |
| S3 | 双端 SHA 相等即停。**不要**顺手合并提交或改写历史 |
| S4 | 8/8 PASS 即停。**不要**跑全量回归（N-03） |
| S5 | 四条 grep 命中即停。**不要**重写 `current-plan.md` 的全文 |

> 这条纪律来自 `PD8-01` 的教训：它本来只是"治理元数据修复"，
> 结果顺手做了 `document-index` 重生成、stage 占位符改写、zip 兜底包——**最后 3 个提交推不上去**。
> **范围蔓延的直接代价就是交付失败。**
