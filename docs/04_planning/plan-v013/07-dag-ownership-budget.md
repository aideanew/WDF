| 09 → 08 | 不把红测试修好就推，等于把失败推给下一个 clone 的人 | 首屏即失败 |
| 03 → 08 | `baseline_commit` 校准后 HEAD 会变，推送校验要对新 HEAD | SHA 比对必然对不上 |
| 全部 → 10 | 指针只能指向已经成立的事实 | 指针撒谎（`05-slices.md S5` 反证） |

## 3. 并行机械判定（四条件逐对验证）

判定规则（指令 §8.1）：**无共享可变状态 ∧ 契约已冻结 ∧ 文件所有权不相交 ∧ 不共用迁移号**。

- **契约是否已冻结**：本版 10 张卡**全部不碰** `packages/contracts/**` → 条件②对**全部 45 对**成立。
- **迁移号**：本版不碰 `database/migrations/` → 条件④对**全部 45 对**成立。
- → 实际只有条件①③会否掉并行。逐对结果：

| 对 | 共享文件 | 判定 |
|---|---|---|
| 01 ↔ 02 | 无（01: tools/package/tests；02: task-index） | ✅ **可并行**（但 02 依赖 01，故实际串行） |
| 01 ↔ 03 | 无 | ✅ 可并行（03 无依赖 01，**实际上这是唯一的 L0∥L1 重叠窗口**） |
| 01 ↔ 09 | 无 | ✅ 可并行（09 依赖 01，故串行） |
| 01 ↔ 04/05/06/07/08/10 | 无 | ✅ 理论可并行，均被 DAG 否掉 |
| **02 ↔ 03** | `task-index.json` | ❌ 串行 |
| **02 ↔ 04/05/06** | `task-index.json` | ❌ 串行 |
| **03 ↔ 04/05/06** | `task-index.json` | ❌ 串行 |
| **04 ↔ 05** | `decision-index.json` + `task-index.json` | ❌ 串行 |
| **04 ↔ 06** | 同上 | ❌ 串行 |
| **05 ↔ 06** | 同上 | ❌ 串行 |
| **04/05/06 ↔ 07** | `decision-index.json` | ❌ 串行 |
| **09 ↔ 08** | 无（09 不写 task-index，08 不写文件） | ✅ 可并行（08 依赖 09，故串行） |
| **09 ↔ 02/03/04/05/06/07** | 无 | ✅ **可并行** |
| 08 ↔ 任意 | 08 不写任何文件 | ✅ 可并行（但它是 git 动作，串行更安全） |
| 10 ↔ 任意 | 独占 3 个 planning 文件 | ✅ 理论可并行，被 DAG 否掉 |

**最终并行窗口（只有两个）**：

| 窗口 | 内容 | 前置 |
|---|---|---|
| **W1** | `PD9-03 ∥ PD9-01` | 无（两者互不依赖、文件不交） |
| **W2** | `PD9-09 ∥（PD9-04→05→06 任一）` | PD9-01 完成 + PD9-02 完成 |

→ **10 张卡的 45 对组合里，只有 2 对能真正并行。** 串行度 96%。

**这个数字本身就是结论**：治理类工作的并行度天然接近 0，因为它改的是**同一个事实源**。
任何"多 agent 并行治理"的方案在这份所有权矩阵面前都会撞墙。

## 4. 档位分配与成本预算

### 4.1 档位规则

| 档 | 用途 | 硬约束 |
|---|---|---|
| `fable` | 需要**一次设计判断**、返工代价最高的卡 | **每切片 ≤1 次** |

## 5. 熔断与停止条件

| 场景 | 动作 | 依据 |
|---|---|---|
| **同一张卡连续 2 次验收失败** | **停止改代码**，把失败命令与输出写成 `EVD-9xxx/README.md`，卡转 `BLOCKED` + `blocked_reason` | 指令 §熔断 |
| 守卫 `PD9-01` 上线后 error 数 > 100 | 停止，先做分级调整（把 P2 降为 warn），再继续 | 防止"满屏红"导致绕过守卫 |
| `PD9-08` 推送连续 2 次 403 | 停止，不换第 3 种认证方式；直接转 `BLOCKED` + 输出 zip 兜底 | `PD8-01` 已踩：硬试只烧时间 |
| 任何卡发现要改 `packages/**` | **立即停止**，本版范围外 | `06 §1` 零业务代码声明 |
| `PD9-04/05/06/07` 用户未回复裁决 | 该卡保持 `TODO`，**不自行填 decided_by** | 裁决权属用户 |
| 发现新的 P0 缺陷 | 登记进 `08-metrics-risks.md`，**不在本版修**（防蔓延） | `05-slices.md §7` |

## 6. 关键路径（决定总工期的那条线）

```
PD9-01 → PD9-02 → PD9-04 → PD9-05 → PD9-06 → PD9-07 → PD9-08 → PD9-10
（8 张卡，全部串行）
```

| 卡 | 是否在关键路径 | 说明 |
|---|---|---|
| PD9-01 | ✅ | 起点，且是 fable 唯一消耗点 |
| PD9-02 | ✅ | 抢 `task-index.json` |
| PD9-03 | ❌ | 可与 04/05/06 交错，但抢同一文件 → 实际也串行，只是不延后终点 |
| PD9-04/05/06 | ✅ | 三张都抢 `decision-index.json` |
| PD9-07 | ✅ | 唯一裁 D-61 的卡，`PD9-08` 硬依赖 |
| PD9-08 | ✅ | 终点前必须成功 |
| PD9-09 | ❌ | 可与 S2 并行（窗口 W2） |
| PD9-10 | ✅ | 终点 |

**结论：8/10 在关键路径上，关键路径长度 = 8。**

**缩短关键路径的唯一办法**：把 `PD9-04/05/06/07` 四张决策卡**合并成一次裁决会**（用户一次给出 4 条裁决），
则 4 张卡退化为 1 个"落账"动作，关键路径从 8 降到 **5**：

```
PD9-01 → PD9-02 → PD9-落账(04~07) → PD9-08 → PD9-10
```

→ **这是本版能给用户的最具体的提速建议：一次性把 D-57/58/59/60/61 五条裁完**（`08 §3` 已备选项表），
比任何排期优化都有效。

## 7. 与既有 PD8 卡的交叉

| 项 | 事实 |
|---|---|
| 本版是否重写 PD8 卡面 | **否**。18 张 PD8 卡原样保留（`00 §4`） |
| 本版是否改 PD8 卡状态 | **仅 04/05/06 三张会改 `decisions` 字段**，不改 `status`（除了 `PD8-07` → 见 `PD9-04` 的 note 提及 D-63，实际在 `08 §3`） |
| 本版与 PD8 的路径重叠 | **0**（本版不碰 `packages/**`、`client/**`、`server/**`、`game-data/**`） |
| 结论 | 本版可与 PD8 的任意实现卡**并行执行**，不会覆盖 |

**→ 这是本版相对 v012 的一个实质改进**：v012 的 `PD8-*` 相互有 7 对路径重叠（`02 §4`），
而 `PD9-*` 与 `PD8-*` 的重叠是 **0**。治理卡与实现卡天然不抢文件。
