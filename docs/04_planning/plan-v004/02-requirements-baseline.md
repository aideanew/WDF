# 02 · 需求基线复核

## 2.1 复述与拆解

**核心问题**：完成 v1.0 版本的"临门一脚"，补齐玩家在界面层（UI）的交互拼图，使得后端已有的 `economy.sell`、权威背包逻辑，以及数值表中已落地的 `merchants` 和 `locks` 能真正在客户端展示并被玩家使用，最终通过合规检查，达成 v1.0 的可玩、可审核标准。

**关键词**：UI 实现（商人页、回收入口、开锁交互）、契约解冻（错误码）、真机验证、文档对齐。

## 2.2 需求分级

| 级 | 内容（每条可验证） |
|---|---|
| MUST | ① 商人页UI实现并能调通 `economy.sell`；② 背包提供回收入口组件；③ 遇到带锁箱子时弹出开锁交互，完成打捞结算；④ 2004 错误码按计划解冻并接入系统。 |
| SHOULD | 真机 6 态测试及性能采样，合规清单文档就绪。 |
| COULD | 暂时无。 |
| MUST NOT | 严禁自编数值（已锁定在 decision-sheet 中）；严禁修改已冻结的其他契约；严禁跳过测试和规范检查直接修改业务代码。 |

## 2.3 冲突检查

1. **MUST 与 MUST NOT 冲突**：本次任务规划指令要求“核心任务+高难度任务你自己完成（尤其是UI设计和实现）”，但全局硬约束规定“默认只读。不得修改任何业务代码。仅可写入规划产物”。
   **裁决**：作为规划 Agent，本次只输出规划（落盘到 `docs/04_planning/plan-v004/` 和 `docs/05_execution/tasks/`）。在任务卡中，明确指定该 UI 任务交由具备写权限的执行 Agent（如助手 A 或核心执行器）来落实。
