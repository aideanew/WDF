# 08 · 档位分配与成本预算

## 1. 本项目档位的实际含义（不套虚名）

输出格式 §8.2 给的是模型档位名。本项目的执行体系是 `config.json:roles` 三角色，
**必须先把两套词对齐，否则预算表是空的**：

| 输出格式的名称 | 本项目对应 | 谁 |
|---|---|---|
| `fable`（最强最贵） | 规划者终裁 / 改已冻结口径 | 用户（裁决）+ 主控（起草） |
| `opus` | 主控（Claude）—— 架构、契约语义、**UI**、高风险 review | 主控 |
| `sonnect`（主力） | 执行助手（DeepSeek）—— 原子实现、单测、CRUD、迁移脚本 | executor |
| `haiku`（最廉） | 机械活 —— 改注释、索引更新、模板填充 | executor（低成本模式）或 tester |

**默认档 = opus**（按 §8.2）。下表**逐卡**给出档位与理由；凡写 `sonnect` 的都必须说明"为什么不需要 opus"。

**券制度（每阶段额度）**：

```
opus   每阶段 ≤3 次（契约审 / 卡住升级 / 高风险 review）
fable  每阶段 ≤1 次（仅当需要动需求或已冻结口径时）
超出 → 停下来找用户批，不许自行"多花一次应该没事"
```

**本版预算与券制度的冲突必须提前说清**：A 阶段按卡算有 **3 张 opus**（01/03/04），正好用满额度；
C 阶段有 **4 张 opus**（10/11/14/15），**超出额度 1 次**。处置：
C 阶段拆成两批（C1 = 10/11/12/13，C2 = 14/15/16），每批 ≤3 次 opus —— **不是放宽额度，是拆批次**。

## 4. 阶段体检协议（用户明确要求：按阶段体检，拒绝全量回归）

### 4.1 单卡（日常）

```bash
npm run gen                 # 只在该卡改了 game-data/ 或 contracts/ 时跑
npm run impact <关键词>     # 圈定受影响的测试文件（tools/guard/impact.mjs）
node --import ./tools/runtime/register.mjs --test <圈出的文件>
```

**禁止**在单卡里跑 `npm run verify`（gen + guard + test + typecheck 全量）。
唯一例外：该卡改了 `tools/guard/**` 或 `packages/contracts/**`（本版无此卡）。

### 4.2 阶段出口（每个阶段一次，且只一次）

| 阶段 | 出口检查命令 | 必须全绿才算出口 |
|---|---|---|
| **A** | `npm run verify` + `du -sh client/build/wechatgame` + 人工截图（3 张：筏 Tab / 建成 / 拒绝态） | ✅ |
| **B** | `npm run gen && node tools/guard/placeholders.mjs && npm run test` | ✅（31 空表 = 0） |
| **C** | `npm run verify` + `pd.mjs health .`（0 错误） | ✅ |
| **D** | `npm run release:check` + 提审清单人工项 | 外部依赖项记 `UNKNOWN` |

### 4.3 全量回归（只在两处）

1. **阶段 C 出口**（因为 C 动了 7 个模块的跨模块参数）；
2. **发版前**（`release-checklist.md` 要求）。

## 5. 防自证循环（§9.3 的落地）

| 环节 | 谁做 | 禁止 |
|---|---|---|
| 写验收标准 | **本规划（已完成）** —— 每卡的 `acceptance` 已写进 `task-index.json` | 执行者不得改自己的验收标准 |
| 执行 | 执行助手 / 主控 | — |
| 判定 | **独立验证者**（tester 角色），**只看 diff + 命令输出** | 不许读卡面自述当证据 |
| 输出格式 | `PASS` / `FAIL` / `UNKNOWN` 三个词 + 一行依据 | 不写长篇解释；`UNKNOWN` 必须写"缺什么" |

**验证者的硬约束**：`pd.mjs record --event TESTED` 的 `PASS` **必须带 `--cmd`**（`pd.mjs:502` 已强制），
所以"我觉得过了"这种判定在工具层面就写不进去。

## 6. 熔断规则（§8.4 落地）

```
同一张卡连续 2 次验收失败
  → 立刻停止改代码
  → 三选一：① 重写卡面（验收写错/步骤漏了前置）
            ② 升档（sonnect → opus）
            ③ 标 BLOCKED 并上报（缺数据/缺决策/缺环境）
  → 禁止换提示词硬撞第 3 次（隐性烧钱最大的洞）
```

本版已预判**最可能熔断的三张卡**：

| 卡 | 为什么可能熔断 | 预置出路 |
|---|---|---|
| PD7-03 | UI 无自动化测试，验收靠截图；主控自评容易"看起来对了" | 出口检查要求**3 张截图**且必须包含"拒绝态"，缺一张不算过 |
| PD7-08 | 5 张表 + 30 行半实现，容易一步写太多 | 卡面已限制"只做 1 波可跑通"，不做多波平衡 |
| PD7-15 | 塔防是全项目最重的一环 | `mvp-scope.md:52` 已授权降级为文字结算 → 第一次失败即可考虑降级，不必硬撑 |
