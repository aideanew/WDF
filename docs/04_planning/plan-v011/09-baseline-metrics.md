# 09 · 基线指标

> **本版不排任何"优化"任务。** 理由在 §4：三个真正重要的用户可感指标**全部没有基线**。
> 没有基线就排优化，等于给一个不知道起点的人定"跑得更快"的目标 —— §13.8 明令禁止。

## 1. 用户可感的 3 个核心操作（先选操作，再选指标）

| # | 操作 | 玩家在哪一刻感知到它 | 可测的代理指标 |
|---|---|---|---|
| O-1 | 冷启动 → 点"进入主界面"看到打捞面板 | 第一次打开游戏，"怎么还没进去" | ① 主包体积 ② 启动链 RPC 次数 ③ 首屏节点数 |
| O-2 | 一次完整出钩（蓄力 → 命中 → 入包 → 写存档） | 每 1–3 秒一次，是全游戏最高频操作 | ① 单次 hook 判定耗时（纯函数） ② 每次出钩的存档写入次数 |
| O-3 | 完成一次「捞 → 做 → 扩」 | **本版新增的第五环**，决定 v1.0 是否成立 | ① 从空手到扩一格需要的钩数 ② 该链路上的 RPC 次数 |

> **注意 O-3 现在是"不存在"，不是"慢"。** A 阶段做完之后它才第一次可测。

## 2. 指标的资格判定（§9.1 要求：证明不了"数字降了用户也感知到"→ 下线）

| 指标 | 能证明"降了→用户可感吗" | 判定 | 处置 |
|---|---|---|---|
| 主包体积（MB） | **能（方向性）**：微信小游戏首包需下载后启动，包体与下载时长在弱网下单调相关 | ✅ **保留** | 作为 A 阶段出口的观察项 |
| 启动链 RPC 次数 | **不能**：本地回环 RPC 是毫秒级，减少 1 次玩家感知不到；真实弱网下才有影响，但无真机数据 | ❌ **下线**（不作为目标） | 只作"设计约束"记录，不设指标 |
| 单次 hook 判定耗时 | **不能**：`hook/index.ts` 是纯数学，Node 单次 < 1ms，已在帧预算里可忽略 | ❌ **下线** | 不测 |
| 每次出钩存档写入次数 | **能（有依据）**：微信 storage 同步写会掉帧，写次数与卡顿正相关 | ⚠ **部分可证** | 只登记当前值，不设目标 |
| 完成「捞→做→扩」所需钩数 | **能**：直接等于玩家"多久能扩第一格"，是最直观的成就感 | ✅ **保留** | **本版核心体验指标** |
| 背包面板首帧节点数 | 不能（无真机帧率数据） | ❌ 下线 | 不测 |
| 测试数 / 守卫数 | **不是用户可感** | ❌ 不作为"优化目标" | 只作**闸门**（§3） |

### 3.2 尚无基线（明确标注，不许伪精确）

| 指标 | 状态 | 缺什么才能测 |
|---|---|---|
| 冷启动 ≤5s（P90）/ 低端弱网 ≤8s | **尚无基线** | 真机 + 微信开发者工具真机调试（`01 §F-3`） |
| 低端安卓 4GB 稳定 30 帧 | **尚无基线** | 真机 profiling |
| 内存 180–250MB | **尚无基线** | 真机平台工具 |
| 本地存档 ≤300KB | **尚无基线** | 一次完整游玩的存档体积采样（本地存档结构存在，但无采样脚本） |
| 首钩命中率 ≥45%（C1） | **尚无基线**（有 SIMULATED 值 12/20 = 60%，**不得当作基线**） | D-52 `red_lines` 明确禁止 |
| 完成「捞→做→扩」所需钩数 | **尚无基线，且现在不可测**：扩筏不存在（`02 §1.2`）⇒ A 阶段完成后才能首次测量 | 扩筏落地后跑一次人工序列 |

## 4. 因此本版的行为约束（写死）

| # | 约束 | 依据 |
|---|---|---|
| **M-1** | **不排任何以"优化/提速/减包"为目标的卡** | §13.8：缺少基线就排"优化"任务 = 禁止 |
| **M-2** | 主包体积只在 A 阶段出口**观察**，不设"必须降到 X" | 3.1/3.5 已有余量，且降包需要动 Bundle/引擎裁剪（高风险、无收益证明） |
| **M-3** | 每张卡若新增"性能敏感"逻辑（如离线结算遍历全表），卡面必须写清**复杂度上限**（O(n) 且 n ≤ 106 行 CSV），不做基准测试 | 106 行物品表的上限使 O(n²) 也只有 1 万次运算，测了没意义 |
| **M-4** | 允许出现的"数字目标"只有一类：**闸门类**（§3.1）与**体验类**（扩筏所需钩数，A 阶段采集首值后由用户定目标） | 其余一律不许写数字 |
