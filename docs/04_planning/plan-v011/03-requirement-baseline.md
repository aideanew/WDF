# 03 · 需求基线复核

> 需求虽已由人理清，本文件仍**独立复核**一遍。复核结论与既有裁决冲突时，**以裁决为准**（裁决是用户的决定，复核只是我的判断）。

## 1. 复述与拆解

**项目要解决的核心问题**（一句话）：做一款「出钩打捞 → 制作 → 扩筏 → 商人回收」为核心循环的微信小游戏，
三平台（微信 / 抖音 / 未来 APP）共用一套客户端逻辑与一套服务端，**必须联网**（ADR-0008），服务器为竞争数据的唯一权威。

**拆解与关键词**：

| 维度 | 内容 | 证据 |
|---|---|---|
| 用户 | 微信小游戏玩家，性能基线 = 10 年前手机 / 4GB 安卓 | `REQ-NF-0001:10`；`product-vision.md` |
| 管理端 | **不做界面**，只有脚本 + SQL（开新区、封号） | `mvp-scope.md:56`；TASK-1401 已落地（`1d34fc6`） |
| 系统边界 | 客户端 Cocos 3.8.8 + 网关 Fastify 5 / PGlite + 纯规则包 game-core + 数值包 game-data | `README.md:8-19`；`docs/03_solution/architecture/architecture-overview.md` |
| 权威划分 | 金币/榜单/存档 = 服务端权威；出钩/合成/浮力 = game-core 本地确定性判定 | ADR-0012；`glossary.md:32-35` |
| 版本节奏 | v1.0（微信首发）→ v1.1（上线后 2–4 周）→ v2.0（PVP/交易等，只登记） | `mvp-scope.md:44-68` |

## 2. 分级

### 2.1 MUST（缺失则本版不成立）—— 每条都改写成一句可验证的话

| # | 需求 | 可验证改写（**这就是验收判据**） | 现状 | 归属阶段 |
|---|---|---|---|---|
| **M-1** | 扩筏可演示（C2 的"扩"） | 玩家在主界面能找到一个入口，点进去看到当前船体地块数、点"建一格"后地块数 +1、金币按 `prices` 扣除、**浮力不足时被拒绝并显示差额**，退出重进后地块数不变 | ❌ 无入口（`MainView.ts:27-34`） | A |

| **M-3** | 拒绝态可辨（六态第 4 类） | 浮力不足时 UI 显示 `3000 段` 文案 + 差额数字，**不是** `4999 服务器故障`，且不自动重试 | ⚠ `3101` 只存在于 game-core，无 UI 消费 | A |
| **M-4** | 出钩手感（C1） | 同一输入序列（蓄力时长 + 角度）在 Node 与客户端得到相同命中结果 | ✅ `hook 152` + `tests/determinism/hook.test.mjs` | 已完成 |
