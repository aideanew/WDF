# 06 · 垂直切片

## 1. 切片原则（与本仓现实的对齐）

正常项目的第一刀是"步行骨架"（健康检查 + 鉴权写接口 + 一张表 + 前端打到真 API）。
**本仓的步行骨架已经存在**（22 动作 / 15 实现 / 云存档闭环 / 8 个真 UI 面板），
所以本版的第一刀**不是**再搭骨架，而是**先修地基上的裂缝**：

> **SG-1 治理收口** —— `pd.mjs health` 5 错误 + 19 个未推提交。
> 它不产生任何玩家可见行为，但它是唯一"不做就会让后续所有决策失真"的一刀。
> 判据：`health` 0 错误 + `status` 不再输出 `undefined` + `origin/master == HEAD`。

## 3. 诚实承认：5 个切片"不可演示"，为什么仍然要留

| 切片 | 为什么不可演示 | 为什么必须存在 |
|---|---|---|
| **SG-1** | 治理元数据不是玩家行为 | 不做它，`pd.mjs status` 的阻塞原因是 `undefined` → 后续派工基于坏数据 |
| **SG-2** | 改的是测试断言，不是产品行为 | **不做它，所有"阶段出口 `verify` EXIT=0"都是空话**：`items-w 3/6` 两条断言写的是 D-54 之前的语义，在 HEAD 恒红（`01 §4`） |
| **SA-1** | 纯函数，没有界面 | SA-2 的 UI 要调它；先做它 + 测试，SA-2 才有可依赖的地基 |
| **SB-1** | 枚举扩展，用户看不到 | **它是 10 个模块的前置**：`TableName` 不扩，`levels`/`unlocks`/`jobs`/`rooms` 全不可读（`02 §1.4`） |
| **SB-2** | 是"输入换成配置"，行为看起来一样 | 不做它，"打捞"这一环永远只有 1 种产出（`HookModel.ts:21`），C2 的"捞"是假的 |

**这与 §5.2 的"每刀必须多一个可演示行为"冲突**——我承认，并给出处理：
前 5 刀是**投资**，用最短路径做完（每刀 ≤ 半天），不追加任何"顺手优化"。
从 SA-2 起，每一刀都恢复"可演示"要求。

**关键观察**：`SB-1`（`TableName` 扩展）是**唯一一个横跨 A 段与 C 段的切片**。
它不做，SC-1~SC-9 全部无法读取自己的表 → 这是本版最重要的"先做它"的理由。

## 6. 为什么不是"前端组 / 后端组 / 数据组"

因为本仓 13 个模块**全部是客户端侧**（`05 §1` 结论：零 PG 表改动）。
如果按"后端组"切，后端这一组**没有活干**（7 个 todo 动作里 5 个属 `salvage`/`event`/`social`，
而这 3 个模块的实现恰好就是它们的客户端 + 服务端，同一个切片内）。
按技术层切会出现两组互相等；按切片切每刀自闭环。
