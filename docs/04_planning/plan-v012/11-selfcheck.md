## 4. 建议第一刀（如果只做一件事）

### 4.1 第一刀不是 PD8-01，而是 **PD8-06 + PD8-18 并行**

理由（三条，逐条可验）：

1. **PD8-06 是 10 张卡的唯一前置**（`07 §1` 的入度表：PD8-07~16 共 10 张卡都 `depends_on PD8-06`）。
   不做它，C 段 9 张卡全部读不到自己的表 —— 这是**单点瓶颈**。
2. **PD8-06 的收益/成本比最高**：纯类型扩展、零逻辑改动、`sonnect` 档、半天、且**它的验收本身就是"46 张表能不能读出来"的行为证据**（不是结构证据）。
3. **PD8-18 是"判定可信"的前提**：不做它，`items-w` 2 条恒红 → 任何人跑 `npm run verify` 都会认为"仓库是坏的"，后续每张卡的"验收失败"都无法区分"我改坏了"还是"本来就红"。

### 4.2 为什么 PD8-01 可以稍后

PD8-01 修的是**治理元数据**（`health` 5 错误）与**推送**。
它不产生任何代码能力，但它有一个硬前置：`~/.git-pat` 权限 644（协议要求 600）+ 用户确认"就绪"。
**在你确认之前，PD8-01 的第 7~10 步（chmod / 提交 / 推送 / 回读）无法执行**，
而第 1~6 步（修 task-index）只要 30 分钟。

→ 所以第一刀的并行安排是：

```
第 1 天上午：PD8-06（TableName 46）∥ PD8-18（测试口径）∥ PD8-01 步骤 1~6（元数据）
第 1 天下午：PD8-01 步骤 7~10（chmod + 逐文件 add + 推送）← 需你确认 ~/.git-pat 就绪
```

## 5. 给下一个执行者的一段话（交接）

> 这个仓库最大的坑不是"没写"，而是**"写了但输入是占位值"**。
> `facilities.effect_bp` 九行全是 10000、`items.stack` 106 行全是 99、`recipes.unlock_level` 80 行全空 ——
> 每一个都长得像"已有数值"，而每一个都不是。
> 所以你读任何一段代码时，先问一句：**它的输入是从哪来的？** 如果答案是"常量"或"表里那列",
> 就去 `game-data/schema` 看那列是不是 `draft`、看那列的值是不是全表同值。
> `02 §11` 那张 11 行 draft 表就是你的地图：**列数 = 3 的表（`rooms`/`waves`/`limits`/`phrases`/`regions`）
> 只有 `id/name/note`，它们不能支撑任何玩法计算。**
>
> 第二条纪律：**验收必须是行为证据**。`grep` 到表名不算，读到行数才算；
> 写在注释里的流程不算，方法体里有 `return` 才算。
> 本版所有卡的验收都按这条写，你也按这条交。
