## D-42 · 35 张空表的数值来源与 v1.0 范围重裁 🔴

**事实基线**
- 46 张数值表，**35 张 0 行**（`game-data/UNKNOWN-TABLES.md §二`）。
- 这 11 张有数的表里，**除 `prices` / `items.base_price` / `recipes` 原料配比外，其余字段几乎全是 D-07~D-10 的裁决占位值**（`04 §4`）。
- 13 个未实现模块中 **11 个**的第一阻塞点是空表（`02 §2.1`）。

**为什么必须人来定**
填这些数不是"找个合理值"——它是**游戏平衡的唯一来源**。我编一个"员工幸福感 25×4"的数字，
玩家体验就是错的，而没有任何测试能发现"错得离谱"（因为测试只验算得对不对，不验好不好玩）。

**条件方案**

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A. 逐表裁决** | 用户（或授权 hark 代定）按 D-01~D-10 的同一格式，一批一批给值 | 35 张 × 平均 8 列 ≈ 280 个数字，按每天 5 张算 ≈ 7 天 | 裁决期间开发停摆；且"代定值"会重复 D-07 的错误（占位当真实） |
| **B. 缩 v1.0 范围** | v1.0 只交付 `02 §2.1` 的 8 个完成模块 + **扩筏（C2）**，其余 12 个模块移入 v1.1 | 功能少，但每个是真的 | 与 `mvp-scope.md §5` 的"v1.0 已定范围"冲突 → 需显式修订该文档 |
| **C. 混合** | 只补"核心循环必需"的 4 张表（`levels` / `unlocks` / `raft_tiles` / `rooms`），其余移 v1.1 | 比 B 多一个"等级推进"；比 A 少 31 张表 | 需要 hark 代定 4 张表 ≈ 60 个数字，仍可能编错 |

**共同部分**（无论选哪个都要做）
S0（7001~7005）、S1 的 7010/7012、S2 的 7020/7022、S4 的 7041/7042、S5。

**分叉点**
选 A → S3 全开；选 B → S3 只留 7031（扩筏）；选 C → S3 留 7031/7032/7033。

**我的倾向（非结论）**：**C**。
理由：`mvp-scope.md:19` 有一条闸门——「**C1 未达标前不扩展新系统**」。
C1（出钩手感）已实现但**没有真机手感数据**（`success-metrics.md` 的 "30 秒学会 ≥70%" 需真人测试）。
在 C1 未经真人验证前，把 12 个未验证手感的系统全部实现，等于在未验证的地基上盖 12 层楼。
**但这条倾向本身也缺证据（C1 到底达标没有），所以我不能替你定。**

**需你回答**：A / B / C（或"先按 C 做，同时你补 A 的数据"）。

## D-43 · `items.weight` / `capacity` 真实值 🔴

**事实基线**

```bash
# items.csv 全表实测
weight  取值集合: [ '1' ]     # 106 行全是 1
capacity 取值集合: [ '0' ]    # 106 行全是 0
```

**后果（不是推测，是算术）**
`packages/game-core/src/raft/index.ts:10-15`：

```ts
export function remainingBuoyancy(hull: readonly Load[], cargoWeight: number): number {
  let cap = 0; let w = cargoWeight;
  for (const t of hull) { cap += t.capacity; w += t.weight; }
  return cap - w;          // = 0×n - (cargo + 1×n)  → 恒为负
}
```

⇒ **任何非空船体的 `checkChange()` 都返回"浮力不足"→ 扩筏永远失败 → C2 循环断在第三步。**

**为什么必须人定**
浮力是"捞—做—扩"的核心手感：材料容量太小 → 玩家扩不动；太大 → 无挑战。
这是平衡设计，不是技术选型。**且设计源确实没给**（`UNKNOWN-TABLES.md §三` 已登记）。

**条件方案**

| 方案 | 内容 | 代价 |
|---|---|---|
| **A. 设计源补值** | 由原设计者补 `材料与工具总表` 的容量列 | 最准；但需设计者时间，不可控 |
| **B. 授权 hark 代定** | 按"容量 ≈ 面积/10、物品重量按品类（原料 1 / 工具 3 / 设备 10）"生成一版 | 快；但必然与设计意图有偏差，需试用后调 |
| **C. 暂不扩筏** | 承认 C2 不完整，v1.0 只做到"捞 → 做" | 诚实；但 C2 是本项目的核心循环之一 |

**我的倾向**：**B**，并**明确标注它是可调值**（进 `UNKNOWN-TABLES.md` 而不是伪装成设计源原值）。
理由：C2 的缺失比"数值不准"严重得多——没有扩筏，玩家 15 分钟就撞墙（`mvp-scope.md:16` 的验收是"连续玩 15 分钟不卡不迷路"）。

**需你回答**：A / B / C。

## D-46 · "功能未开放"用哪个错误码 🟡

**事实基线**：8 个 todo handler 返回 `ERR.INTERNAL (4999) + 'not implemented'`。
客户端会把 `4999` 当系统错误 → 弹"网络异常"→ 玩家重试 → 永远失败。

**选项**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 复用 4999 + 固定 msg** | `msg = 'FEATURE_NOT_AVAILABLE'` | 零契约变更；但"用 msg 当协议"是坏味道 |
| **B. 新增 4998** | 需解冻契约（ERR 15→16 码） | 干净；但要 ADR + 客户端同步 |
| **C. 不改，客户端按 action 白名单判断** | 客户端维护"未开放动作列表" | 双源，最差 |

**我的倾向**：**A**（本期），把 B 登记为解冻窗口的候选。
理由：这 8 个动作在 v1.0 里本来就不该被调用（客户端没有入口）。**为一个不该发生的路径解冻契约，收益为负。**

**需你确认**：A 可否。
