# 03 · 自我否定清单

> 纪律：下任何结论前先找自己的反证。本文件按"错得多严重"排序，不按时间。

## N-1 ★最贵：我上一轮"修好了"一处注释，其实只是给一个不存在的东西换了措辞

**我做了什么**（commit `ea6ad20`）：把 `GameApp.ts:4` 的
`5 save(load+migrate)` 改成 `5 save(load)`，并补了「第 5 步没有 migrate」的说明，
还把它写进了提交信息与记忆，当作"诚实化"的成果。

**实际是什么**：`GameApp.start()` **只有 6 行有效代码**（取 platform、注册 onHide），
**第 2~7 步一行都没有**。整条启动链是虚构的：

```ts
static async start(): Promise<void> {
  if (GameApp.started) return;
  GameApp.started = true;
  const platform = getPlatform();
  platform.lifecycle.onHide(() => {
    // 切后台尽力保存：services/save.flush()
  });
}
```

**我为什么没发现**：我只盯着"migrate 有没有被调用"这一个词，**没有问"这条链存在吗"**。
这是典型的**局部正确掩盖整体错误**——我验证了一个细节的真假，
却没验证承载这个细节的容器本身是否存在。

**修正动作**：S0-7002 把 `GameApp` 的注释改成"本类只做 onHide 注册，启动链在 BootController"，
并把"离线结算 / Bundle 预下载 / save.flush"三项**登记为未实现需求**（M-2/S-4），不再当作既有能力。

> **教训（写进记忆）**：修注释前先问「这句话描述的对象存在吗」。
> 改措辞 ≠ 改事实。**给虚构的流程改措辞，会让虚构看起来更可信。**

## N-2 v009 的收官口径把"门禁全绿"当成了"项目状态良好"

v009 的终值是：`verify exit=0` / 守卫 9/9 / 174 tests pass / 双 tsc 0 错。
这个陈述**字面为真**，但它给读者的印象是错的：

- 174 个用例**全部落在 8 个模块**（hook/crafting/inventory/chest/economy/leaderboard/save/account）；
- 另外 15 个模块**一行代码都没有**，所以自然 0 用例；
- 9 项守卫检查的是"目录/清单/边界/纯度"，**没有一项检查"模块里有行为"**。

⇒ **"全绿"是"没有代码可以出错"的全绿。** 这跟"测试通过"是两件事。
本版 S0-7001 新增空壳检测，就是为了让这个差别变成红灯。

## N-3 我（在更早的轮次）把"文件内容为空"等同于"功能不存在"

v009 `02-fact-corrections.md` 更正 1 已记过一次（F-42 版本闸），当时的教训是
**"判定功能不存在前必须 grep 全仓"**。

本版又犯了第三次，形态是：**把"目录存在 + 类存在 + 装饰器存在"等同于"模块有实现"**。
`features/fishing/` 有 `FishingModel` 类、有 `@ccclass` 装饰器、有 `lateUpdate` ——
一切"看起来对"，但方法体是空的。

⇒ 结论：**"存在性"有三种伪装：文件空、功能搬家、脚手架齐全。三次都是同一个病根——用结构证据代替行为证据。**
本版的判据统一改成：**要么有可执行的断言，要么有可复现的行为，否则一律记为未实现。**

## N-4 我上一版说"v1.0 仍在收口中"，这是重大低估

`current-plan.md:14` 写着「**v1.0 仍在收口中**」。按 `02-requirement-inventory.md` 的实测，
v1.0 的 24 个模块里只有 **7 个完整**，13 个**完全未实现**。

"收口"意味着"差最后一点"。**实际是半程。**
这句话是我写的（v009 TASK-6005 落盘），它会让接手者按"收尾"的心态排期 → 必然崩。

**修正**：本版把 `current-plan.md` 的现行指针改为 v010，并把措辞从"收口"改为
**"8 完成 / 3 部分 / 13 未实现"**（S5-7051）。

## N-5 我一度认为"数值表 11 张有数"意味着数值基础已具备

`UNKNOWN-TABLES.md` 用 ✅ 标记了 11 张"已转录"的表，我一开始把它读成"数值可用"。
实测 `items.weight` 取值集合 `{1}`、`capacity` 取值集合 `{0}` ——
**这两列是 D-07 的占位裁决值，物理意义为零**。

⇒ 一张表"非空"和"可用"是三件事：**非空 / 语义正确 / 数量级合理**。
本版新增 I-2（占位值必须可区分）作为流程修补。

> 顺带自查：`locks.hits_required` = 0/3/5/8/12、`chests.smashable` 全 `true`、
> `recipes.unlock_level` 全 `0`、`items.stack` 全 `99` —— 同样是 D-08/D-09/D-10 裁决占位。
> **除 `prices`/`items.base_price`/`recipes` 的原料配比外，几乎全部"已转录"字段都是裁决占位值。**
> 这条如果成立（S3-7030 需逐列核），则"11 张表有数"应降级为"3 张表有真实数值"。

## N-7 我上一版把"未实现"的边界划在"契约里有没有"上，划错了

v009 认为 `economy.sell` 不存在（ADR-0010 缺口 1）。现在它在 `handlers.ts:47` 实现了。
我当时没有反向搜 `handlers.ts`，只看了 ADR 文本。

本版因此对所有"未实现"结论都做了双向核：**既查契约声明，也查 handlers 注册表，也查实现体**。
例：`ads.claim` 契约完整（`packages/contracts/src/ads/index.ts` 2 行）且 `ad_placements` 有 3 行数据，
所以它**不是"缺数值"**，而是"没写代码" —— 这个区分决定了它能不能派给外部 Agent。
