## 2. 为什么本规划不产出性能基线（诚实说明）

用户 §9.1 要求"定义 3–5 个用户可感的核心操作 + 首次测量值"。我**没有做**，理由三条：

1. **用户 10-23 已定"先本地开发，不用真机"**。而"用户可感耗时"必须在目标机型上测（基线是"10 年前手机性能"）。在开发机上测出的数字**不能代表用户可感**，测了也是伪精确（§13 禁止第 7 条：无数据支撑的伪精确量化）。
2. **用户 16:44 明确"拒绝全量回归/门禁"，要求"按阶段体检效率最高"**。性能采样属于"全量"性质的动作，与本轮节奏冲突。
3. **§9.1 的结论本身**："没有基线数字，后续禁止任何'优化'任务。" → 本规划**未排任何优化任务**，所以不需要基线。这是自洽的。

**代价（不粉饰）**：
- 发版前无法回答"包体积是否超标"（已知历史值：主包 3.1MB，引擎 `cocos-js` 占 2.5MB，微信上限 4MB → **余量不足 1MB**，这本身就是风险）。
- 无法回答"开箱一次要多久"。

**补救**：`08` 的 TASK-5011 第 2 步加了"最后一次全量体检"，届时可顺便采三项最低成本基线（构建产物体积 / `chest.open` 服务端耗时 / `npm test` 总时长）。**但这三项都不满足"用户可感"标准，只能做趋势参考，不得作为优化目标。**

→ 已登记为 **BLOCKING-B5**（见 §3）。
