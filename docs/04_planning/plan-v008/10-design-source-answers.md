# 10 · 从最初设计文件找回的答案

## 1. 直接回答 B-1（三箱要不要配锁）：**问法错了，真实情况更麻烦**

### 1.1 设计源说了什么（原文）

| 位置 | 原文 |
|---|---|
| `对话讨论.txt:4151` | 「开锁与箱子：箱子分木 / 铜 / 铁材质 × 不上锁 / 铁 / 铜 / 银 / 金锁；开锁工具三级，用一次断一个；**上锁箱不能砸**。」 |
| `材料与工具总表.md:100` | 「**小锁柜** \| **任意箱子 + 一把锁（装上即成）** \| —」 |
| `对话讨论.txt:5117` | 「第三层：首版建议延期 —— **所有材质箱子与五类锁组合形成的完整开锁矩阵**。」 |
| `对话讨论.txt:5162` | 「3 类箱子 × 5 种锁已经有 15 种组合；开锁工具只有 3 级，每次还会损坏。**必须提前定义每级工具能够开哪些锁、消耗多少耐久，以及不同锁对应的收益**。否则玩家和开发者都不知道规则是否合理。」 |
| `材料与工具总表.md:167` | 「很多东西不能打造（如**开锁工具**、发电机、发动机）」 |

### 1.2 三条硬结论

**结论 A：锁不是箱子的属性，是可装上去的独立物品。**

「任意箱子 + 一把锁（装上即成）→ 小锁柜」——这行是关键。它意味着：

- 木箱 / 铜箱 / 铁箱 = **容器**，出厂无锁
- 铁锁 / 铜锁 / 银锁 / 金锁 = **独立物品**（`items.csv:68-71`，价格 259 / 712 / 3440 / 29640）
- 玩家把锁**装到箱子**上，箱子才变成"上锁箱"（不能砸，要靠开锁工具）

**所以 `chests.csv` 里那一列 `lock` 放错了地方。** 它不是箱子的固有属性，而是**实例状态**（这只箱子装没装锁、装的什么锁）。

**结论 B：现有背包结构无法表达"这只箱子装了什么锁"。**

存档 `modules.inventory` 是 `{ "item_0065": 2 }` 这种**物品 → 数量**的计数表。它只能说"我有 2 个木箱"，**说不出**"这 2 个里 1 个装了铁锁、1 个没装"。

要做开锁，必须先把背包结构升级（每个箱子带实例状态，或用"木箱@铁锁"这类复合键）。**这是数据模型改造，不是加个配置值。**

**结论 C：开箱能开出什么，设计源从来没定义过。**

`对话讨论.txt:4247` 把这件事列为**待回答的问题**：

> 「随机与概率公示：**开箱**、沉船、每日活动出箱的随机在哪算，怎么做到可公示、可核对？」

全文搜索"出箱 / 箱内 / 开出"，**没有任何一条给出箱子内容物规则**。也就是说：

- `drops` 表 0 行不是"漏填"，是**本来就没有规则**
- 现在代码里硬编码 `item_0020`（木棍）当保底，是 10-27 某次裁决（D-27）临时定的，**不是设计源的规定**

### 1.3 所以 B-1 的正确处置是：**按设计源，v1.0 不做开锁**

设计源第 5117 行已经明确把"完整开锁矩阵"列为「**首版建议延期**」。这不是我替用户做的决定，是文件里写着的建议。

| 方案 | 内容 | 依据 | 代价 |
|---|---|---|---|
| **A（推荐）** | **v1.0 只做无锁开箱**：捞到箱子直接开（或砸），掉保底。开锁整套（装锁/升级工具/耐久/失效）延到 v1.1 | `对话讨论.txt:5117` 明确建议延期 | 少一个卖点；但少改一次背包结构 |
| B | v1.0 做简化开锁：只做"铁锁一档 + 普通工具"，命中次数由服务端判 | 无设计源支持（`5162` 说"必须提前定义"，而它没被定义） | 要改背包结构；数值只能自己编，违反 R-2 |
| C | v1.0 做完整 15 组矩阵 | 与 `5117` 直接冲突 | 工期不可控；背包结构 + 工具 + 耐久 + 数值全要新建 |

**采 A。** 于是 `06` 的 TASK-5006（开锁下沉服务端）应当**从 v1.0 移出**，改为 v1.1 种子。

> 这不是"我不做"，是"设计文件建议首版不做，且做下去需要先改背包结构"。任何相反的决定都必须先回答 `5162` 提的三个问题：每级工具能开哪些锁、消耗多少耐久、不同锁对应什么收益。

## 2. 顺带纠正 F-31 的判断（箱型校验仍然要做）

`chests.csv.item_id` 的 `ref: items.id` **只校验 id 存在**，不校验类型（`tools/gen/config.mjs:50-54`）。这一点不变，`06` 的 TASK-5005 仍然成立、仍然要做。

但新增一条：**`item_0068~0071`（四种锁）也是"合法物品"，如果玩家把锁当箱子传给 `chest.open`，现在的代码会接受它。** 箱型校验必须排除这四类。

## 3. 一个之前没人注意的模型问题（新增 F-38）

| 项 | 现状 | 设计源 |
|---|---|---|
| 箱子带锁 | `chests.csv.lock` 列（3 行全 `none`） | 箱子出厂无锁；锁是物品，装上才成"小锁柜" |
| 能否砸开 | `chests.csv.smashable` 列（3 行全 `true`） | 「上锁箱不能砸」——`smashable` 是**实例状态**，不是箱型属性 |

**F-38：`chests` 表把两个"实例属性"（`lock` / `smashable`）当成了"箱型属性"。**

后果：
- 现在全 `none` / 全 `true` 看不出问题（因为没有箱子装锁）
- 一旦支持装锁，同一个 `chest_wood` 会出现"能砸"和"不能砸"两种状态，配置表**无法表达**
- 正确落点：`lock` / `smashable` 属于**存档里的箱子实例**，不属于 `chests.csv`

**本规划不改这个模型**（改了要动迁移 + 存档结构 + 客户端），只登记。v1.0 按方案 A 不做开锁，所以这个模型问题暂时不暴露。

## 4. B-2 / B-3 的答案

### B-2（开箱奖励是否固定 `item_0020`）

**设计源未定义，因此维持现状（固定保底）是唯一合规章法。**

但必须做两件事：
1. `probability-disclosure.md` 如实写「当前无随机掉落，开箱固定获得木棍 ×1」
2. `06` 的 EVD 里写明「固定保底是临时口径，等 `drops` 有设计源再改」

### B-3（响应是否回 `ledgerIds`）

设计源要求「随机要可公示、可核对」（`4247` / `4995`）。**要核对就必须能追到账本**，所以长期应当回 `ledgerIds`。

但 v1.0 没有随机，核对需求弱。**建议：仍按方案 A（`{success, rewards[]}`），但在 `02` §4.2 把 B-3 标为"v1.1 随机掉落上线时必须改"**，避免以后忘。
