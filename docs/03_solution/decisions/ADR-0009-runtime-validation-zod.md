# ADR-0009 运行时校验采用 zod

## 背景

- 用户在第 4 步要求："运行时校验是否用 zod 要给出一个 ADR"。
- 现状：`packages/contracts` 只有 **TypeScript 类型**（编译期），**没有运行时校验**。
- `server/src/gateway/rpc.ts` 目前只校验"动作是否存在"与"幂等动作是否带 rid"，**不校验 payload 字段**。
- 后果：任何格式错误的请求都会直接进入 handler；一旦 handler 真实化，会产生不可预期的行为。
- 主包 ≤4MB 是硬约束，任何新增依赖都要计入包体。

## 选项

| 选项 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A. zod | 一份 schema 前后端共用，`safeParse` 产出统一错误 | 单一真源、错误文案一致、类型推导 | 增加包体；需要把现有 20 个 payload 改写成 schema |
| B. 手写守卫 | 每个动作写 `assertXxx(payload)` | 零依赖、包体最小 | 20 个动作 × 多字段 = 大量重复代码；易漂移（DRY 违背） |
| C. 不做运行时校验 | 只信 TypeScript | 零成本 | 边界失守；客户端可发任意 payload；违反"A. 信任边界"原则 |

## 决定

**采用 A（zod）**，但附三条硬条件：

1. **单一真源**：schema 与类型都由 `packages/contracts` 产出；类型用 `z.infer` 推导，**不再手写 interface**（避免两份漂移）。
2. **包体闸门**：S1 阶段实测"引入 zod 后主包增量"；若增量 > **30KB**（压缩后），回退到方案 B，并把结论回写本 ADR。
3. **服务端强制、客户端可选**：服务端对所有 `POST /v1/rpc` 的 `p` 做 `safeParse`，失败返回 `1001 BAD_PAYLOAD`；客户端只在 `save.push` 的 `snapshot` 上做校验（防写入脏数据），其余不校验以省 CPU。

## 后果

- 正面：错误码 1001 的触发条件变得确定；契约漂移在测试期即可发现；`TASK-1601`（契约测试自动生成）可以直接从 schema 生成用例。
- 负面：需要一次性把 20 个 payload 改写为 schema（估 1 人日，算进 S1）；包体增加（待实测）。
- 中立：`packages/contracts` 的对外 API 从"纯类型"变为"类型 + schema"，导入方式不变。

## 与既有决策的关系

- 不违反 ADR-0006（脚本进主包）：zod 是脚本，进主包，属于已知代价。
- 不违反 ADR-0005（只热更数据）：校验规则随代码走，不热更。

## 待验证

| 验证项 | 方法 | 通过条件 |
|---|---|---|
| 包体增量 | S1 构建后对比主包大小 | ≤30KB |
| 开发效率 | 改 20 个 payload 的实际耗时 | ≤1 人日 |
| 错误文案一致性 | 服务端与客户端对同一坏数据给出同码同文案 | 一致 |
