# ADR-0015：合规状态的数据模型

> **状态 `accepted`（D-45=B，2026-10-28 用户裁决）：v1.0 不提审，合规状态推迟到 v1.1。**
> 本 ADR 不建表、不改代码。**记录"为什么不在 v1.0 做"与"v1.1 再做时怎么选"**。

## 0. 决策摘要（D-45=B）

- **v1.0 不提审**（提审拆为独立里程碑），本版只做本地可玩版。
- 合规状态**保持现状桩**（`compliance.check` 恒 `minor=false`），**不建** `compliance_state` 表、不写迁移 0002。
- 真名/防沉迷是**微信强制要求**（国家规定），没有就过不了审；但 v1.0 既然不提审，**做了反而是假的**。
  假防沉迷一旦上线是**监管风险**，不是技术债 → 宁可推迟，不装作做了。

## 1. 事实基线（逐条可核）

| # | 事实 | 证据 |
|---|---|---|
| F-1 | `compliance.check` 是**恒真桩**：返回 `{verified:true, minor:false, ...}`，不读任何状态 | `server/src/modules/compliance/service.ts:13` |
| F-2 | 现状**无** `compliance_state` 表（`0001_init.sql` 13 张表无此表） | `server/db/migrations/0001_init.sql` |
| F-3 | `ERR.MINOR_TIME_LIMIT (2101)` 已在契约定义，但**零调用点** | `packages/contracts/src/common/errors.ts`；`04 §2 G-2` |
| F-4 | 微信小游戏**强制**实名 + 防沉迷（国家规定），无则不能提审 | `07_release/compliance/anti-addiction.md`（draft，未宣称实现） |
| F-5 | `mvp-scope.md:57` 曾把"实名、防沉迷、隐私协议"列入 v1.0 | 已被 D-45=B 修订（提审拆出） |

## 2. 选项分析（v1.1 再选，本版不选）

| 选项 | 内容 | 隐私面 | 防绕过 | 查询成本 | 代价/风险 |
|---|---|---|---|---|---|
| **A. 只存 `minor` 布尔** | `compliance_state(player_id, minor, last_seen_at)` | 低（非个人信息） | 中（客户端可传任意 minor） | 1 次读 | 无法区分"未实名"与"成年"；服务端必须自算 minor，不能信客户端 |
| **B. 存 `birth_year` + `minor`** | 加 `birth_year int` | **高**（生日年份属个人信息） | 高（服务端自算，不信任输入） | 1 次读 | 触碰个人信息合规，需隐私协议；建表 + 采集流程 |
| **C. 不存状态，每次向平台查** | 每次 `check` 调微信实名接口 | 中 | 高 | 每次网络往返 | 需平台实名接口权限（可能需资质 → 回备案问题）；离线不可用 |

## 3. 为什么本版选"推迟"而非 A/B/C

- 三选项都需要**真名采集流程**或**平台接口**，都回到"备案/资质"这个已定不做的前提。
- v1.0 不提审 ⇒ 无监管义务 ⇒ **任何合规状态都是"为未来预埋的假门"**（C-风险）。
- `compliance.check` 恒真桩不构成虚假陈述（`anti-addiction.md` 未宣称实现），已由 `01 §5` 记录。

## 4. 到期/回访条件

- **触发**：当"提审"被重新排入某版本（独立里程碑），或微信要求小游戏上线需实名（监管变化）。
- **回访动作**：重开本 ADR，从 §2 三选项中选一，然后才写迁移 `0002_compliance.sql` + 实现 `check()`。
- **在此之前**：禁止建 `compliance_state` 表、禁止写 0002、禁止把 `2101` 接到任何调用点（维持 F-3 现状）。
