### 🔴 问题 1：5 周 1 个人，当前范围至少需要 20 周

**【PM 判断】**

我来数一下一期清单里的系统：出钩核心、两片海域、五项深海玩法、百种物品制作、船体建设（含浮力/重量计算、多层堆叠）、7 岗位员工、电力系统、岛屿、塔防（9 兵种、迷宫寻路、离线结算、回放）、开锁系统、商人、保护卡、聊天、三榜（全服/区服/省份）、称号、每日活动、新手引导、三档画质。

**这是一个中型独立游戏的工作量，经验丰富的小团队（3–4人）做 6 个月才稳妥。单人 5 周，正常上班节奏下，代码量和联调时间根本不够。**

**📌 推荐方案（MVP 切割原则："好玩第一，完整第二"）**

砍到能体现核心乐趣的最小闭环：

| 保留（P0，必须上线） | 推后二期 |

| 出钩核心手感（弧形力度条、三色判定） | 深海野人 / 石油 / 潜水员 |

| 单一电力来源（太阳能） | 省份榜（IP 定省份的合规麻烦也同步推后）|

**备选 B：** 5 周只做可玩 Demo + 微信好友榜，再用 1 个月迭代后公测。

### 🔴 问题 2：个人主体能不能上这款游戏？聊天和排行榜有坑

**【PM 判断 + 合规核查】**

个人主体发布小游戏，只需《计算机软件著作权登记证书》和《游戏自审自查报告》即可，不需要版号。企业主体则必须有版号及配套文件。

不开通支付的免费游戏，个人开发者不需要版号；平台代扣个人所得税 20%。

**但有两个致命细节：**

**① 聊天（自由打字）功能让个人主体难以过审。**
微信对小游戏内的 UGC 文字（用户自己打的字）要求接入审核服务（违禁词过滤、实名关联等），这通常需要企业主体签署平台协议并接入内容安全 API。个人主体在技术上可以接，但责任主体不清晰，微信审核员大概率驳回。

**② 按 IP 判断省份 = 收集位置信息，需在隐私政策里单独说明。**
不应在非服务所必需或无合理应用场景下超范围收集用户个人信息。 IP 定省份属于"地区信息"，不算精确位置，合规风险中等，但必须在隐私政策中明示"我们通过您的 IP 地址判断所在省份用于显示省份排名"。

**📌 推荐方案：**
- 首版聊天用**预设快捷短语 + 表情**（15–20 条，如"好嗨哦！""来我这交易！"），完全不涉及 UGC，审核无压力，也不需要内容安全 API。
- 排行榜首版只做**微信好友榜**（平台自带，个人主体可用）+ 全服总榜（用云数据库存），省份榜推到有企业主体时再上。
- 将来想上聊天和省份榜，注册一个**个体工商户**或**一人有限公司**，成本 500–2000 元，解锁企业主体权限。

**备选：** 直接注册个体工商户（不是公司，手续更简单），依然个人经营，但拿到企业主体资格。

**不这么做的风险：** 自由聊天 + 个人主体 → 大概率被审核驳回，来回改 3–4 轮，浪费 3–4 周。

### 🔴 问题 3：断网可玩 vs 排行榜公平——这俩天生对立

**【DEV + GPM 联合分析】**

你的设计里，野人离线袭击、员工产出、潮汐都在离线期间发生，玩家重新联网后同步。但"赶海多捞哦"按打捞总价值排名，且物品可以本地生成——**只要本地数据可写，刷榜就停不住**。

**📌 推荐方案（分层离线策略）**

| 功能 | 哪里算 | 理由 |
|---|---|---|
| 员工产出（食物、资源）| 客户端算，联网时上报，服务器校验上限 | 低价值，容忍小误差 |
| 野人塔防结算 | 服务器算（离线时服务器跑，联网后推结果给客户端） | 防止本地作弊改结果 |
| 每日活动排名数据 | **全部服务器计算和存储**，不信任客户端上报的"总价值" | 排行榜核心防作弊点 |
| 潮汐倒计时 | 服务器时间为准，客户端只做展示 | 防止改本地时间刷内容 |

**关键防作弊原则：只要影响排名的数值，必须走服务端验证，不能信任客户端自己报的数字。**

**备选方案：** 每日活动单独做成"进服务器房间"模式，捞到的物品实时上报，不在本地累计。

**不这么做的风险：** 上线一周内必然出现刷榜大佬，正常玩家看到排行榜全是异常分，失去攀比动力，次日留存直接崩。

### 🔴 问题 4：微信 + 抖音双平台同步首发，开发成本翻 1.5 倍

**【DEV 判断】**

Cocos Creator 3.8.x 理论上可以一套代码构建微信和抖音两个包，但以下内容每个平台都要单独写：

| 差异点 | 微信 | 抖音 |
|---|---|---|
| 登录 | `wx.login` → code → openid | `tt.login` |
| 广告 SDK | 腾讯优量汇 | 穿山甲 |
| 分享 | `wx.shareAppMessage` | `tt.shareAppMessage`（参数不同）|
| 存储 | `wx.setStorage` | `tt.setStorage` |
| 排行榜 | 开放域（独立子项目）| 自建或云数据库 |
| 审核节奏 | 一般 3–7 天 | 一般 1–3 天 |
| 包体限制 | 主包 4MB，总包 20MB（最新扩至 30MB）| 主包 4MB，总包 约 20MB |

Cocos Creator 3.8.x 微信小游戏使用 Wasm 模式，抖音小游戏同时编译出 Wasm + AsmJS 两个版本，以兼容旧版本环境。

**📌 推荐方案：设计一个平台适配层（PlatformAdapter）**

```
PlatformAdapter（接口）
├── login()
├── shareGame()
├── showRewardAd()
├── getStorage() / setStorage()
└── postScore()

WechatAdapter（implements PlatformAdapter）
DouyinAdapter（implements PlatformAdapter）
NativeAdapter（以后上 APP 时用）
```

游戏逻辑只调用 `PlatformAdapter`，不直接写 `wx.xxx` 或 `tt.xxx`。切换平台只换 Adapter 实现，主逻辑零改动。

**备选：** 微信先上，抖音延后 2–4 周移植（审核排队时间差可以利用）。

**不这么做的风险：** 代码里到处写 `if platform === 'wechat'`，以后上 APP 时要全局搜改，极易漏改出 bug。

### 🔴 问题 5：后端选型——现在选错，以后搬家很痛

**【DEV 判断】**

你提了三个候选：微信云开发、抖音云、轻量云服务器自建。逐一分析：

| 方案 | 优点 | 缺点 | 月费估算 |
|---|---|---|---|
| 微信云开发 | 免运维、自带数据库/函数/存储、与微信登录天然打通 | 只能在微信用（抖音不能直接用）、并发上限低、贵 | 日活 1 万约 200–500 元 |
| 抖音云 | 类似微信云，适合纯抖音产品 | 同样锁定平台 | 类似 |
| 腾讯云 CloudBase / 阿里云轻量服务器 | 双平台均可用、可控、能接 APP | 要自己运维、写后端代码 | 日活 1 万约 100–300 元 |
| Serverless（云函数 + 云数据库，如腾讯云 SCF） | 按量付费、0 运维、扛突发流量（自动扩容） | 冷启动延迟（可预热解决） | 日活 1 万约 50–200 元 |

**📌 推荐方案：腾讯云 Serverless（SCF 云函数 + COS + TencentDB MySQL/MongoDB）**

理由：
1. **双平台通用**——微信和抖音都能调 HTTPS 接口，APP 以后也一样调；
2. **自动扩容**——突然爆量不用手动扩服务器；
3. **费用低**——日活 1 万以内月费约 100 元左右，日活 10 万约 800–2000 元；
4. **个人开发者能驾驭**——不需要自己管 Nginx、MySQL 主从等运维工作。

**服务器费用随规模变化：**

| 日活 | 推荐架构 | 月费估算 |
|---|---|---|
| <1 万 | Serverless 云函数 + 云数据库 | 50–200 元 |
| 1 万–10 万 | Serverless + Redis 缓存 + CDN | 500–2000 元 |
| >10 万 | 迁移到容器集群（腾讯云 TKE）| 5000 元起，需要专职运维 |

**备选 A：** 微信云开发（首版只上微信时最快，之后再迁移）。
**备选 B：** Railway / Supabase 等海外 Serverless（便宜，但数据在境外，合规有风险，**不推荐**）。

**不这么做的风险：** 选了微信云开发 → 抖音版本要再写一套 → 以后上 APP 还要第三套，白做了三遍。

### 🔴 问题 6：塔防系统的"离线结算 + 迷宫寻路"是开发黑洞

**【DEV 判断】**

迷宫式多入口寻路（A* 或 BFS，每波都要跑），服务器离线结算一场战斗，还要存一份够回放的战斗日志——这三件事加在一起，**保守估计需要 2–3 周纯开发时间**，而且极其容易出 bug（寻路死锁、结算时序错误、回放对不上）。

**📌 推荐方案：首版塔防极简化**

- **去掉迷宫**：改为固定路径（3条岔路选1条），玩家放塔/障碍，敌人沿路线走。实现 1 周搞定。
- **离线结算**：首版离线期间不发动袭击，玩家上线后收到一条"野人试探进攻，你的士兵守住了"的通知，扣一点资源（固定比例），不做真实战斗模拟。等系统稳定后再做真实结算。
- **回放**：首版不做，只显示"你损失了 xxx，守住了大门"的文字结算。

**备选：** 塔防整体推到二期，首版只做"出钩捞东西 + 建船 + 商人卖东西"的核心循环。

**不这么做的风险：** 塔防寻路和离线结算出 bug → 整个系统卡住 → 其他功能全部停工等 debug。

### 🟡 问题 7：经济系统没有闭环设计，会通胀或卡死

**【GPM 判断】**

金币从哪来？捞东西→卖给商人。金币往哪去？买装备/工具/赶海票。但：
- 没有"金币消耗天花板"——老玩家会无限囤积；
- "赶海票按装备定价，公式未定"——这句话是定时炸弹，公式决定游戏是否好玩；
- 浮力 ≥ 总重量的规则，如果数值不当，新手刚加两个房间就动弹不了，极易挫败卸载。

**📌 推荐方案：先做数值原型**

上线前必须用 Excel 模拟：
1. 玩家每小时能赚多少金币（各种途径加总）；
2. 建一个新房间要花多少金币 + 多少天材料；
3. 从 1 级玩到 20 级，每个档位的收入/支出曲线是否顺滑；
4. 赶海票价格 = 该场次用到的最贵钩子的市价 × 0.3 左右（让玩家赚票价的 2–3 倍才觉得值）。

**浮力/重量建议：** 初始木筏给 120% 浮力余量（轻松扩建 2–3 个房间），随等级提升材料密度才开始变紧张，不要一开始就卡玩家。

**不这么做的风险：** 上线后发现经济断层（资源太难）→ 留存差；或资源太容易 → 几天就玩完卸载。

### 🟡 问题 8：未成年人 20:00–21:00 每日活动的防沉迷矛盾

**【GPM + PM 判断】**

国家防沉迷规定：未成年人工作日每天限玩 1.5 小时，节假日 3 小时，22:00–8:00 禁止。20:00–21:00 虽在允许时段，但：
- 防沉迷系统接入需要实名认证（接国家未成年人游戏防沉迷实名认证系统）；
- 如果玩家是未成年人，当日剩余可玩时长不足 1 小时时，进入每日活动倒计时可能直接被踢出；
- 你的每日活动时间窗口只有 1 小时，未成年人当天如果已经玩了 30 分钟，剩余 60 分钟，活动内 3 分钟不受影响，但要注意总时长累计提醒。

**📌 推荐方案：**
- 接入微信/抖音平台自带的防沉迷 SDK（平台已集成，不用自己写）；
- 每日活动对未成年人正常开放，但时长累计计入防沉迷总额；
- 在每日活动入口处显示"剩余可玩时间 xx 分钟"提示，满足合规要求。

**不这么做的风险：** 没接防沉迷 → 微信 / 抖音审核直接驳回，这是硬性要求。

### 🟡 问题 9：微信好友排行榜 vs 全服排行榜——技术实现差异极大

**【DEV 判断】**

微信好友排行榜（开放域）是微信给的现成能力，只需要一个独立的"开放域小项目"，用 `wx.getFriendCloudStorage` 拉数据，开发相对简单。

全服排行榜 / 省份排行榜需要自建后端，存所有玩家的分数，做排序查询，还要防刷——这是完全不同的工程量。

**📌 推荐方案：**
- **首版只做微信好友榜**（1 周内搞定）；
- **全服榜**用后端数据库做，但首版只做"总资产榜"（简单 SUM，不做实时榜）；
- 省份榜推到有企业主体+服务器能力时再上。

**不这么做的风险：** 全服实时榜 + 省份榜一起做，数据库设计和防刷逻辑会消耗 1–2 周。

## 二、建议重新考虑的已定设定

> 以下几条技术上可行，但有比较严重的问题，建议在立项阶段重新讨论：

### ⚠️ 设定 1："微信 + 抖音同等优先，同步首发"

**问题：** 两个平台的登录、广告、审核流程、包体要求都不同，同步首发意味着开发、联调、提审要做两遍。对单人开发者来说，这会稀释核心循环的打磨时间。

**建议：** 先在微信首发，审核期间开始移植抖音版本，错峰上线，工期风险减半。

---

### ⚠️ 设定 2：首版就上省份排行榜（按 IP 判断省份）

**问题：** 
1. IP 定省份不准确（VPN、校园网、漫游），会导致排名争议；
2. 省份榜意味着全服排行榜，防刷要求极高；
3. 个人主体省份榜的合规风险（位置信息收集）。

**问题：** 真实时间潮汐意味着玩家必须在特定时间点上线才能体验潮汐内容。对于轻度碎片化玩家，这是强制绑定时间 → 增加流失。

| Cocos Creator 开发者 | 客户端玩法与联网竞争混在一起，系统耦合风险高     | 本地负责即时手感，服务器负责身份、竞争记录及需要防作弊的结果     |

本次评审的基本原则：不推翻已有设定，但把“已决定做什么”与“首版必须做完什么”分开。 以下会明确哪些建议可以直接执行，哪些重大冲突值得重新考虑。

## 二、①十大优先问题：必须先解决什么

以下按对项目成败的影响排序，不是给想法打分。

## 01

5 周内究竟交付什么

最高优先级

判断：完整一期不现实。建议将“5 周能玩、能测、能提交候审”作为阶段目标，将正式上线设为额外的合规与审核里程碑。

风险：如果所有功能都必须在第 5 周完成，最终容易出现功能都有入口、核心却不好玩、联网和存档还有漏洞的情况。

## 02

断网期间获得的东西，能否影响排行榜

判断：必须在开发前定下规则。客户端可以负责离线体验，但不能让客户端自己决定具有竞争价值的最终成绩。

风险：本地存档能被修改，玩家可伪造金币、装备、开箱结果和活动成绩。

## 03

浮力、重量和失败惩罚能不能让玩家接受

判断：游戏最有特色的建造规则，也可能是最大的挫败来源。超重应该先限制扩建或航行，而不是直接毁掉积累。

风险：玩家玩了数天，因为一个数值错误而损失整条船，极容易弃玩。

## 04

首钩是否真的好玩

判断：出钩是唯一必须首先做出真实手感的核心玩法。蓄力时间、力度窗口、目标移动、反馈和连续操作的节奏，决定玩家是否愿意继续玩。

风险：后期养成系统再丰富，也无法挽救一个每次操作都像重复小游戏的核心循环。

## 05

小游戏备案、广告资格和主体资质是否匹配

判断：手续必须从第 1 周并行启动，不能等游戏完成才研究。微信和抖音分别确认规则，不能把一个平台的准入结论直接套到另一个平台。

风险：开发完成后才发现不能按预期方式运营，整个排期失去意义。抖音官方明确区分小游戏备案与 ICP 核准流程。

## 06

浅海和深海是两个场景，还是两套游戏

判断：深海五项玩法必须共用制作、物品、航行、背包和成长系统，不能各做一套独立逻辑。

风险：为了五个玩法建立五套流程、界面和掉落规则，开发量与后续维护量都会迅速膨胀。

## 07

每天 20:00–21:00 的活动会不会把人挡在门外

判断：这会让游戏的某项主要奖励依赖特定时间。玩家下班晚、节假日安排不同、网络异常，都可能错过。

风险：活动本来是拉动留存的功能，反而成为流失原因。未成年人可游戏的时段还受额外限制。

## 08

金币、物品价值和打捞收益是否闭环

判断：必须列清金币从哪里来、消耗到哪里去，以及高级装备如何影响收益。稀有度不能仅由价格反推。

风险：无限出钩、重复回收、员工离线产出和活动奖励叠加，容易导致金币通胀、高级玩家碾压新玩家。

## 09

区服、排行榜和省份排名如何公平

判断：首版不应该急着把聊天和多人实时交互引入后端。先做低频、服务器校验的排行榜，省份选择优先使用玩家主动选择的方式。

风险：本地修改成绩、重复提交、修改系统时间和刷榜，会直接损害排名的可信度。

## 10

独立开发者的工作量是否有上限

判断：必须建立功能准入制度。新增系统只能替换现有同等规模的工作，或明确排到后续版本。

风险：不断加入玩法会让核心循环迟迟无法稳定，技术债务（为了赶工留下、以后不得不偿还的代码问题）逐周累积。

# 三、A｜公司项目经理视角

## A1. 目标与定位：先定义成功，而不是先定义功能数量

### 产品定位建议

把《我的筏》定位为：

一款以精准打捞为即时操作、木筏成长为长期目标、异步基地防守为策略挑战的轻度生存建造小游戏。

三项体验分别解决不同的问题：打捞解决“现在想玩一下”，建造解决“我还想再玩一天”，基地防守与排名解决“我为什么还要回来”。

竞品参考应当学习具体机制，而不是照搬完整游戏：

| 参考对象或类型              | 值得研究的机制         | 不应该直接照搬的东西       |
| -------------------- | --------------- | ---------------- |
| 《木筏求生》类生存建造游戏        | 漂浮物收集、资源制作、船体扩建 | 大规模世界、复杂生存模拟     |
| 《Coin Master》类轻度成长游戏 | 短周期收益、突发事件、成长反馈 | 过度依赖付费或攻击他人的经济设计 |
| 《海岛奇兵》类基地策略游戏        | 基地防守、布阵、战斗结果复盘  | 大规模实时战斗和复杂兵种克制   |
| 轻度收集与排行榜小游戏          | 短局、分数目标、可比较的成绩  | 把排行榜当成核心玩法本身     |

差异点不是“我们也能建造、打野人、开箱”，而是一条逐渐变大的木筏，既是玩家自己的家，也是可计算、可布置、可防守的成长成果。

### 成功指标建议

下面数字是首轮测试的建议验证目标，不是行业保证值。

| 阶段        | 建议目标                      | 判断标准                       |
| --------- | ------------------------- | -------------------------- |
| 第 1–2 周原型 | 核心钩子闭环可反复游玩               | 新玩家不看说明能理解长按、瞄准或蓄力、松手、获得物品 |
| 首轮可玩测试    | 新手关键流程完成率 ≥70%            | 玩家能从打捞走到第一次制作或扩建           |
| 小规模测试     | 次日留存率 ≥25%                | 第二天仍愿意打开游戏                 |
| 小规模测试     | 七日留存率 ≥8%                 | 一周后仍有可追求的成长目标              |
| 稳定性验收     | 无崩溃会话占比 ≥99.5%            | 低端机、断网、切后台等情况下基本可靠         |
| 正式运营观察    | 统计有效广告曝光、玩家人均广告次数、次日与七日留存 | 判断广告是否损伤留存，以及收入是否覆盖成本      |

不要把 DAU（每日活跃用户）当作单人游戏的首要成功标准。没有确定的流量来源，首月 DAU 1,000–10,000 只能作为目标情景，不是可信的基础预测。

建议首轮按 100–500 名真实测试用户做行为观察；随后再评估 1,000 DAU 目标是否合理。

### 广告收入怎样估算

使用同一套简单公式：

\\[ \text{月广告收入} = \text{DAU}\times \text{每日有效广告展示次数}\times \frac{\text{实际到手 eCPM}}{1000}\times30 \\]

其中 eCPM 是每千次有效广告展示对应的收入。以下用三个假设场景演示，不是微信或抖音的报价，也不是收入承诺。

| DAU     | 低情景：1 次/日、到手 ¥5 | 中情景：2.5 次/日、到手 ¥15 | 高情景：4 次/日、到手 ¥30 |
| ------- | --------------- | ------------------ | ---------------- |
| 1,000   | ¥150/月          | ¥1,125/月           | ¥3,600/月         |
| 10,000  | ¥1,500/月        | ¥11,250/月          | ¥36,000/月        |
| 100,000 | ¥15,000/月       | ¥112,500/月         | ¥360,000/月       |

这里的“有效展示次数”应以实际有效展示为准，不能把玩家点击广告按钮的次数当成已完成展示。具体收益还会受到广告填充、平台结算规则及用户实际观看情况影响。

\*\*结论：\*\*如果只有 1,000 DAU，纯激励视频通常很难支撑长期美术外包、运营和服务器投入。因此首版要先证明留存，再谈广告规模。

## A2. 范围与 A3. 进度：5 周应该怎样排

完整一期无法按当前清单可靠交付。建议采用以下 5 周里程碑。

第 1 周

原型与技术验证

做出钩子手感、漂浮物、圆形碰撞、物品掉落、基础界面；跑通目标安卓机，并分别编译微信、抖音测试包。并行启动主体与手续核验。

第 2 周

一条完整成长循环

完成打捞、物品库存、制作 3–5 种工具、扩建木筏、金币回收、升级反馈和最小新手引导。

第 3 周

船体规则与一次防守

完成浮力、重量、房间地块、最简员工生产、单个岛屿和可重复测试的塔防结算。

第 4 周

存档、联网与数据记录

完成本地存档、最小云端同步、服务器校验的排行榜样例、激励广告测试接口与关键埋点。这里不默认承诺开放聊天。

第 5 周

测试与候审版本

修复主流程问题，完成低端机测试、离线测试、数据迁移测试和提审自查。是否能正式上线，取决于当时的资质、备案、广告能力及平台审核。

这 5 周是可控的软件交付目标，不应把手续审批及平台实际审核时间强行塞进同一个确定日期。

### 关键路径

下列事情一旦延期，会直接阻塞后续工作：

1. 钩子手感没有确定，不能开始完整的新手教程与数值调优。
2. 物品、配方和存档的数据结构没有确定，制作、背包、商人会重复返工。
3. 浮力与重量规则没有定清楚，建造 UI、扩建限制和存档验证无法定稿。
4. 两个平台的登录、广告、文件存储和分包没有验证，无法判断双端交付成本。
5. 主体与准入条件没有明确，不能把“游戏开发完成”直接等同于“可以上线”。

### 新增需求如何控制

新增需求必须先回答三个问题：它是否让核心循环更好玩？它影响哪些已有模块？加入后要从当前计划中拿掉什么？

设置三个级别即可：P0 是上线必需；P1 是能显著提升体验但可推迟；P2 是扩展性或运营增强。每周只允许调整一次计划，不能因为想到一个新玩法就直接插入当前工作。

## A4. 资源与成本

### 美术、音效、测试

一个人开发不等于所有工作都必须亲手完成。建议：

- 核心场景、主界面布局、木筏和关键交互自行控制。
- 海水、木板、木箱、材料、工具尽量做统一风格的可复用图集。
- 音效采用少量合法授权素材，优先制作命中、拾取、建造、升级、失败等关键反馈。
- 不要在首版一次性生产百种独立的高质量图标；先用统一模板和少量基础素材跑通数据驱动的物品展示。
- 用真实设备与自动化测试脚本补充人工测试，不依赖“我自己的手机上能运行”。

### 服务器预算建议

下表仅用于规划支出，不是云厂商实时报价。假设游戏主要采用低频 HTTP 请求，不做实时多人对战，图片和资源通过 CDN 分发，玩家操作主要在本地执行。

| 规模            | 初期架构建议                       | 可预留月预算         |
| ------------- | ---------------------------- | -------------- |
| 原型 / 内测       | 单环境、托管云函数或小型云服务，少量数据库和日志     | ¥100–500       |
| 1,000 DAU 级   | 共享后端、托管数据库、基础备份、限流           | ¥100–800       |
| 10,000 DAU 级  | 服务无状态部署、数据库监控、排行榜缓存、日志采样     | ¥500–3,000     |
| 100,000 DAU 级 | 可扩缩 API、托管数据库扩容、缓存、CDN、风控和告警 | ¥3,000–20,000+ |

这些区间不是硬性成本上限。频繁写数据库、无限保留战斗日志、开放大规模聊天、给每次操作都发起请求，都可能让实际账单明显升高。

人力投入才是首版最大的隐性成本：一次错误的存档设计可能让几十个界面都要返工，所以数据结构和接口契约比过早追求复杂云架构更重要。

## A5. 主要风险及提前信号

| 风险    | 提前信号             | 推荐应对方案             | 不处理的风险        |
| ----- | ---------------- | ------------------ | ------------- |
| 工期超出  | 第 2 周还没有完整成长循环   | 冻结 P0 范围，取消新增玩法    | 5 周后仍无法稳定试玩   |
| 操作不好玩 | 测试者连续打捞几分钟就停下    | 先调力度判定、物品反馈和目标密度   | 后续系统无法补救核心体验  |
| 数值失衡  | 金币快速堆积、物品价值失去意义  | 建立材料与金币收支表，做自动模拟   | 通胀、刷榜、成长失去目标  |
| 存档作弊  | 客户端修改后排行榜出现异常跃升  | 排名由服务器校验，离线成绩单独标记  | 公平性崩溃、用户投诉    |
| 平台驳回  | 资质状态不清、隐私文案后补    | 第一周确认准入路径，建立提审检查表  | 完成开发却无法发布     |

| 服务器突增 | 数据库连接、接口延迟、写入数暴涨 | 限流、缓存、降级、告警、分级保留日志 | 爆量后服务不可用或费用失控 |

## A6. 合规与上线：不要把备案和版号混为一谈

这是需要认真处理的部分。以下是当前能从公开官方资料确认的规则及边界，不构成对某一主体的最终法律结论。

### 个人主体能不能做？

不能仅根据“个人开发者可以注册平台账号”，就推导出“个人主体一定能开通所需的全部运营能力”。

抖音开放平台的注册规范包含个人开发者路径，但主体注册通过不代表该游戏的类别、资质、广告变现能力和全部线上功能必然通过审核。

抖音开放平台

+1



本项目包含广告变现、在线存档、排行榜、聊天、用户举报处理和可能的未成年人使用场景。推荐在开发前核实主体资质。如果未来确定长期经营，建议优先考虑企业主体，因为它更便于统一管理知识产权、平台授权、广告收入、用户投诉和运营责任。但这是一项运营建议，不等于所有场景法律上都强制要求公司主体。

### 纯激励视频、没有内购，还需要版号吗？

需要将三个概念分开：

| 概念          | 说明                                |
| ----------- | --------------------------------- |
| 游戏出版审批 / 版号 | 国家层面的游戏出版审批事项                     |
| 小游戏备案       | 平台适用的小游戏备案流程，不应自动等同于版号            |
| ICP 核准或备案   | 涉及互联网信息服务及具体平台准入的另一类程序，也不应与游戏版号混淆 |

抖音开放平台的官方说明明确写明：小游戏都需要按照规定完成相应备案登记；已经取得国家新闻出版署等渠道的版号批文，可免于重复申请小游戏备案。没有版号的小游戏则需要先走小游戏备案流程；此外，小游戏上架前还需完成 ICP 核准。

国家新闻出版署公开的游戏出版审批材料要求中，也涉及游戏名称、运营机构和著作权证明等信息。

### 建议的时间线

第 1 周

主体与准入核验

明确个人或企业主体，检查游戏名称、知识产权材料、平台小游戏备案、ICP 核准及广告开通条件；需要办理的软件著作权等材料尽早申请。

第 2–3 周

开发和材料并行

完成可演示的游戏内容、软件名称与著作权材料的一致性检查、隐私政策、用户协议、权限用途说明、广告位设计和内容审核方案。

第 4–5 周

提审准备

对照微信与抖音实际后台完成相应资料、测试版本和自查项；对发现的问题及时修改，避免把提审只当成上传操作。

第 5 周后

审核、补材料与上线

预留多轮修改和补材料的时间，按实际审核结果确定发布时间。不承诺固定审批天数，也不在资质未确认时假定可以正式运营。

如果计划申请国家层面的游戏出版审批，另行评估所需材料、出版单位配合和更长周期；不能用 5 周软件开发排期来推算版号必然获批的时间。

### 防沉迷与 20:00 活动

国家新闻出版署关于防止未成年人沉迷网络游戏的通知明确规定，适用范围内的未成年人网络游戏服务时间限制为周五、周六、周日和法定节假日每日 20:00–21:00，同时要求落实实名注册与登录。

# 四、B｜小游戏产品经理视角

## B1. 核心循环设计

建议将游戏拆成三个相互连接的循环：

短循环：10 秒到 3 分钟

出钩 → 命中 → 获得材料/箱子 → 拾取与反馈

中循环：5 到 15 分钟

制作工具 → 扩建木筏 → 解锁功能 → 派遣员工/准备防守

长循环：数天到数周

解锁深海 → 占领岛屿 → 强化基地 → 塔防挑战 → 排名和称号

短循环必须在不进入背包、不阅读说明的情况下反复成立。中循环负责给玩家短期目标。长循环则应当给前两个循环提供有意义的奖励，而不是强迫玩家等待解锁。

### 玩家在不同阶段为什么觉得好玩

| 阶段      | 玩家应该获得的体验     | 首版需要实现的关键反馈            |
| ------- | ------------- | ---------------------- |
| 第 1 分钟  | 我会操作，而且很快捞到东西 | 首次命中有明确音效、震动和物品飞入背包的反馈 |
| 第 10 分钟 | 我能把原本的小木筏改得更好 | 第一次制作和扩建形成可见变化         |
| 第 1 天   | 我还有明确的下一目标    | 新图纸、员工岗位、材料目标或基地扩建     |
| 第 7 天   | 我的积累能带来不同结果   | 深海成长、岛屿防守配置、称号或周排名     |

如果第 1 天就只能重复打捞，而第 7 天仍只是数值增加，那么游戏容易失去新鲜感。首版应该至少建立“打捞—升级—新目标”这条可重复的成长循环。

## B2. 已定规则的冲突与修复建议

### 1. 出钩规则

\*\*判断：\*\*长按蓄力、约 1.2 秒往返的力度条、蓝绿红判定、无限次数，整体可以成立。但是“无擦钩”的具体含义必须转成明确规则。

\*\*推荐：\*\*将力度判定、命中窗口和物品运动拆成三份配置。分别记录蓄力时长、有效命中区、不同物体命中半径，以及失败的具体反馈。蓝绿红不能仅以颜色区分，需同时有符号或文字标记，照顾色觉差异。

\*\*备选：\*\*只保留成功与失败两档；或使用三档力度与三个明确结果。

\*\*不处理的风险：\*\*玩家会觉得判定不透明、操作没有可学习性，开发者也无法根据埋点定位问题。

### 2. 浮力与重量规则

建议统一使用整数游戏单位，避免浮点精度带来的误差。

设船体总承载能力为 \\(B\\)，船上全部物品、建筑、货物和员工的重量总和为 \\(W\\)。

\\[ R=\frac{W}{B} \\]

其中 \\(R\\) 是承载比例。

| 情况                    | 推荐结果                        |
| --------------------- | --------------------------- |
| \\(R \le 0.8\\)       | 正常航行和建造                     |
| \\(0.8 < R \le 1.0\\) | 出现超重警告，限制新增重物               |
| \\(R > 1.0\\)         | 阻止新增超重建筑、货物或扩层，提示需要先增加浮力或减重 |

以上 80% 是第一轮测试参数，不是最终数值。重点是给玩家保留可预期的缓冲空间。

\*\*推荐：\*\*超重不会直接导致整船沉没，也不销毁已积累资源；以扩建受限、航行受限或效率下降作为代价。玩家必须能够在界面中查看“浮力总量、重量总量、剩余承载能力、超重来源”。

\*\*备选：\*\*超重影响航速；或在连续超重时触发可恢复的事故事件。

\*\*不这么做的风险：\*\*浮力规则会从建造乐趣变成不透明的惩罚，尤其当几十个货物与员工被一起计算时。

### 3. 稀有度、价格和制作经济

目前“白绿蓝紫金按价格落档”存在循环定义问题：如果价格决定稀有度，而稀有度又用于决定价格与掉落，那么所有物品最终会互相依赖。

\*\*推荐：\*\*将稀有度和回收价格分开配置。稀有度用于定义掉落档次、获取难度和外观边框；回收价格则单独定义。制作成本也单独列出。

\*\*备选：\*\*以物品类别和用途决定稀有度；或为每种材料设置固定价格区间。

\*\*不处理的风险：\*\*同一物品的掉落、制作、回收和升级会形成自相矛盾的数值关系。

### 4. 每日活动赶海票

票价 200–2,000 金币，需要一个能落入数值表的计算公式。

推荐先定义每件参与装备的参考价 \\(P_i\\) 及其装备系数 \\(w_i\\)，再计算：

\\[ T=\operatorname{clamp} \left(200,\ 2000,\ \operatorname{round}\left(0.08\sum_i P_iw_i\right)\right) \\]

这里的 0.08 是首轮测试参数。参考价应来自统一的配置表，而不是玩家自己报出的价格；不同装备槽位可以使用不同系数。`clamp` 的意思是将票价限制在 200 到 2,000 之间。

\*\*推荐：\*\*先通过模拟 200、500、2,000、10,000 名玩家的装备分布与参赛结果，检查高低装备玩家的成本和收益，再确定系数。单次平均打捞价值至少需要覆盖合理的入场成本，否则活动会变成亏损惩罚。

\*\*备选：\*\*设置三档固定票价；或根据装备评分而非价格收票。

\*\*不处理的风险：\*\*高等级玩家以超强装备反复取得高分，低等级玩家虽然票价低，却几乎无法参与竞争。

需要注意：当前设定以“打捞总价值排名”。如果坚持这个规则，票价本身并不能消除高级装备玩家的优势。这个矛盾必须在排行榜规则中单独说明。

### 5. 每日活动、潮汐与离线袭击的时间冲突

\*\*判断：\*\*每 6 小时潮汐、每天 20:00 活动、离线自动袭击和员工离线产出，都是独立的时间机制。它们同时存在时，必须有唯一可靠的时间来源。

\*\*推荐：\*\*服务器时间是在线活动与竞争结果的时间依据。潮汐以固定起始时间和 6 小时周期计算，服务器与客户端都能算出当前潮汐阶段。离线玩家重新上线时只结算一次，不重复补算。

员工离线收益建议先设 8 小时上限。服务器记录离线开始时间、最后结算时间、可领取收益和结算版本。

\*\*备选：\*\*只允许结算固定离线收益；或将潮汐作为场景变化，而不改变材料产量。

\*\*不处理的风险：\*\*玩家修改手机时间、连续切换网络、重复登录，就可能重复领取收益或错过活动。

### 6. 岛屿失败与基地保护

判断：“进大门即失败”简单明确，但如果整局失败意味着损失全部材料、船体甚至数日积累，惩罚就过重。

\*\*推荐：\*\*保留防守失败的结果，但让损失可控：例如基地资源损失比例、短暂停产或局部建筑受损。玩家应能查看袭击报告和回放，并明确知道失败原因。

\*\*备选：\*\*只减少本次防守的收益；或保留建筑损坏但不删除稀有装备。

\*\*不处理的风险：\*\*由于无预警的离线袭击，玩家即使没有参与战斗，也会承担难以理解的损失。

### 7. 玩家账号、平台和区服

\*\*推荐：\*\*首版先支持平台身份登录、个人存档同步及一个服务器校验的排行榜。先不做跨平台实时聊天、跨区交易与复杂区服生态。

区服不应只是为了技术实现而提前建立。如果总用户量尚小，分区会稀释排行榜人数和社交活跃度。早期可以使用统一排行榜，达到实际负载或运营管理需要后，再划分分区。

跨平台账号也不能仅凭微信与抖音都能登录就自动合并。需要独立的内部玩家 ID、平台身份映射，以及经过用户同意的账号绑定机制。

### 8. 聊天系统

\*\*判断：\*\*自由打字聊天增加敏感内容审核、举报、拉黑、删除和运营责任，不只是增加一个聊天窗口。

\*\*推荐：\*\*首版使用快捷短语、有限表情以及举报入口。区服聊天、跨区聊天可以先验证使用需求；跨平台聊天后续再做。

\*\*备选：\*\*只提供个人公告和系统消息；或首版直接关闭玩家互发信息。

\*\*不处理的风险：\*\*一旦出现违规内容、骚扰或用户信息泄露，单人开发者很难及时处置。

# 五、C｜游戏 UI 设计师视角

## C1. 建议先定下的视觉规范

推荐先采用清爽的卡通 2D、暖木色与海洋蓝绿色搭配、轻量的 45° 俯视视角。

理由是木筏、资源、工具和箱子本身具有较明确的形状，可以用统一的图标风格表达。不需要为每件物品制作复杂的独立动画。

### 推荐色板

海洋蓝绿

浅海青色

木材色

深木色

重点操作

以上为风格提案，实际使用时仍需经过对比度和真机测试。

品质色建议统一为：

| 品质 | 建议色值      | 同时使用的辅助标志 |
| -- | --------- | --------- |
| 白  | `#E7E7E7` | 一颗小标识     |
| 绿  | `#5DBB75` | 双线框或圆点    |
| 蓝  | `#5BA8F5` | 双层图形      |
| 紫  | `#A77BED` | 星形或菱形     |
| 金  | `#E4B84E` | 皇冠或特殊角标   |

颜色不能成为唯一信息载体，尤其是出钩力度条。红、绿难以区分的玩家也必须能够通过形状、文字或图案理解结果。

### 竖屏主界面的信息排序

第一优先级：玩家正在操作什么、钩子当前状态、是否命中。

第二优先级：金币、等级经验、船体浮力与重量状态。

第三优先级：活动入口、潮汐倒计时、员工待领取收益。

建议底部将常用功能固定为四个入口：探索、建造、员工、背包。聊天和排行榜不应该占用钩子主要操作区域。

主屏常驻信息不宜超过玩家一眼可以扫过的范围。潮汐倒计时和活动信息可以用小图标及轻量提示呈现，不应在操作时不断弹窗。

### 关键交互的最低反馈要求

| 交互   | 至少需要的反馈               |
| ---- | --------------------- |
| 出钩   | 蓄力动画、力度窗口、抛物线、命中或落空反馈 |
| 拾取   | 物品飞入背包、数量变化、稀有物品强调    |
| 开箱   | 锁具变化、开锁失败提示、物品展示      |
| 建造   | 地块预览、合法/非法放置提示、建造完成动画 |
| 扩层   | 层级轮廓出现、浮力/重量同步变化      |
| 升级   | 经验条变化、解锁内容明确提示        |
| 防守结算 | 战斗摘要、资源损失、失败原因与回放入口   |

### 美术资源怎么准备

优先做资产清单，而不是先画大量美术。

首轮建议制作一张资源清单：海面、木筏地块、漂浮物、箱子、钩子与工具、三档基础塔防资源、主要 UI 图标、少量角色立绘或头像、动效与音效。大量普通物品可以复用基础轮廓，通过颜色和小标志区分。

字体可以选择许可明确、支持中文的免费商用字体，例如思源黑体，并随项目保存对应许可证及字体来源记录。外部图片、AI 生成图、音效也应保留来源和授权说明。

### C2. 首版必须形成的 UI 文件

1. 风格参考板：确定颜色、线条、阴影、材质和界面气质。
2. 低保真线框图：确定主界面、建造、背包、制作、员工、箱子、结算等页面。
3. UI 设计规范：字号、按钮尺寸、安全区、间距、弹窗、品质色和禁用状态。
4. 交互流程图：从点击入口到返回、取消、失败、成功和断网时如何处理。
5. 关键界面高保真稿：至少主界面、建造界面、背包/制作界面、塔防布局、结果结算。
6. 资源清单与命名规范：每类资源的尺寸、格式、数量、命名及图集规划。
7. 动效说明：明确每个动画的触发条件、持续时间和低配降级方式。
8. 宣传素材与版权台账：图标、截图、宣传图、素材来源、授权范围。

首版没有必要一次完成全部百种物品的独立高保真设计；应该让物品图标系统能够从配置表读取图标 ID，并逐步补齐素材。

Cocos Creator

+2

### 建议的代码分层

```

assets/
  game/
    core/                 # 与平台无关的核心规则

      raft/

      app/                 # 未来 APP 平台适配
```

核心游戏规则不要直接调用微信或抖音 API。例如，制作系统只调用 `InventoryService.addItem()`，它不应该知道底层是微信、抖音还是 APP。

平台适配层负责将各平台接口统一成项目内部格式。这样未来更换登录、广告、分享和存储方式时，修改范围才能控制在平台层及少数服务模块。

## D2. 存档与同步：本地快，服务器可信

这是本项目最重要的技术决策。

建议将数据分成三类：

| 数据类型      | 主要存放位置       | 处理规则                                         |
| --------- | ------------ | -------------------------------------------- |
| 即时操作状态    | 客户端内存        | 出钩、动画、碰撞、UI 状态，不需要每帧发给服务器                    |
| 单人体验进度    | 本地存档，可在联网时备份 | 允许离线继续玩，但不直接信任其中的竞技成绩                        |
| 竞技与线上关键数据 | 服务器为准        | 排行榜成绩、活动结果、账号映射、奖励领取记录以及需要防刷的关键物资变化必须经过服务器校验 |

本地存档建议使用带版本号的 JSON 或紧凑的结构化存档，并对大体积记录做归档。不建议把大量运行时对象完整序列化存储。

每次存档要包含数据版本、最后保存时间、关键资源数量、船体布局、员工状态等必要字段；迁移时采用逐版本迁移函数，例如 `v1 → v2 → v3`，不能仅靠字段缺失后临时补默认值。

### 如何兼顾断网与公平

推荐如下规则：

1. 断网时，玩家仍然可以打捞、制作和建造。
2. 离线过程中产生的单人体验进度，先在本地保存。
3. 重新联网时，提交待同步的操作摘要和存档版本，由服务器检查时间范围、数量变化、版本以及可验证的规则。
4. 无法验证的离线成绩不进入竞争排行榜，也不作为活动名次依据。
5. 排行榜和每日活动只接受服务器确认的参赛记录及结果。
6. 如果发生冲突，服务器的线上竞争数据优先；本地独有且合法的单人进度通过明确的合并规则处理，而不是直接覆盖整个存档。

\*\*不能做的事情：\*\*把本地保存的总金币、箱子内容或最终战斗胜负，直接同步为服务器可信结果。客户端文件加密也不能解决这个问题，因为玩家最终可以控制自己的客户端。

## D3. 塔防计算与回放

第一版塔防不必建立复杂物理战场。采用网格地图、预设入口和出口、离散单位移动即可。

建议的寻路流程：

- 将地图表示为格子网格。
- 玩家布置建筑或抬高地形时，验证每个入口到目标大门是否仍有可达路径。
- 使用 BFS（广度优先搜索，即从起点逐层搜索相邻可走格子）检查通路。
- 战斗过程按固定逻辑步进，而非根据设备每帧速度推进。
- 战斗由明确的布局、敌人波次、随机种子和算法版本共同决定。

如果随机掉落或战斗涉及排名，随机种子和结果必须由服务器确认；不能让客户端自己生成结果后直接提交排行榜。

### 回放怎样节省空间

不建议储存每一帧画面或完整动画。首版仅储存以下数据：

- 防守布局版本与地块数据；
- 进攻单位与波次配置；
- 随机种子；
- 战斗算法版本；
- 结果摘要和必要的事件记录。

观看回放时，用相同版本的逻辑重新模拟。算法变化后，旧回放应能够识别版本；不能保证重现时应保留结果摘要，而不是假装回放仍然准确。

## D4. 船体的数据结构

建议将船体视为一组可定位的地块，而不是把每个房间作为自由放置的复杂物理对象。

每个地块至少记录：

- 唯一 ID、X/Y 坐标、所属层；
- 地块类型、材料 ID、浮力值、重量值；
- 是否被占用、所属房间 ID；
- 建造状态及所需材料。

房间记录用途类型、覆盖地块、所需设施和用途限制。设施和货物另设对象记录，员工拥有岗位、当前状态和所在位置。

浮力与重量变化时，仅重新计算受影响对象所属的船体数据，并提供一套统一的服务接口查询剩余承载能力。不要让每个 UI 页面都自己累加数值，否则不同页面容易显示不同结果。

## D5. 数据与配置表

所有能够由策划调整的物品和数值，都应进入配置表，而不是散落在程序里。

首版至少包含：

| 配置表    | 关键字段                    |
| ------ | ----------------------- |
| 物品表    | ID、名称、图标、类型、重量、回收价、品质   |
| 配方表    | 配方 ID、材料需求、产物、制作时间、解锁条件 |
| 打捞表    | 区域、漂浮物、出现条件、可获取物品、掉落规则  |
| 船体材料表  | 浮力、重量、建造成本、可放置规则        |
| 员工表    | 岗位、薪酬或食物消耗、生产能力、解锁条件    |
| 防守单位表  | 生命、攻击、射程、攻速、成本、行为类型     |
| 岛屿与袭击表 | 地图、入口、敌人波次、结算规则         |
| 经济表    | 金币来源、金币消耗、商人价格、活动奖励上限   |
| 活动表    | 开启时间、参赛限制、票价参数、奖励和排名规则  |
| 成长表    | 等级经验、等级奖励、功能解锁条件        |

建议先用 Excel 管理数值，通过统一脚本导出 JSON，开发时只读取生成结果。表格应有字段校验，例如物品 ID 不能重复、配方材料必须存在、奖励数值不能为负、引用的图标必须能找到。

热更新不要作为首版核心功能。先做好资源分包与配置版本兼容，后续再处理线上配置发布、版本回滚与兼容性校验。

## D6. 后端选型：低运维比“自己搭得很灵活”更重要

推荐方案：采用同一套 HTTPS API 后端，结合托管数据库及可扩缩的函数或服务。 微信、抖音和未来 APP 都通过统一 API 访问游戏数据；各平台的登录信息在适配层换取内部玩家 ID。

对于小规模原型，可以选择任一适合的托管云开发方案，但必须首先验证它能被微信与抖音共同访问，并且能支持未来的 APP。不要为两个平台分别建立互不兼容的业务数据库。

如果选择腾讯云开发等服务，要先确认数据存储模型、调用额度、数据库连接、访问控制、自动扩缩和费用；不能仅因为与微信集成方便，就默认它天然适合所有平台。腾讯云开发存在独立的资源和计费项目，实际预算应根据调用量与资源配置计算。

### 服务器接口与数据表

首版不需要几十个微服务。推荐按业务模块组织一套后端应用：

- 账号与平台身份：`users`、`platform_identities`
- 玩家进度：`player_profile`、`save_snapshots`
- 经济与物资：`inventory`、`inventory_ledger`
- 船体与建造：`raft_tiles`、`raft_rooms`、`raft_objects`
- 员工与岛屿：`employees`、`islands`、`defense_layouts`
- 战斗记录：`attack_records`、`battle_summaries`
- 排行榜与活动：`leaderboard_entries`、`event_entries`、`event_results`
- 奖励与安全：`reward_claims`、`anti_cheat_events`
- 配置与版本：`config_versions`

以上是逻辑数据表，不代表每张表都必须独立成为一个数据库。

API 首版可控制在：

`POST /auth/exchange`：平台登录凭证交换为内部账号身份。

`GET /player/save`、`PUT /player/save`：获取、备份或更新存档快照。

`POST /player/sync`：提交待同步变化并处理冲突。

`GET /leaderboard`：查询排行榜。

`POST /event/enter`、`POST /event/finish`：报名活动与提交结算。

每一个涉及金币、奖励、物品数量的请求都应检查是否重复提交，并对数据变更记录流水。对于有奖励价值的操作，使用幂等 ID，避免同一个请求重复发放奖励。

### 不同规模怎样演进

首版使用统一 API，避免客户端直接访问数据库。低频的存档同步、排行查询和活动结算，已经足以覆盖 MVP。

当 DAU 增加时，按以下顺序扩容：

- 先减少不必要的 API 调用，避免每次出钩都访问后端。
- 对排行榜、配置与只读数据加缓存。
- 统计请求量、数据库慢查询、连接数、流量和日志体积。
- 后续再按真实负载增加缓存、分离服务或数据库读写压力。

服务无状态化（不同请求可由任一服务实例处理）能帮助扩容，但数据库仍然可能成为瓶颈。突然爆量时，应有明确的降级策略：先保护账号和存档，再限制聊天、排行榜刷新和非必要统计。

## D7. 防作弊需要做到什么程度

| 攻击方式      | 首版应采取的措施                         |
| --------- | -------------------------------- |
| 修改本地金币或背包 | 不把客户端最终资源值直接作为线上可信结果；关键变化由服务器校验  |
| 修改内存或加速游戏 | 对竞争活动采用服务器时间、次数限制、合理的行为上限与异常检测   |
| 抓包篡改接口    | HTTPS、服务端登录凭证验证、权限检查、字段范围检查、请求限流 |
| 重复领取奖励    | 幂等 ID、唯一记录、服务器结算状态               |
| 刷打捞总价值榜   | 服务器校验活动规则和可验证的拾取流水；离线成绩不参与排名     |
| 修改战斗结果    | 排名战斗采用固定版本规则、布局、波次与种子重演或服务器计算    |
| 重复注册刷活动   | 频率限制、异常账号识别、服务端活动次数与报名记录         |

不建议为了“防作弊”把每一次钩子动画、碰撞和移动都上传服务器。这样既增加成本，也不一定更安全。

应当区分“普通单人游玩”和“具有竞争价值的线上活动”，对后者采取严格校验，对前者允许更好的离线体验。

## D8. 性能、包体与埋点

### 包体

你提出微信主包约 4MB 的方向应当继续按主包优先设计。当前可查到的 Cocos 3.8 分包说明中，微信小游戏主包上限为 4MB、整体分包大小上限为 30MB；抖音小游戏则为整体包不超过 20MB、主包不超过 4MB、单个分包不超过 20MB。

平台限制和账号开通能力可能变化，提审前还应以对应开发者后台的实时要求为准。

主包建议仅放启动所需代码、最基础 UI、必要配置、登录与资源加载逻辑。深海、塔防、较大的资源集合等功能按需加载，不应让首次启动下载所有内容。

### 性能预算

建议以低端 Android 目标机为基准：

- 同屏漂浮物保持在设定的 20 个以内；
- 重复物体使用对象池，避免频繁创建和销毁；
- 优先复用图集，减少无意义的材质和绘制切换；
- 低配档默认关闭全屏波纹、复杂粒子与高频装饰动画；
- 测试长期运行、切后台恢复及大量物品出现时的内存变化；
- 首次加载、切场景、GC 峰值和真实帧率都要记录，而不仅是看平均帧率。

### 埋点、日志与崩溃收集

首版不需要收集所有动作，只需能回答三个问题：玩家为什么停下、哪里卡住、什么让他继续回来。

重点记录：

- 首钩耗时、打捞成功率、失败原因；
- 新手引导每一步的进入与退出；
- 第一次制作、第一次扩建、第一次升级；
- 背包满、超重提示、员工缺食、基地失败；
- D1 / D7 回访、游戏时长、活动参与；
- 广告入口点击、广告实际展示完成、奖励领取；
- 存档同步冲突、崩溃、请求失败与关键接口延迟。

对用户标识做必要的去标识化，日志只留必要字段，并在隐私政策里披露数据用途和保存规则。不要为了以后可能用到而无限收集。

# 七、B1、C2、D2｜立项阶段应该准备哪些文档

你列出的文档大部分都是有必要的。不过，单人开发不能把“文档齐全”理解成每个系统都要写几十页。每份文件应该解决一个实际问题，并能够被后续开发、测试或审核直接使用。

### 文档准备顺序

推荐按以下顺序执行：

1. \*\*先做决策文档：\*\*产品立项书、首版范围、核心循环图、目标指标、准入核验表。
2. \*\*再做规则文档：\*\*游戏设计总案、数值总表、经济系统、成长曲线、船体规则、失败与奖励规则。
3. \*\*再做实现文档：\*\*数据结构、技术架构、API 契约、存档同步、防作弊、分包方案。
4. \*\*再做用户体验文档：\*\*线框图、界面流程、交互规范、关键高保真图、美术资源清单。
5. \*\*最后补齐交付材料：\*\*埋点、测试、合规文案、发布检查表、回滚方案和运营监控表。

不是说合规要等到最后才开始。合规核验和资料办理应从第一周并行启动；这里的“最后”仅指完整的上线检查表与实际材料收口。

# 八、首版功能如何取舍

为了让 5 周计划有兑现的可能，我建议将首版拆成三层。

## 第一层：必须真正做完

| 模块 | 首版最低可用范围                 |
| -- | ------------------------ |
| 打捞 | 长按蓄力、松手出钩、命中判断、拾取反馈      |
| 物品 | 少量基础材料、工具、食物与箱子，结构支持后续扩展 |
| 制作 | 3–5 个关键配方、明确的材料消耗与产物     |
| 船体 | 地块扩建、浮力/重量显示、超重预警、存档恢复   |
| 成长 | 等级、经验、明确的下一个目标           |
| 经济 | 金币、商人回收、固定价格表、资源消耗闭环     |
| 体验 | 新手引导、主要界面、基础音效、低配画质      |
| 数据 | 本地存档、版本号、基础统计、错误记录       |
| 联网 | 最小账号映射、云端备份、服务器校验的测试排行榜  |

第一层决定这款游戏是不是成立。它必须完整、可重复游玩，不能用未来的功能入口替代真正可用的系统。

## 第二层：尽可能保留，但只实现最小版本

| 模块      | 保留方案                           |
| ------- | ------------------------------ |
| 深海      | 保留 20 级解锁设计，首版只做一个可重复的探索/打捞活动链 |
| 岛屿      | 一座可占领或解锁的测试岛                   |
| 塔防      | 一张固定地图、一组可配置敌人波次、离线结算逻辑        |
| 9 个兵种   | 如果必须保留数量，尽量共用底层行为和资源，用配置区分数值   |
| 员工      | 先完成能影响生产的少量岗位，其余岗位建立配置接口       |
| 每日活动    | 先验证一次短局、打捞价值、奖励结算和排名           |
| 激励视频    | 最多接入少量清晰自愿的奖励位置，并有广告无法播放时的兜底   |
| 排行榜     | 先做一个服务器校验的排行榜样例，不急着做多个复杂榜单     |
| 分包与平台适配 | 提前验证，不追求首版就覆盖所有未来平台功能          |

## 第三层：首版建议延期

- 完整的深海五项玩法和大量独立场景内容。
- 所有 7 类员工、复杂幸福感计算及完整自动化流水线。
- 太阳能、电鳗、石油发电全部并行的完整电力系统。
- 复杂研究树、研究室和完整多层房间扩展。
- 所有材质箱子与五类锁组合形成的完整开锁矩阵。
- 自由聊天、跨区聊天及跨平台社交。
- 多区服管理、跨区世界频道和复杂称号体系。
- PVP、交易、结盟、共管岛、埋宝挖宝与虚拟玩家。
- 完整的远洋内容。

这些功能仍然可以保留在游戏设计总案中，但首版不应因为“以后要支持”就将全部功能同时写成必须交付。拓展性意味着未来容易接入，而不是今天就把未来的全部功能做好。

# 九、需要重新考虑的已定设定

以下不是直接推翻原方案，而是认为其存在足以影响整个项目成败的问题。其余已定规则应当保留在游戏设计总案中，未经确认不要擅自改变。

| 已定设定                          | 评审判断                 | 推荐处理                         | 如果坚持原设定的风险                   |
| ----------------------------- | -------------------- | ---------------------------- | ---------------------------- |
| 一个人 5 周做完全部一期                 | 范围与工期明显不匹配           | 保留 5 周目标，但把可交付的 MVP 与完整一期区分开 | 开发完成度、稳定性和体验质量同时下降           |
| 微信与抖音同等优先、同时完成                | 单人开发需要承担双端调试、兼容和审核工作 | 共用核心代码，同时验证两端；正式发布可以分批       | 一个平台遇到问题，两个平台的交付都会被拖住        |
| 20:00–21:00 每天只进一次活动          | 活动机会过于集中             | 保留 20:00 的活动主题，评估增加补参与机制     | 玩家因为工作、网络或其他安排错过活动           |
| 无预警袭击且进门即失败                   | 对离线玩家过于严厉            | 保留突袭与失败结算，重新评估资源损失是否可恢复      | 玩家会把离线袭击视为对自己时间的惩罚           |
| 首版同时完成 9 兵种、7 类岗位、完整电力及完整深海内容 | 各系统的依赖关系和调试量过大       | 保留最终设计，但通过复用逻辑、缩短内容量分阶段实现    | 各系统只能勉强完成，交互和数值难以调好          |
| 通过 IP 直接确定玩家省份                | 有误判和隐私处理负担           | 优先让玩家主动选择省份                  | 玩家使用代理网络或网络地址发生变化时，排名归属可能不准确 |

另外，深海的 800×800 公里和远洋的 2,500×2,500 公里可以保留为世界设定，但首版没必要真的创建如此庞大的连续地图。用海域区域、航线和探索节点表达就能支持大部分玩法，而且更适合低端手机与单人开发。

## 目前还存在的几组明确冲突

第一组：无体力、无限出钩，与经济平衡。

无限出钩是好事，玩家不会被体力系统阻断核心操作。但是，每次打捞都必须定义时间成本、物品价值和回收收益，不能出现几乎没有成本的金币无限循环。

第二组：离线可玩，与离线防守排行。

离线体验必须开放，但离线模拟的成绩不能直接转成可信的线上竞争成绩。服务器需要有明确的校验边界。

第三组：箱子组合复杂度，与开锁工具数量。

3 类箱子 × 5 种锁已经有 15 种组合；开锁工具只有 3 级，每次还会损坏。必须提前定义每级工具能够开哪些锁、消耗多少耐久，以及不同锁对应的收益。否则玩家和开发者都不知道规则是否合理。

第四组：电力系统，与当前缺少明确的电力消耗端。

太阳能、电鳗、石油发电的出力比为 1:3:10，但如果机械设备没有明确的耗电需求，这个比例暂时没有游戏意义。应先确定设备耗电量、燃料消耗和停电后果，再做完整电力经济。

第五组：45°俯视的 2D 船体，与上下多层房间。

必须提前确定地块坐标、房间占用方式、层与层之间的视觉遮挡、设施放置范围及浮力计算单位。否则建造、碰撞、渲染和存档都可能各自采用不同的坐标规则。

# 十、上线验收标准与测试机型

建议将验收分成三组：产品体验、客户端质量、线上数据可信度。

| 验收项       | 推荐目标                                      |
| --------- | ----------------------------------------- |
| 首次进入与开始打捞 | 首屏关键操作在 5 秒左右完成，低端机或较差网络可放宽至 8 秒左右；采用真机测量 |
| 首钩体验      | 玩家可以不看长篇说明完成第一次出钩                         |
| 新手引导      | 第一次打捞、制作与扩建流程可完整跑通                        |
| 崩溃稳定性     | 稳定测试阶段无崩溃会话占比达到 99.5% 以上                  |
| 帧率        | 目标低端 Android 在典型场景维持 30 FPS；60 FPS 作为高配可选 |
| 本地存档      | 强制退出、切后台、重启、断网重连后，不出现明显的数据丢失或重复领取         |
| 排行榜       | 篡改本地分数、重复提交、重放领奖请求均不能直接产生可信成绩或重复奖励        |
| 版本升级      | 老存档能够完成迁移；迁移失败有备份和恢复策略                    |
| 广告        | 广告加载失败或用户不看广告时，游戏仍能继续                     |
| 隐私与账号     | 用户可以找到隐私政策、相关设置、账号退出或注销说明以及必要的投诉入口        |

这些指标是工程验收目标，仍需在真实设备上校准。尤其是加载时间，不应该只在开发者工具中测试。

| ----------------- | ------------------- |
| 4 GB 内存低端 Android | 帧率、内存、首次加载、资源释放     |
| 主流中档 Android      | 默认画质和日常长时间运行        |
| iPhone 刘海屏机型      | 安全区、按钮遮挡、触控布局       |

| 微信与抖音各自真机宿主       | 登录、广告、分享、存储、分包和返回逻辑 |

对第二份评审的取舍

### 一、学到的（采纳）
1. **5 周的目标是“能玩、能测、能提审”**，正式上线要看手续和审核，单独算一个里程碑。
2. **抖音要办两样手续（官方已核实）**：所有小游戏都要 ICP 核准；没有版号的还要先做小游戏备案。顺序是软著 → 基本信息审核 → 版本审核 → 小游戏备案 → ICP 核准 → 上架。这条我上一版漏了。
3. **安全域名白名单**：后端域名必须是 https 或 wss，两个平台后台都要配置。
4. **防重复领奖**：发金币、发奖励的请求都带唯一编号，服务器只认一次；物资每次增减都记一笔流水。
5. **存档不要整份覆盖**：合法的单人进度按规则合并；老存档一个版本一个版本地迁移，迁移前先备份。
6. **回放记上算法版本号**：规则改了以后，旧回放如果放不准，就只显示结果。改地形时实时检查每个入口到大门还有没有路。
7. **浮力提示分三档**：用到 80% 以下正常，80–100% 黄色警告，100% 禁止再建再装（就是你定的规则）。界面要能看到“最重的是哪几样”。
8. **赶海按总价值排名，票价只能拉平收益率，拉不平名次**，高装备玩家一定占优。规则不改，结算页可以加一行“同装备档位内排名”。
9. **出钩不限次数**，要把每钩的时间成本和平均收益算清楚，防止刷金币；离线收益每次上线只结算一次。
10. **深海 800×800 公里保留为设定**，实现上用海域区块加航线、节点，不做连续大地图。
11. **三个还没细化的冲突**：3 类箱子 × 5 种锁对上 3 级开锁工具，每级能开哪些、损耗多少还没定；电力 1:3:10 还缺各设备的耗电量；45° 俯视下多层船怎么排坐标、上层怎么遮挡。
12. **新功能进门先问三个问题**：让核心玩法更好玩吗？影响哪些模块？加了要拿掉什么？
13. **先找 100–500 个真实玩家测试**，日活不当首要指标；广告收入用公式按低、中、高三种假设各算一遍。
14. 首版不做线上热更新；数值表导出时自动检查有没有错。
15. **验收清单**：低端安卓稳定 30 帧、只在真机上测、测试机型表；每次提审前把全部清单跑一遍。
16. **UI**：底部 4 个常驻入口；品质除了颜色再加小角标；列出每个关键操作的最低反馈；图标从配置表读取。
17. **文档顺序**：先决策，再规则，再实现，再界面体验，最后交付材料。

1. **脚本放哪**：方案三把逻辑放进一个叫 `bundles/main` 的资源包。这个名字和 Cocos 自带的 main 包重名，而且 Cocos 官方建议不同资源包之间的脚本不要互相引用。→ **所有脚本统一放主包，资源包只放场景、图片、音频。**
2. **后端**：方案二是每个功能一个云函数，方案三用微信云开发。但微信云开发的云函数抖音调不到。→ **一个统一的后端服务，两个平台调同一个域名。**
3. **共享代码怎么进 Cocos**：方案二、三用路径映射引用工程外的代码，但 Cocos 只编译 assets 里的脚本。→ **用工具把共享代码复制进客户端，标为“只读”，有人手改就会报错。**
4. **数值表**：三份都是 Excel 转 JSON。→ **改用 CSV 作为源文件，好看出每次改了什么；导出前自动校验，只热更新数值，不热更新代码。**
5. **文档**：方案一、三按开发阶段分 10 层，方案二按主题分。→ **保留 10 层的骨架，合规、界面、模板这些主题放进对应的层里。**
6. **纠正的错误**：
   - 方案二把微信和抖音的包体上限混在一起说了；
   - 方案三的“每钩都由服务器复算”“离线袭击三限”和你定的规则冲突；
   - 方案二的“好友排行榜”和你定的省份榜不符；
   - 方案三说 profiles 文件夹不进版本库，这条和 Cocos 官方一致；但三份都漏了一条官方要求：.meta 文件必须跟资源一起提交，资源也只能在 Cocos 编辑器里移动或改名。

### 三、最终结构
- `client/`：Cocos 3.8 工程。脚本分 5 层：画面、流程与状态、规则副本、基础服务、平台适配。资源按玩法拆成 7 个分包（common、浅海、深海、岛、塔防、赶海、社交）。
- `server/`：一个后端服务，内部按模块划分。统一入口负责登录校验、限流、版本检查、防止重复提交。数据库建议用 PostgreSQL。
- `packages/`：`contracts` 是前后端接口的唯一定义；`game-core` 是前后端共用的规则，规定不能读系统时间、随机数必须带种子。
- `game-data/`：所有数值的唯一来源，目前 46 张表。
- `tools/`：生成、同步和自动检查工具，不依赖任何第三方包。
- `tests/`、`docs/`、`art-source/`（美术源文件和版权台账）。

### 四、增删改查怎么做
1. 先判断改的是哪一类：数值、规则、接口、存档、数据库、画面资源、整个模块。一次只做一类。
2. 每一类只有一个地方能改，其他地方自动生成。
3. 新增模块：先在模块登记表里登记，自动生成骨架，再由自动检查确认目录完整。
4. 删除模块：先断开所有引用，再删实现；存档字段只标记为废弃，不直接删。
5. 改接口：分两个版本完成，保证旧客户端还能用。
6. 查影响范围：`npm run impact 关键词`，会列出这个词牵涉到的所有模块和文件。
