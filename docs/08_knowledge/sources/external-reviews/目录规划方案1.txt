# 一、总体架构：一个项目仓库，三个主要边界

## 游戏客户端：Cocos Creator

场景、UI、出钩、背包、建造、员工、塔防、离线存档

## 统一数据契约与接口

请求与响应格式、数据类型、接口规则、错误码、配置版本

## 统一后端服务

账号、云存档、物品校验、经济、岛屿、防守、活动、排行榜

### 数据库与基础设施

持久化数据、数据库迁移、缓存、日志、备份、部署

微信、抖音、未来 APP 通过各自的平台适配层接入，不分别复制整套游戏业务。

这里我最推荐的结构是：

- 一个游戏客户端项目：使用 Cocos Creator，内部再按业务模块划分。
- 一个后端应用：早期采用模块化单体，即一个可以统一部署的后端，但内部各业务模块有清晰的边界。暂时不拆成很多微服务。
- 一套接口契约：明确前后端如何交换数据，生成或校验双方需要的类型。
- 一套统一文档体系：需求、架构、任务、测试及证据均放在规定位置。

不要一开始就把玩家、背包、建造、塔防拆成八九个独立服务器。单人开发时，目录边界应该清晰，部署边界却可以保持简单。

另一个重要原则是：目录可以多层，但真正的业务流程不能被人为切成过多小文件。 简单功能不需要为了显得规范而强制创建十几个空目录。

这些目录的职责必须明确：

| 层               | 负责什么               | 不应该负责什么         |
| --------------- | ------------------ | --------------- |
| `domain/`       | 浮力、重量、合法放置等规则      | 直接请求服务器、操作 UI   |
| `application/`  | 组织一次完整业务操作，决定调用顺序  | 直接依赖微信 API 或数据库 |
| `presentation/` | 界面显示、按钮事件、动效与状态反馈  | 自己计算完整经济规则      |
| `data/`         | 本地存档、API 请求、数据格式转换 | 决定游戏规则是否合法      |
| `types/`        | 只在本模块内使用的类型        | 存放所有全局类型的大杂烩    |

其他模块可以采用相同模式，但允许按实际复杂度裁剪。例如，一个只有简单设置的功能不必硬凑五层；一个涉及金币、制作、掉落和防作弊的模块则值得细分。

这里还要区分两个看似类似但实际不同的概念：

- Cocos 的 `Component` 是游戏引擎里的组件。
- 业务模块的 `domain/` 是业务规则层。

不要因为一个规则由 Cocos 组件触发，就把规则本身也全部写进组件脚本中。

这也是为什么我不建议采用“一个全局 `controllers/`、一个全局 `services/`、一个全局 `repositories/`”的结构。一个功能的核心代码分散在很多目录里，每次增删改查都容易漏改。

# 五、前后端数据交互：必须规定唯一的数据流

目录再整齐，如果页面随处调用 API、直接改存档、单独计算金币，最终仍然会混乱。

我建议把读数据与写数据分成两条清晰的路径。

## 5.1 读取数据

Cocos 界面 / 场景

业务模块的查询用例

API 客户端或本地存档仓储

统一数据契约与响应格式

后端查询用例 → 仓储 → 数据库

数据转换 → 客户端状态更新 → 界面刷新

读取数据时，可以根据数据类型使用本地缓存、服务器查询或两者结合。但页面组件不应该直接知道数据库表结构。

例如，建造界面只需要读取：

```
interface RaftSummary {
  raftId: string;
  buoyancy: number;
  totalWeight: number;
  remainingCapacity: number;
  canExpand: boolean;
}
```

不需要知道后端用了哪种数据库、表叫什么、ORM 如何组织。

## 5.2 修改数据

写操作需要更严格的规则：

```
用户点击按钮
    ↓
客户端检查基础输入，给出即时反馈
    ↓
调用明确的业务用例
    ↓
在线操作 → 提交业务命令给后端
离线操作 → 按允许的规则更新本地进度
    ↓
服务器执行权限、材料、数量和业务规则校验
    ↓
数据库事务提交成功
    ↓
返回权威结果
    ↓
客户端更新界面、存档及相关状态
```

数据库事务可以理解为：几个相互关联的数据变化要么一起成功，要么一起失败。

比如玩家制作一个铁钩，不能出现扣除了材料却没得到铁钩，或者重复发送请求导致获得两把铁钩的情况。

### 平台适配层究竟放在哪里？

不要在每个业务模块里直接写：

```
wx.login(...)
wx.request(...)
```

应由 `platform/wechat/` 实现项目定义的平台接口；业务层只依赖统一的登录、存储、广告与分享能力。抖音和 APP 需要时，分别实现对应适配层。

网络访问则集中在 `network/`，负责统一处理请求超时、身份凭证、错误转换和可安全重试的请求。平台 API 与游戏业务规则是两件不同的事情，不要将它们合并。

# 六、真正让增删改查高效的关键：按业务切片修改

你问的核心其实不是怎样存放文件，而是：

> 当我新增一个功能、修改一个字段或删除一个业务时，能否快速找到所有相关代码，又不破坏其他系统？

我的推荐是使用 业务模块内聚 + 明确的数据契约 + 可追溯的变更流程。

附件已经提出按业务边界组织代码；文档规范则要求正式需求形成方案、任务、验证和证据之间的追溯链。

## 6.1 不要把数据库 CRUD 直接暴露给游戏客户端

这是游戏项目与普通后台管理系统很重要的区别。

普通管理系统有时会采用通用的增删改查接口。但在《我的筏》中，金币、背包、开箱奖励、制作和塔防成绩，都受游戏规则限制。

例如，不推荐开放一个客户端可以随意调用的接口：

```
PUT /player/inventory
```

由客户端直接把完整背包提交给服务器，要求服务器照单全收。

更推荐设计明确的业务接口：

| 业务动作   | 推荐接口示例                            | 服务器必须检查的内容       |
| ------ | --------------------------------- | ---------------- |
| 查询背包   | `GET /v1/inventory`               | 账号权限、返回范围        |
| 制作物品   | `POST /v1/crafting/execute`       | 配方、材料、产物、重复请求    |
| 放置船体   | `POST /v1/raft/tiles`             | 地块位置、材料、重量、浮力    |
| 拆除船体   | `POST /v1/raft/tiles/{id}/remove` | 地块状态、拆除限制、返还规则   |
| 回收物品   | `POST /v1/economy/sell`           | 物品是否存在、回收价格、金币流水 |
| 领取活动奖励 | `POST /v1/activities/{id}/claim`  | 活动资格、结算结果、是否已领取  |

这些接口路径只是建议示例，并非已经确定的 API 契约。

这样设计的好处是：玩家无法通过修改一个通用更新请求，就任意增加金币或伪造奖励。

## 6.2 一项业务应该有一个明确的所有者

举例说：

- `inventory` 拥有背包物品与物品变更规则。
- `economy` 拥有金币流水、买卖价格和经济结算规则。
- `raft` 拥有船体布局、浮力和重量规则。
- `defense` 拥有战斗规则与结算过程。
- `leaderboard` 拥有排名数据的查询和排序方式。

其他模块不能私下修改这些模块的内部数据。

假如塔防获胜后需要奖励金币，应通过经济模块公开的应用接口，或者由明确的奖励结算流程协作，而不是直接访问经济模块的内部数据库实现。

这种分工也能避免双重事实来源：金币数量与金币流水分别有明确含义，不能让活动模块、战斗模块和玩家模块各自维护一份独立金币余额。

## 7.2 如果只是修改一个字段呢？

例如，将普通木板重量从 2 改为 1。

如果重量是策划配置项，应该优先修改权威数值表，而不是去搜索所有代码手工修改常量。

```
game-data/source/items.xlsx
          ↓
配置字段与引用校验
          ↓
导出配置
    ├── 客户端可用配置
    └── 服务端权威配置
          ↓
重量规则测试
          ↓
验证配置版本一致
          ↓
构建与发布
```

但是，如果重量从一个字段变成多个字段，例如从 `weight` 拆为 `baseWeight` 与 `loadedWeight`，这就不再只是数值调整。它可能影响配置表结构、船体计算、存档和数据迁移，需要执行更完整的变更评估。

\*\*推荐原则：\*\*数值变更走配置流程，业务规则变更走代码流程，持久化结构变更走数据库迁移流程。不要把三种事情混在一起做。

## 8.1 API 契约建议

推荐把 API 定义集中放在：

```

│   ├── common.schema.json
```

`openapi.yaml` 是接口的权威定义，描述接口路径、输入、输出、错误码和权限要求。客户端与服务端的类型定义可以由它生成，或者由自动化脚本校验。

这不意味着把服务端的业务规则共享给客户端。共享接口格式，不共享服务器的信任边界。 客户端知道“拆除地块需要传什么”，不代表它可以决定“拆除后到底应该返还多少资源”。

## 8.2 数据库变更

任何数据库字段新增、修改或删除，都应进入 `database/migrations/`。

例如：

```
database/migrations/
├── 0001_initial_schema
├── 0002_add_player_save_version
├── 0003_add_raft_tile_status
└── ...
```

文件或迁移名称可以随使用的迁移工具调整，但规则必须固定：

- 已经在某个环境执行过的历史迁移，不应直接改写来制造不同历史。
- 新的结构变化通过新的迁移表达。
- 删除数据或字段前，先检查旧版本兼容性、数据保留和恢复方式。
- 数据库迁移应在测试环境验证，生产变更应有备份与回滚或前向修复方案。

# 十、最关键的一步：建立自动化架构守卫

你附件中提出的 Architecture Guard（架构边界守卫）值得保留。它的作用是将“不要这样写”的约定变成自动检查，而不是每次都要求开发者或 AI 自觉遵守。

项目完整目录结构.txt



在这个项目里，建议分四层实施。

| 守卫        | 检查什么                    | 不通过时的处理          |
| --------- | ----------------------- | ---------------- |
| 第一层：格式与类型 | TypeScript 类型、代码格式、明显错误 | 修复后才能合并          |
| 第二层：目录与依赖 | 禁止模块内部越权访问、循环依赖、错误的层级依赖 | 拒绝构建或合并          |
| 第三层：数据契约  | 前后端接口类型、错误码、配置字段是否一致    | 重新生成代码并复测        |
| 第四层：完整行为  | 业务测试、数据库迁移、小游戏构建及关键流程   | 不允许以“代码已经写完”代替验证 |

对于 TypeScript 工程，可以按实际采用的工具评估 ESLint、dependency-cruiser 以及 CI 自动检查。Cocos Creator 自身的文件结构不一定能直接套用普通 Web 项目的所有规则，所以需要针对 `assets/scripts/`、后端 `src/modules/`、契约代码和生成目录分别配置。

建议先把以下几条规则落地：

1. `features/raft/` 不允许直接访问 `features/economy/` 的内部文件。
2. UI 组件不能直接调用数据库或微信平台接口。
3. 后端控制器不能跳过应用层直接操作仓储。
4. `generated/` 下的文件不能手动编辑。
5. 业务配置必须通过校验脚本。
6. 每个实际修改的功能必须能找到对应测试或明确的人工验证记录。
7. 任何涉及结构变化的任务，必须检查 `project-map.md`、`module-catalog.md` 是否需要更新。

# 十一、最后把“新增和修改功能”固定为一种工作流程

这里是整套体系能否长期有效的关键。不是每次都写一大堆文档，而是同一类变更遵循相同的处理步骤。

第 1 步：收录需求

新需求先进入 `docs/02_requirements/inbox/`，保留原始描述。确认后再归类到正式需求中。

第 2 步：分析影响范围

从 `module-catalog.md` 找到所属模块，检查 UI、业务规则、API、配置、数据库、存档、测试和平台适配是否受影响。

第 3 步：设计方案

简单改动可以直接形成任务；跨模块变更建立 Solution；关键技术决策建立 ADR。先明确改什么、不能改什么，再动代码。

第 4 步：按业务模块实施

先确定接口契约及数据变化，再修改对应客户端和后端模块。数据库变化单独通过迁移表达。

第 5 步：自动验证

运行类型检查、模块边界检查、契约校验、相关测试、存档迁移测试与目标平台构建。

| L：结构性修改 | 新增业务模块、改变存档格式、修改服务器权威数据规则 | 需求、方案、必要的 ADR、迁移与兼容设计、完整测试、发布及回滚方案 |

这可以避免两个极端：小修改也要造十几个文档；大修改只改了代码，却没有同步更新接口、存档、测试和需求。

# 十二、针对《我的筏》的实际落地顺序

不建议你一次性新建所有目录和所有文档。更合理的办法是先建立骨架，再让真实功能逐步填充。

1. \*\*先建立项目治理骨架：\*\*根目录、`AGENTS.md`、`README.md`、文档索引、项目地图、模块目录、依赖规则。
2. \*\*建立游戏客户端骨架：\*\*启动场景、平台适配、存档、网络、配置加载、一个完整的 `hook/` 业务模块。
3. \*\*建立后端骨架：\*\*应用启动、统一错误处理、身份接入接口、一个可用的玩家资料或存档接口。
4. \*\*打通一条完整纵向链路：\*\*首次打捞 → 获得物品 → 保存进度 → 重启恢复 → 联网备份 → 测试通过。
5. \*\*再扩展到背包和木筏：\*\*落实接口契约、库存规则、重量/浮力规则与数据库变更机制。
6. \*\*最后增加竞争系统：\*\*岛屿防守、排名、每日活动、防作弊，再针对微信和抖音分别完成平台适配。

为什么先打通一条完整的链路？因为它会验证目录是否真正好用。如果做一个简单的打捞功能就要跨十几个彼此不清楚的层，说明结构可能过度设计；如果金币、存档和 UI 全写在一个脚本里，又说明职责分离不足。

## 我最想强调的结论

你要建立的不是一棵“看起来完整”的目录树，而是一套明确归属、明确依赖、明确修改路径，并且能自动验证的工程体系。

对这款游戏而言，我最推荐的最终规则是：

- 按运行边界区分客户端和后端，按业务边界组织模块。
- 客户端以 Cocos Creator 的 `assets/` 为核心，不照搬 Web 项目的页面架构。
- 前后端以统一 API 契约协作，游戏关键结果由服务器校验。
- 配置、数据库结构、需求和 API 各自只有一个权威来源。
- 每次修改都能找到所属模块、相关需求、对应测试与完成证据。
- 目录规则和依赖方向要由自动化工具检查，不靠 AI 的记忆或提示词维持。

这样，当未来新增“钓鱼”“石油开采”“多层船体”“野人袭击”“每日赶海活动”时，都是在已有体系中增加业务能力，不需要不断推翻目录重新整理。
