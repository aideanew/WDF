# 评审结论

**四位评审一致意见：这个项目可以做，但“一人、5 周、原一期全部做完、微信和抖音正式上线”不能按现有范围立项。**

问题不是某个功能特别难，而是你把几类游戏的主要系统都装进了一期：打捞、制作、船体搭建、员工经营、资源生产、占岛、塔防，再加排行榜、聊天、定时活动、广告和双平台适配。

**推荐：5 周做出“双平台可运行的核心验证版”，先验证“出钩好玩、捡东西有期待、扩筏有满足感”。正式公开上线，还要以资质齐全、审核通过为前提。**

以下遵守两个原则：

- **不改你的核心设定。** 长按出钩、严格判定、无体力、真实时间潮汐、浮力规则等继续保留。
- **后移不等于取消。** 首版砍掉的系统留在路线图中；确实需要重新考虑的已定要求，单独列出，不暗中改掉。

另有一个重要说明：**平台资质、包体限制、广告接入条件会调整。以下是立项方案，不冒充对两个平台当前后台规则的实时核验；涉及正式上线的硬条件，必须在第一周逐项核实并留下记录。**

# ① 十大优先问题

## 1. 【公司项目经理】先分清“5 周交付什么”，否则项目必然失控

### 判断

原一期不现实。即使每个系统只做一个很粗的版本，最后的联调、存档迁移、双平台测试和审核整改，也会超过一人的承受范围。

还有一个经常被低估的问题：

> “代码写完”不等于“能上线”，更不等于“有人愿意持续玩”。

### 推荐：把交付分成三层

| 层级 | 要证明什么 | 本项目怎么安排 |
|---|---|---|
| 核心原型 | 出钩、收集、扩筏是否好玩 | 第一周完成 |
| 5 周验证版 | 一个完整小循环能稳定运行，双平台真机可玩 | 本次开发目标 |
| 正式运营版 | 资质、审核、数据、安全、运营都能支撑公开用户 | 验证版合格后推进 |

**双平台仍然同等优先，但不把“两边必定同一天审核通过”当成可承诺事项。**

### 推荐的 5 周里程碑

按 25 个工作日算，**只安排约 20 天明确开发任务，另外 5 天留给问题和整改**。

| 时间 | 主要工作 | 验收条件 |
|---|---|---|
| 第 1 周 | 出钩原型、漂浮物、收集反馈；两平台最小工程；资质核查 | 两边真机能进游戏、能出钩；找至少 10 人试玩 |
| 第 2 周 | 背包、基础配方、船体扩建、重量检查、本地存档 | 连续玩 15 分钟能形成“捞—做—扩”的循环 |
| 第 3 周 | 精简成长、20 级深海探索入口、引导、设置、平台登录及最小云存档 | 主流程闭环；此后原则上不再加新系统 |
| 第 4 周 | 低端机优化、断网/重连测试、广告测试、隐私和提审材料 | 完成测试清单；有资格提审则尽早首提 |
| 第 5 周 | 修复、回归、审核整改、上线准备 | 没有严重存档问题、死路和关键流程阻断 |

**审核建议预留至少两轮修改窗口，内部先按额外 1–2 周缓冲排，但这不是平台审核时长承诺。** 资质缺失、类目不符或玩法需整改，可能远不止这个时间。

### 关键路径

这几件事一旦卡住，后面会一起停：

1. **主体与上线资格**：没有资格，游戏做完也不能按原计划运营。
2. **出钩手感**：不好玩，后面几十个系统都是在放大问题。
3. **船体、背包、物品的基础数据结构**：后面制作、员工、塔防都要依赖。
4. **存档与升级迁移**：不能到了发布前才补。
5. **双平台登录、广告和资源加载实测**：不能只在编辑器里验证。

### 新想法怎么处理

建立一个简单的“需求停车场”：

- 写清楚：解决什么问题、预计增加多少开发和测试时间。
- **新增需求必须包含界面、素材、存档、双平台测试成本，不能只算写逻辑的时间。**
- 固定期限内，实行“加一个，换掉同等工作量的一个”。
- 第三周后，除阻断游玩、丢档、违规等严重问题，不再插入新系统。

### 备选方案

1. 保留原一期全部内容，把计划改为**数月开发、分批验证**。一人初步可按 4–8 个月评估，原型完成后再重估，不能把这个区间当交付保证。
2. 保留 5 周和原范围，引入有经验的程序、美术与测试协助；先做拆分和报价，不能认为“加人就能线性提速”。

### 不这么做的风险

最后大概率得到的是：系统很多，每个都浅；新手流程长；低端机卡；存档不稳；作者已经没有精力继续运营。

## 2. 【小游戏产品经理】核心卖点还不够聚焦，成功标准也没定义

### 判断

“喜欢生存、建造、塔防、收集的人”范围太大。

这些玩家对游戏的期待不一样：

- 生存玩家想管理风险。
- 建造玩家想自由设计。
- 塔防玩家想研究布阵。
- 碎片收集玩家想快速获得东西。

**首版应该先服务“喜欢轻收集和扩建、每次玩几分钟的人”，而不是同时满足四类重度需求。**

### 推荐：首版主卖点定为“出钩有手感，木筏越捞越大”

省份排名作为后续长期目标，不要拿它弥补前十分钟不好玩。

#### 玩家在各阶段应该获得什么

| 阶段 | 应该发生的事 | 为什么愿意继续 |
|---|---|---|
| 第 1 分钟 | 学会蓄力、命中、得到第一批材料 | “我会操作了，而且捞到了东西” |
| 第 10 分钟 | 完成一次工具制作和明显的船体扩建 | “这些材料真的让我的筏变大了” |
| 第 1 天 | 完成几个短目标，看到深海目标和新的物品期待 | “下一次回来还能解锁东西” |
| 第 7 天 | 筏的外观、收集和效率有明显变化 | “这是我自己的筏，不是开局那块木板” |

如果员工、岛屿还没做，就不要在首周宣传中承诺“第七天一定解锁员工基地”。

#### 出钩规则要补齐

目前“蓝绿红判定”没有定义清楚：颜色到底表示力度、距离，还是成功概率？

**推荐：力度条只决定落点，颜色帮助理解力度区间，不额外叠加隐藏的成功率。**

具体落地：

- 约 1.2 秒完成一次完整往返，按真实经过时间计算，不按帧数计算。
- 命中由钩子落点和目标有效区域严格判定。
- 没有吸附、没有擦边补偿，遵守已定规则。
- 教学通过“目标大、漂速慢、距离合适”降低难度，不偷偷放宽命中。
- 连钩只做震屏反馈，不额外堆复杂特效；提供减少震动效果的选项。

#### 第一轮指标建议

这些是**内部试验门槛，不是行业保证值**：

| 指标 | 初始目标 |
|---|---:|
| 新手流程完成率 | ≥70% |
| 教学第一钩命中率 | ≥85% |
| 普通新玩家首钩命中率 | 先争取 60%–80%，结合挫败反馈调整 |
| 次日留存 | 先争取 ≥25% |
| 七日留存 | 先争取 ≥8% |
| 单次有效游玩 | 3–8 分钟 |
| 每日有效游玩 | 初步观察 10–20 分钟，不强行拉长 |

留存要按平台、来源、版本分开看。先有几百到一千名真实新玩家，再判断；不能用几十个朋友试玩的数据认定产品成立。

### 竞品怎么参考

- **《Raft》及筏类生存作品**：参考“收集—扩建—探索”的循环，不照搬内容量。
- **轻量打捞、钓鱼、开箱小游戏**：参考前三分钟节奏和单手操作。
- **《保卫萝卜》等塔防作品**：参考路径、攻击范围和失败原因的可读性，不照搬关卡制作成本。

差异点可以是：

> **严格但易懂的出钩操作 + 看得见的积木式扩筏。**

不是“比别人多十个系统”。

### 备选方案

1. 把“岛屿迷宫塔防”定为主卖点，打捞只负责提供建设资源；但开发重心和工期都要重排。
2. 把产品定为偏放置经营，降低操作占比；这会明显改变当前体验方向，不建议首轮就做。

### 不这么做的风险

玩家不知道这游戏到底主打什么；作者也无法判断应该优先优化钩子、建造还是塔防，最后所有系统都在争时间。

## 3. 【游戏开发者＋产品经理】“断网可玩”与“公平排行榜”不能靠上传存档兼得

### 判断

这是本项目最大的技术与产品冲突。

**只要玩家能在自己的手机上自由产生资源，再把资源直接上传成排行榜成绩，就不能认为排行榜公平。**

以下办法都只能增加一点修改成本，不能从根上解决：

- 本地存档加密。
- 在客户端藏一个签名密钥。
- 检查文件有没有被修改。
- 上线、下线时各传一次总金币。

### 推荐：主线和竞争分开记账

这是两个“信任等级”，不一定需要两套界面。

| 内容 | 权威来源 | 是否能影响公平排行榜 |
|---|---|---|
| 主线打捞、建造、普通收集 | 本地为主，可云备份 | 不直接影响 |
| 主线离线产出 | 本地先显示预估，联网按规则处理 | 不直接变成竞争收益 |
| 活动入场资格、次数、竞争装备、成绩、奖励 | 服务器 | 可以 |
| 普通外观展示、个人成就 | 可以使用主线数据 | 明确不是强公平竞技依据 |

**首版推荐暂不上竞争榜；后续优先做“在线活动成绩榜”，不要先做“全服总财富榜”。**

#### 每日活动的关键补充

你已定装备从背包、仓库自选，可以保留，但需要增加：

- 比赛只认可服务器能核验来源的装备。
- 离线存档里凭空多出来的高级钩，不能提交一下就变成“合法比赛装备”。
- 实现上可以在原背包里给装备标注“可参赛”，不必再做一整套复杂背包。
- 但装备认证需要一条独立、可信的发放记录，不能根据客户端声称“我拥有它”自动认证。

这会带来一定产品复杂度，所以**不建议五周内硬上正式竞争活动**。

#### 防作弊分别怎么做

| 作弊方式 | 推荐防法 | 必须承认的边界 |
|---|---|---|
| 改本地存档 | 主线允许有限信任；竞争资产不从本地认账 | 无法保证离线主线绝对不被改 |
| 改内存、改客户端 | 服务器验证竞争资源和操作结果 | 客户端无法彻底自证清白 |
| 加速、改时间 | 服务器时间、操作频率上限、产出上限 | 本地时钟不能作为发奖依据 |
| 抓包改请求 | HTTPS、登录凭证、权限检查、参数校验 | HTTPS 本身不能阻止玩家改自己的请求 |
| 重复领广告/活动奖励 | 每次操作有唯一编号；服务器记录“已领取” | 不能只靠前端按钮变灰 |
| 刷活动价值榜 | 服务器生成场次、核验过程、计算价值 | 不能只收一个“本局 999999 分” |
| 脚本自动操作 | 频率和行为检测、异常复核 | 合法输入的自动化很难完全消灭 |

#### 活动随机与成绩

正式竞争场次建议：

1. 服务器生成场次编号、配置版本、装备快照。
2. 奖励随机结果由服务器产生并保存；不要把整局未来高价值掉落提前全部发给客户端。
3. 客户端上传必要操作，服务器检查次数、时间、目标合法性和资源消耗。
4. 服务器计算成绩、发放奖励，拒绝重复结算。
5. 排名奖励发放前复核异常前列账号。

**完整操作录像上传也不是万能防作弊。** 修改过的客户端可以伪造一份看起来正常的操作记录。

### 云存档怎么同步

不能做成“最后上传的覆盖一切”。

推荐：

- 本地存档带存档版本、云端修订号、设备信息、最后同步点。
- 同一设备正常重连，按修订号提交。
- 两台设备发生分叉时，先保留两份，再让玩家选一份主线继续。
- **不能把两份背包相加**，否则可以反复复制资源。
- 竞争资产始终从服务器读取，不参与本地存档选择。
- 重要操作后及进入后台前尽力保存；不能只指望“退出游戏”事件一定会执行。

### 备选方案

1. 做纯娱乐榜：允许展示主线财富，但明确不保证强公平，不发高价值排行奖励，并配置异常清榜规则。
2. 所有竞争相关成长都改成服务器记账，离线仅提供受限的预结算体验；公平性更好，但后端和规则复杂度明显增加。

### 不这么做的风险

上线后最早冲榜的可能不是正常玩家，而是修改存档的人。正常玩家一旦认为“榜全是假的”，省份攀比这个卖点就失效了。

## 4. 【公司项目经理】上线手续必须第一周启动，不能等游戏做完

### 判断

需要先拆开几个经常混用的概念：

- **主体认证**：谁在运营游戏。
- **软著**：软件著作权登记，不等于游戏运营许可。
- **备案**：网站、小程序、APP 等不同对象的备案要求，不能混成一件事。
- **版号**：游戏出版审批相关事项，不能用软著或 ICP 备案替代。
- **防沉迷、隐私、广告接入**：即使没有内购，也可能需要落实。

**“只做激励视频、没有内购”不能直接推出“不需要版号”。也不能把“平台能创建小游戏项目”理解为“已经具备公开运营资格”。**

### 推荐：正式公开运营按“需完成适用审批和资质”排期

在拿到明确、适用于本项目的规则依据前，**不要把无版号商业上线当作默认路径**。

第一周就完成一张核查表：

| 核查项 | 必须取得的结论 |
|---|---|
| 主体 | 个人还是企业；两平台对应类目是否支持 |
| 功能权限 | 排行榜、聊天、广告分别要求什么 |
| 游戏资质 | 版号、软著及其他材料具体适用情况 |
| 备案 | 小游戏/小程序备案、服务域名 ICP 备案，未来 APP 备案分别怎么做 |
| 防沉迷 | 接入哪个实名和时段限制方案，责任由谁承担 |
| 广告结算 | 主体资格、开通条件、结算账户和税务要求 |

保存平台规则链接、日期、后台截图和客服答复。涉及出版与运营许可的关键事项，找合规人士或有资质的合作方确认。

### 个人主体能不能做？

**不能笼统回答“个人一定不能做”，也不能保证“个人能做全部功能”。**

推荐答案是：

> **原型验证可以先做；按你计划的长期广告运营、聊天、榜单和后续商业拓展，推荐用企业主体规划。具体功能仍须逐平台核对。**

企业主体也不是万能通行证，出版审批及相关运营要求不会因为注册了公司就自动满足。

### 时间和开发怎么并行

以下仅作预算安排，不是办理时限承诺：

| 事项 | 何时开始 | 排期预留 |
|---|---|---|
| 主体方案、名称、账号归属 | 第 1 天 | 立即确认 |
| 企业设立、银行及结算准备 | 第一周 | 通常按数周统筹，地区和材料会影响 |
| 商用域名、服务器接入及备案 | 第一周 | 常按数周预留；受理后仍可能补件 |
| 小游戏/小程序备案 | 主体与平台资料就绪后尽早 | 以各平台和主管部门要求为准 |
| 软著 | 作品和材料达到申报条件即启动 | 普通办理按约 1–3 个月预留更稳妥 |
| 版号相关路径 | 立项时就咨询有资质的出版单位 | 通常按数月甚至更久考虑，预算可先看 6–12 个月以上 |
| 防沉迷、隐私、广告接入 | 第一周确认方案，开发中接入 | 不能留到最后三天 |
| 平台提审 | 核心功能和资质齐备后 | 留两轮以上整改窗口 |

不要相信“交钱买个版号就行”或不明渠道的“包过加急”。

### 隐私政策至少覆盖什么

- 平台账号标识、存档和登录信息。
- IP 地址及由此推断的省份。
- 设备、性能、错误日志。
- 广告组件实际收集的信息。
- 聊天内容、举报记录，如果以后开放聊天。
- 收集目的、保存期限、使用的第三方服务、联系方式。
- 删除账号、撤回授权、投诉和未成年人保护方式。

**按 IP 判断省份也属于个人信息处理。** 不应为了省份榜索取精确定位。

推荐：

- 服务端判断省份，按赛季固定或限制修改频率。
- 标明这是网络位置，不是户籍认证。
- 不公开完整 IP。
- 允许不进入地区展示，不因此阻断普通游玩。
- 对 VPN、出差等造成的误差，不承诺绝对准确。

### 未成年人和离线游戏

按现行网络游戏防沉迷框架，未成年人通常只能在周五、周六、周日及法定节假日规定的 **20:00–21:00** 时段获得游戏服务，具体以适用规定及接入要求为准。

你的活动时间与这个窗口重合，但要做到：

- 只在允许的日期和时段开放对应账号。
- 不用“离线模式”绕过时长和实名限制。
- 不把工作日错过活动变成未成年人的连续签到惩罚。
- 如断网状态无法可靠落实相应限制，就不能宣称所有账号均可无限离线玩。

### 备选方案

1. 五周只做合规允许范围内的开发、测试，不承诺商业公开运营日期。
2. 与有资质的发行或出版合作方协作；合同写清账号、软著、收入、数据和退出归属。

### 不这么做的风险

最坏的情况不是延迟几天，而是开发完成后才发现主体、广告、审批或备案路径不成立，整个上线计划重做。

## 5. 【小游戏产品经理＋开发者】规则之间还有“接不上”的地方，必须先写成数值和状态规则

### 判断

现在是“功能名称很多”，但不少关键规则还没闭环。

**推荐：先补下面这张规则表，再做界面和内容。以下都可以直接作为默认方案，不必逐条反问作者。**

| 没想清楚的地方 | 推荐方案 |
|---|---|
| 800×800 公里、2500×2500 公里怎么实现 | 作为世界设定和海图尺度；实际用海域节点、区块和事件生成，不创建同等比例的大地图 |
| 价格决定品阶，商人价格变化会不会导致物品变色 | 品阶按配置里的“基准价格”落档；交易折扣、活动加价不改变品阶 |
| 研究台与研究室关系 | 研究台是设施，研究室是房间用途；先能在第一层建研究室，再研究结构解锁上层，避免互相卡住 |
| 7 岗位与 9 兵种关系 | 岗位是员工职业，兵种是战斗模板；潜水员是士兵岗位分支，不额外变成第 8 岗位 |
| 幸福感四项是什么 | 饱食、休息、居住、安全；先简单平均，影响效率，不做随机叛逃、饿死等额外惩罚 |
| 发电 1:3:10 比的是什么 | 明确为标称出力；另列燃料、建造和维护成本，不能只看发电倍率 |
| 自动合成会不会把关键材料吃光 | 玩家设定目标数量、保留数量；缺料或超重时暂停，不能自动花光所有库存 |
| 箱体与锁怎么组合 | 三种箱体 × 六种锁状态，共 18 种组合；不支持的组合在表里明确禁用 |
| 三级工具怎么开四种锁 | 推荐一级开铁/铜锁，二级开银及以下，三级开金及以下；每次消耗一个，高级工具开低级锁给确认提示 |
| 上锁箱不能砸，会不会堵背包 | 保留“不能砸”；允许折价出售或丢弃，不强迫开锁 |
| 保护卡怎么重叠 | 同类延长，不同类型取最晚到期；是否受保护看袭击发生时，而不是玩家登录时 |

### 浮力与重量：推荐做成可恢复的建设限制，不做突然沉船

核心规则继续保持：

> 整船浮力 ≥ 整船总重量。

具体规则：

1. 每次建造、装货、招员工前，先计算变动后的总重量。
2. 不符合规则则不执行，并明确显示“还差多少浮力”。
3. 钩上来的战利品如果装不下，先放到船外的临时漂浮箱，不算船载货物。
4. 自动生产遇到容量不足就暂停，不能悄悄制造超重。
5. 无论如何保留卖货、整理、扩浮力和拆除的恢复途径。
6. 前期常规配方给足余量，建议按正常路线预留约 25%–35% 浮力空间，再用试玩校准。

**不要增加真实倾覆、水线、重心模拟。** 当前全船总浮力规则不需要这些成本。

### 船体数据怎么存

推荐用整数网格：

- 地块：`x、y、层、材料、容量、重量`
- 房间：`房间编号、占用格、用途、层`
- 设施：`设施编号、房间编号、位置、重量`
- 员工、货物另表计算重量
- 总浮力、总重量做增量更新，读档时全量重算校验

这样能接多层和二期扩展，不需要先做复杂物理。

### 金币经济：先让它服务成长，不用它证明玩家实力

来源：

- 商人回收。
- 探索和任务。
- 后续活动奖励。

去向：

- 工具和开锁工具。
- 配方研究、员工雇用。
- 建造、升级、活动门票等。

要注意：

- 出钩无限、生产可重复，长期金币一定会持续产生。
- 在没有玩家交易的单机主线里，这首先是“成长过快”的问题，不等于市场价格一定通胀。
- 不要靠无限加价格解决；应让新配方、新目标和合理消耗承接。
- **未核验的离线金币，二期不能直接变成玩家间交易货币。**

### 备选方案

1. 更简化：首版只做重量上限与建设预检，房间内部设施先减少种类。
2. 更复杂：加结构承重、局部浮力和真实昼夜供电，但必须后移并单独评估，不建议首版采用。

### 不这么做的风险

容易出现循环死锁、自动合成误消耗、背包堵死，以及“规则表面合理，实际三步之后玩不下去”。

## 6. 【产品经理＋开发者】每日活动、潮汐、离线袭击和员工产出，时间规则必须统一

### 判断

现在多个定时系统叠在一起，很容易从“碎片时间游戏”变成“每天按点上班”。

其中风险最大的不是潮汐，而是：

> **玩家离线时无预警失败，上线后发现永久成果被拆掉。**

你定了“离线自动结算、无预警、有回放”，但没定损失，这里必须先收住。

### 推荐：统一服务器时间，离线收益温和，离线失败轻惩罚

#### 时间基准

- 全服潮汐按固定基准时刻，每 6 小时切换，明确使用北京时间展示。
- 客户端在线时校准服务器时间。
- 断网主线可以显示预估状态，但本地改时间不能改变活动资格、保护期限和竞争奖励。
- 员工离线产出先设 **8 小时上限**，以后看留存调整。
- 离线袭击建议最多暂存一场待结算，不因玩家两天没上线连续清空资源。

#### 失败代价

推荐首轮测试：

- 核心船体、永久配方、已解锁进度不丢。
- 岛屿防守失败损失少量、明确可恢复的未保护资源，例如以非保护库存的 5% 为起点，并设置绝对上限。
- 不拆永久设施，不随机杀员工。
- 回放明确指出“哪里漏了”，而不是只显示失败。
- “无预警”保留，但规则说明、保护状态必须常驻可查。

#### 塔防实现

保留“多入口、一个大门、进入大门即失败”：

- 建造时检查每个入口至少有一条到门的通路，禁止完全堵死。
- 统一格子成本时，从大门反向做一次广度搜索，就能给所有敌人找路。
- 有不同通行成本再换成带成本的寻路，不要一开始上复杂算法。
- 地形“每格只能升高一次”要存永久状态，拆建筑不能重置次数。
- 9 兵种后续通过数据表配置生命、速度、攻击等，不额外做克制系统。

离线结算与回放：

- 战斗逻辑与画面分开。
- 固定模拟步长，例如每秒 10 次逻辑更新。
- 保存战斗初始快照、随机种子、配置版本和必要事件，不保存视频。
- 回放使用对应战斗版本；若只留当前配置，改数值后旧回放会对不上。
- 主线断网可本地模拟；若结果关联竞争资产或有价值奖励，联网后以服务器结算为准，未确认奖励不进入竞争账本。

### 每日“赶海多捞哦”

保留已定的时间、三分钟、单钩/多钩和自选装备，但补齐以下规则：

#### 1. “每天一次”怎么算

推荐：服务器成功创建场次才占用次数。

- 尚未开局的加载失败可重试。
- 已开局断线后重连继续同一场，不再领新场次。
- 大面积服务器故障统一补偿，不由客户端自己声称失败后重开。

#### 2. 价值怎么算

推荐统一使用活动配置里的基准回收价值：

- 按本场获得的物品计算。
- 箱子和箱内物品只能计一次。
- 消耗的自带开锁工具不算收益。
- 广告双倍奖励不翻倍榜单成绩。
- 发奖前允许有限时间的异常复核。

#### 3. 门票公式

推荐先按装备档分组实测，不直接拍一个“战力公式”。

可以采用：

\[
门票_i =
按50金币取整\left(
限制在200至2000之间\left[20\%\times(\mu_i-c_i)\right]
\right)
\]

其中：

- \(\mu_i\)：普通操作水平、该档装备三分钟预计获得的总价值。
- \(c_i\)：平均消耗的开锁工具等成本。

例如平均捞到 3000 金币价值，工具消耗 200，门票约为 550 金币。

前提：

- 新手档普通玩家不能长期“门票加工具成本高于收益”。
- 高级装备需要通过实测估算效率，不能只看商店价格。
- **门票只能调节收益，不能消除高级装备在总价值榜上的优势。**

因此推荐增加同装备档榜；若保留一个总榜，就明确它同时比较装备成长与操作，而不是纯技术公平赛。

#### 4. 未成年人怎么参与

只在允许日期的规定时段参与，不另外开违规补场。可以采用每周最好成绩或少量有效场次结算，降低“必须每天来”的压力。

### 备选方案

1. 五周版完全不做定时活动和离线袭击，只保留潮汐展示与单机探索。
2. 先做在线塔防挑战，等战斗逻辑与回放稳定后，再接离线袭击。

### 不这么做的风险

碎片玩家错过活动，回家还被洗劫；勤奋玩家刷时间漏洞；同一个断线场次重复领奖；回放与结算不同步，投诉会非常难处理。

## 7. 【开发者＋公司项目经理】后端先选“少运维”，别先为了爆款堆服务器

### 判断

“日活 1000–10000、峰值几百人”可以作为一个情景，但不是预测。

更重要的是：

> **同时打开游戏的人数，不等于服务器正在计算的游戏人数。**

你的主线主要在本地运行。如果不上实时 PVP，服务器压力主要来自登录、存档、活动结算、聊天和排行榜。

每日 20:00 集中活动，可能比全天日活更影响峰值。

### 推荐：一套统一托管后端，两个平台共用服务，账号和榜单先分开

推荐结构：

```text
微信 / 抖音客户端
        ↓ HTTPS
统一接口入口：登录校验、限流
        ↓
托管函数或可自动扩容的托管容器
        ↓
托管数据库 + 对象存储/CDN
```

- 不建议微信用一套完整业务、抖音再复制一套。
- 选厂商时确认：两个平台都能正常访问、域名能配置、数据库有备份、能设并发上限和费用告警。
- 初期不做实时聊天室，不做常驻长连接。
- 排行榜读取缓存快照，不要每次打开都全表排序。
- 缓存中间件先不强行单独部署，等真实压力需要再加。

### 三种候选方案怎么选

| 方案 | 优点 | 主要问题 | 建议 |
|---|---|---|---|
| 微信云开发/抖音云各自一套 | 对本平台接入方便 | 业务重复，数据和运维分裂 | 不作为默认 |
| 单一云上的统一托管后端 | 一套逻辑，少管机器，便于扩容 | 需验证双平台接入，关注按量计费 | **推荐** |
| 轻量云服务器自建 | 小流量时账单容易理解 | 备份、安全、扩容、故障都归作者 | 有运维经验才选 |

“最便宜”“最省运维”“无限扛量”不能同时无条件获得。对一人团队，**少一次夜间故障，往往比每月省几十元更值。**

### 规模和费用怎么估

先用一个透明假设：**每个日活每天 30 次轻量业务请求**，不含高频聊天、逐钩验证和大文件。

| 日活 | 每日请求 | 按全天平均的 10 倍估峰值 | 月度云资源预算参考 |
|---:|---:|---:|---:|
| 1000 | 3 万 | 约 3.5 次/秒 | 100–500 元 |
| 1 万 | 30 万 | 约 35 次/秒 | 500–3000 元 |
| 10 万 | 300 万 | 约 350 次/秒 | 3000–20000 元 |

**这是方案预算，不是厂商报价。** 数据库规格、请求体大小、日志、网络流量、内容审核、活动验证方式都会改变费用。

尤其注意：

- 30 次/人/天不适用于“每钩都发请求”的活动。
- 聊天轮询可能比云存档贵得多。
- 活动集中开场不能只按“全天平均的十倍”设计，要单独压测。

举例：假设 10% 日活在五分钟内入场，每人玩三分钟，日活 1 万时，仅该活动就可能有约 600 人同时在场；10 万日活时则约 6000 人。是否产生很大服务器压力，还取决于每人每秒发多少请求。

### 爆量时怎么变

- **1000 日活**：最小托管实例/函数、基础数据库、云存档与日志。
- **1 万日活**：加排行快照、请求限流、数据库索引、非关键日志批量写入。
- **10 万日活**：开场排队、活动结算队列、数据库容量和连接池专项压测；必要时按业务拆服务。
- 不要现在就分库分表；但要提前能关闭聊天、暂停新活动入场、降级排行刷新。
- 设置费用告警与资源扩容上限，防止异常流量把账单打穿。

### 最小接口与数据表

**五周版实现：**

- 登录凭证换取游戏会话。
- 拉取配置版本。
- 读取/提交云存档。
- 批量埋点、错误上报。

**后续竞争版增加：**

- 活动开局、操作、结算、成绩查询。
- 榜单查询与奖励领取。
- 广告奖励领取与防重复记录。
- 举报、封禁及人工复核接口。

核心数据：

- 用户与平台身份。
- 主线云存档及修订号。
- 竞争资产与资源变动流水。
- 活动场次、成绩、结算状态。
- 保护期限、结算时间。
- 配置版本、处罚和申诉记录。

### 区服、账号和聊天的默认方案

- 首版**不分区**，先按平台分环境。
- 同一后端不代表必须跨平台混榜。
- 微信与抖音账号默认不互认，不凭昵称或头像认成同一个人。
- 未来统一账号，需要单独的绑定和找回方案。
- 几千日活时过早开新区，会把聊天和榜单切得太空。
- 后续真要分区，按活跃、榜单拥挤程度和活动承载决定，不按“注册满多少人”机械开区。
- 聊天首版推荐不上；确需社交，先用快捷短语、表情、系统公告。自由打字要等审核、举报、禁言和客服流程一起具备。

### 备选方案

1. 最小轻量服务器自建，定期备份，接受需要自己值守和扩容。
2. 完全使用一家平台云能力做试验版，另一平台使用相同业务协议接入；必须先验证可达性和服务条款，不能默认互通。

### 不这么做的风险

要么过早花钱搭复杂设施；要么功能全部挤在一台无备份的小机器上，活动一开就崩，而且没人能腾出手修。

## 8. 【Cocos Creator 开发者】架构要隔离变化，但不要提前做二期全部底座

### 判断

“一期结构能扩展”是合理要求；“二期直接接上、以后 APP 只换接口”则过于乐观。

你可以大幅减少重写，但不能保证：

- PVP 不调整存档和权威来源。
- 交易不重做经济安全。
- APP 不补实名、隐私、支付、原生 SDK、商店审核和适配。

### 推荐：六层结构，纯规则不依赖引擎

```text
界面层
  ↓
玩法流程层：引导、建造模式、活动流程
  ↓
核心规则层：物品、配方、重量、成长、战斗计算
  ↓
数据层：配置、存档、同步队列
  ↓
服务层：账号、云存档、活动、日志
  ↓
平台适配层：微信 / 抖音 / 未来 APP
```

核心原则：

- 核心计算尽量写成普通 TypeScript，不依赖 Cocos 节点和动画。
- UI 只负责展示与发出操作，不直接修改背包和金币。
- 一次制作、建造、领资源按完整操作执行：检查条件、扣除、增加、保存，不能执行一半。
- 平台代码集中，业务里不要到处散落 `wx.xxx`、`tt.xxx`。

### 平台适配层至少统一这些能力

| 能力 | 统一给业务的接口 | 两平台差异由谁处理 |
|---|---|---|
| 登录 | 获取登录凭证 | 适配层＋服务端 |
| 激励广告 | 展示、完成、失败、关闭 | 适配层 |
| 分享 | 调起分享 | 适配层，不保证分享必定成功 |
| 存储 | 读写、容量失败处理 | 适配层 |
| 网络状态 | 当前网络、变化通知 | 适配层 |
| 安全区 | 刘海、胶囊、底部区域 | 适配层 |
| 隐私与权限 | 授权状态和必要提示 | 适配层 |
| 日志 | 统一事件与错误格式 | 适配层/服务层 |

广告奖励不能只信“客户端收到播放完成”。平台支持服务端校验就接；不支持时，不把该回调作为高价值竞争资产的唯一发放依据。

### Cocos 版本

**推荐以 Cocos Creator 3.8 系列中仍受维护、两平台导出验证通过的稳定补丁版作为候选。**

第一天做两个样包，验证：

- 登录、广告。
- 分包及远程资源。
- 后台恢复。
- 字体和音频。
- 最低档真机。

通过后锁版本，开发中不追新版本。补丁号、构建环境和插件版本写入项目记录。

### 包体与资源

你写的微信主包约 4MB，可以先作为内部保守预算，但**两个平台当前主包、单分包、总分包、远程资源限制要分别核对，不能套同一套数字。**

推荐内部目标：

- 主包争取 ≤3.5MB，留审核及平台组件余量。
- 首次只下载进入游戏和前几分钟必需内容。
- 深海、岛屿、塔防、活动、美术分别按场景拆分。
- 不用的资源及时释放。
- 进入活动前完成资源检查，不要门票扣了才发现资源没下载。
- 数值和资源更新遵守平台规则；**新增代码和玩法不能靠热更新绕过提审。**

### 存档

推荐结构包含：

```text
schemaVersion：存档格式版本
configVersion：配置版本
saveId / revision：存档身份及修订号
inventory：物品
boat：船体、房间、设施
campaign：海域、等级、主线进度
employees：员工，未开放时为空
settings：画质、音量、操作设置
```

- 存档目标先控制在几百 KB 内，保留主副两份和校验信息。
- 不把图片、完整配置表和大量日志塞进存档。
- 每次格式升级写迁移函数，保留旧档测试。
- 旧客户端遇到新格式，提示升级，不覆盖成空档。
- 换手机找回依赖已登录且同步成功的云存档；匿名本地档不能承诺一定找回。

### 数值配置

推荐流程：

> Excel/表格 → 导出工具校验 → JSON → 生成带版本的配置包。

校验至少包括：

- 编号不重复。
- 配方材料存在。
- 成本、概率、重量不为非法值。
- 概率合计正确。
- 解锁没有循环依赖。
- 旧配置能否回滚。

每一局竞争活动固定一个配置版本，不能玩家玩到一半换掉落价格。

### 性能目标

不要只写“2 核、4GB”，还要看 GPU、系统、存储和小游戏容器版本。

推荐低配目标：

- 稳定 30 帧，操作反馈不明显拖延。
- 正常打捞场景避免反复出现超过 100ms 的卡顿。
- 首次可操作时间：普通网络目标 P90 不超过 5 秒；低端和较差网络另设不超过 8 秒的初步目标，再据实调整。
- 运行侧可观察内存先争取控制在约 180–250MB 内，测量口径以平台工具为准。
- 漂浮物 20 个限制继续保留；敌人、投射物、UI 节点需另设预算。
- 漂浮物、敌人、弹道都用对象池。
- 背包长列表做按需显示，不一次建几百个格子。
- 图集按同时出现的场景组织，不追求“所有图片塞一张大图”。
- 不把整套大体积中文字体塞进主包。

### 二期现在只预留什么

预留：

- 稳定物品编号。
- 所有者编号。
- 数据版本。
- 资源变动流水。
- 服务端资产与本地主线资产的边界。
- 战斗计算与渲染分离。

不提前做：

- 联盟权限系统。
- 实时 PVP 同步框架。
- 玩家交易所。
- AI 虚拟玩家调度。
- 多人共管岛冲突处理。

### 备选方案

1. 更轻的单机架构，只抽出平台层和核心规则层；适合彻底无竞争的验证版。
2. 一开始全部服务端权威；未来交易和 PVP 更顺，但五周成本明显更高。

### 不这么做的风险

没有隔离会越做越难改；隔离过度又会花两周写“通用框架”，最后钩子都没调好。

## 9. 【游戏 UI 设计师】视觉方案必须围绕“一人能持续生产”，不是先追求精美

### 判断

百种物品、多层船体、俯视 45°、角色与塔防特效，会产生很大的素材量。

尤其是多层建筑，不只是“再画一层”，还涉及遮挡、点击和查看内部的问题。

### 推荐：统一的轻卡通 2D，固定视角，少量模块反复组合

- 采用轮廓清楚、细节少、偏明亮的卡通风。
- 不建议首版做复杂手绘，也不为了“低多边形”额外引入 3D 管线。
- 参考板只选 2–3 个方向：海水、木筏/建筑、物品/UI。
- 固定视角，不做旋转船体。
- 上层通过楼层切换、隐藏上层查看；不做全自动复杂透明遮挡系统。
- 设施尽量使用统一底座、尺寸和阴影。

### 色板建议

| 用途 | 建议色值 |
|---|---|
| 深海背景 | `#174B68` |
| 浅海主色 | `#3FADB5` |
| 木材 | `#B98652` |
| 主按钮 | `#F4B544` |
| 正文深色 | `#20313D` |
| 白品质 | `#E8EEF4` |
| 绿品质 | `#47BD79` |
| 蓝品质 | `#498FFD` |
| 紫品质 | `#B57AE8` |
| 金品质 | `#F5BD4F` |

颜色只是底稿，最后要在真实海面背景上检查对比度。

力度条不能只靠蓝绿红：

- 同时加刻度、图案或“近/中/远”等文字。
- 命中反馈不能只靠变色，还要有数量变化和明确音效。
- 品质同时用边框、星标或文字，照顾色弱玩家。

### 竖屏和单手布局

推荐以 750 宽设计稿建立规范，但使用可伸缩布局，不写死整张屏幕坐标。

- 顶部：等级、金币等低频查看信息。
- 中部：主要游戏画面。
- 底部拇指区：出钩、背包、建造。
- 潮汐和活动入口放次级位置，不压过主操作。
- 浮力/重量在建造、装货时突出；平时只在接近上限时提醒。
- 不要主界面同时摆满全部系统入口。
- 出钩和建造使用不同操作模式，避免长按时误触建筑。
- 避开平台胶囊、刘海和底部手势区域。
- 超长屏多显示海面，不把按钮拉远；平板限制主操作区宽度。

建议触控区不少于 **48 个逻辑像素**；在 750 宽、对应 375 逻辑像素的设计口径下约为 96 设计像素。不要把设计稿像素和真机逻辑像素混用。

正文建议 16 逻辑像素左右，辅助文字尽量不低于 14。

### 字体与素材来源

- 优先系统字体，或确认授权的思源黑体等免费商用字体。
- 素材商店负责大部分基础资源，作者统一颜色、描边、透视和阴影。
- AI 可以用于草图和方向试验；正式采用前核对工具条款与素材来源，不把“AI 生成”理解为没有版权风险。
- 音效用有商业授权的短音效包，至少包含出钩、入水、命中、失败、开箱、建造、升级。
- 建立版权表：来源、作者、订单、授权范围、是否需署名、修改记录。
- 宣传图和游戏内素材一样需要版权凭证。

### 动效优先级

必须做：

- 蓄力变化。
- 出钩轨迹。
- 命中/落空区别。
- 物品进入背包。
- 扣材料与建造完成。
- 升级反馈。

可以后做：

- 华丽开箱。
- 大量海浪。
- 多层建筑展开动画。
- 员工生活动作。
- 高品质全屏特效。

低配关闭装饰特效，但保留上述必要反馈。

### 备选方案

1. 像素风：适合已有完整同风格资源包的情况，不一定比卡通更省工。
2. 定制关键宣传图和少数核心建筑，其余采购素材；成本更高，但比全套定制现实。

### 不这么做的风险

素材风格拼贴、物品认不出、按钮太小、上层挡住下层，最终作者不断返工，却没有改善核心玩法。

## 10. 【项目经理＋产品经理】预算、验收和运营不能等上线后再想

### 判断

单人项目最容易漏掉三个成本：

1. 测试和处理玩家问题的时间。
2. 合规与素材版权成本。
3. 获客成本。

有游戏不等于自然就有 1000 日活，日活也不等于广告盈利。

### 推荐：先给验证预算，再决定扩大投入

#### 验证版现金预算

| 项目 | 节省型预算参考 |
|---|---:|
| 美术与音效素材 | 1000–6000 元 |
| 二手测试机、借机补充 | 1000–4000 元 |
| 测试期云资源、域名等 | 数百至约 1000 元 |
| 软著材料服务等 | 自办或单独询价，代办费不等于官方收费 |
| 可选关键 UI/宣传图外包 | 3000–15000 元 |
| 主体、记账、出版发行合作 | 单独预算，不混入开发素材费用 |

已有电脑并能借设备的情况下，**验证版先控制在约 3000–12000 元现金投入**可以作为预算目标；不含作者工资、大规模买量、版号相关合作与完整企业年度成本。

#### 广告收入怎么算

\[
每日广告收入 =
日活 \times 人均有效广告展示次数 \times eCPM \div 1000
\]

eCPM 就是每一千次有效展示带来的收入。

例如：

- 日活 1000。
- 每人每天平均 0.8 次有效展示。
- eCPM 假设 30 元。

则约为：

\[
1000 \times 0.8 \times 30 / 1000 = 24 元/天
\]

日活 1 万、人均 1.5 次、eCPM 40 元，约 600 元/天。

**这些是算式演示，不是收入预测。** 平台、用户地区、填充率、完成率、时段都会影响实际结果。

广告推荐放在：

- 非竞争主线的额外一份奖励。
- 可拒绝的便利收益。
- 明确不看也能继续的再尝试。

不要：

- 教学没完成就推广告。
- 广告增加正式比赛成绩。
- 反复弹窗诱导点击。
- 通过故意失败逼玩家“再来一次”。

#### 获客与更新

推荐先验证自然传播素材：

- 三秒能看懂的“钩中稀有物”。
- 小木板变大筏的前后对比。
- 后续有塔防时再做“奇葩迷宫守岛”。

微信分享不当作强制任务；抖音录屏、达人合作要准备平台能力和授权，不能把“能录屏”当成自然就会传播。

上线后：

- 前两周：优先修复、引导和手感，不急着塞活动。
- 稳定后：一至两周小调整，数周一个有验证价值的内容包。
- 不承诺单人团队每天新活动、每周大系统。

### 上线验收标准

| 类别 | 推荐门槛 |
|---|---|
| 严重问题 | 无稳定复现的丢档、资源重复领取、付出后无结果、主流程死路 |
| 稳定性 | 内测后争取无崩溃会话率 ≥99.5%，逐步向 99.8% 以上提升 |
| 存档 | 杀进程、断网、切后台、旧档升级、双设备冲突均通过 |
| 性能 | 低配实机达到前述 30 帧和加载目标 |
| 广告 | 完成、取消、无填充、网络失败、重复回调均测试 |
| 账号 | 登录过期、换号、注销、封禁流程有明确结果 |
| 合规 | 权限、隐私、未成年人限制、广告说明与实际行为一致 |
| 发布 | 能关闭活动入口、回滚配置，备份能实际恢复 |

留存是产品验证指标，不能当成提交审核前已经能保证的技术验收指标。

### 测试机型

建议覆盖约 6–8 台真实设备，能借就借：

- 至少两台不同芯片的低端安卓 4GB。
- 一至两台中端安卓。
- 一台当前主流较新安卓。
- 至少一台较旧、仍在支持范围内的 iPhone。
- 一台刘海/灵动岛设备。
- 长屏、小屏和平板尺寸补充测试。

同时测两平台不同客户端版本。编辑器和云测试不能完全替代真机。

### 主要风险的提前信号

| 风险 | 提前信号 | 应对 |
|---|---|---|
| 工期失控 | 第一周还没有真机出钩闭环 | 立即停新系统，回到核心 |
| 手感不好玩 | 玩家不断问怎么瞄、连续落空后不愿再试 | 调目标、漂速、反馈，不先加奖励掩盖 |
| 手续阻塞 | 第一周还不能列清双方所需材料 | 停止承诺公开日期，找专业核验 |
| 审核驳回 | 权限、文案、功能与提交说明不一致 | 用提审检查表逐项对齐 |
| 刷榜 | 新号短时间达到不可能资源或分数 | 隔离异常成绩，暂缓发奖，保留申诉 |
| 云费用异常 | 单日请求、流量突然远高于日活增长 | 限流、告警、关闭高频非核心功能 |
| 版权问题 | 素材来源只剩“网上找的” | 上线前替换，不等投诉 |
| 单人运维崩溃 | 每天处理问题占掉大部分开发时间 | 暂停更新新系统，补自动化与客服说明 |

### 备选方案

1. 只做小规模封闭测试，先不接广告，以最低成本验证玩法。
2. 找发行合作方负责获客、合规和部分运营，但先把分成、数据访问与账号归属谈清楚。

### 不这么做的风险

可能出现“有一万日活却没利润”“广告伤留存”“每天救火无暇更新”，甚至现金投入越来越大但没有一个明确的止损点。

## 单独列出：建议重新考虑的已定要求

这里不是直接替你改，而是明确指出哪些承诺不应原样保留。

### 1. “原一期全部功能，一人五周完成并正式上线”

**建议重新考虑。** 原因是范围、外部审批和测试时间同时不受控。

推荐保留五周做验证版；或保留原范围，调整工期。

### 2. “上线/下线时同步”

如果只是说这两个时点会同步，没问题；如果意味着**只有这两个时点同步**，建议重新考虑。

小游戏可能直接被杀掉，没有可靠的“下线通知”。应增加关键操作保存、节流同步、切后台保存和失败重试。

### 3. “二期直接接上，以后 APP 只换平台接口”

建议改为：

> 一期尽量避免重写核心规则；二期及 APP 仍单独做安全、权限、存档、经济和审核适配。

这不是架构做得不够好，而是交易、PVP、APP 本身就引入新责任。

# ② 需要作者拍板的问题清单

**只保留两项真正影响设计方向的问题。其他事项可以直接按上面的推荐执行。**

## Q1：五周到底交付哪一种版本？

**1.【推荐】五周交付双平台核心验证版。**  
按下方首版范围开发；正式公开时间由资质和审核决定。

**2. 保留原一期全部内容，改成数月开发。**  
五周作为第一阶段，不是完整上线期限；原型后重新估算总工期。

**3. 保留五周期限与完整范围，引入团队和外包。**  
先做资源与报价评估，再决定可承诺内容，不能直接保证原要求可达。

## Q2：排行榜希望做到哪一种公平程度？

**1.【推荐】主线离线自由玩，正式竞争只认服务器可核验数据。**  
不上主线总财富公平榜；活动、竞争装备、奖励单独记可信账。

**2. 接受娱乐榜。**  
可以展示主线数据，但不承诺强公平，不发高价值竞争奖励，并接受异常清榜和误判申诉成本。

**3. 希望主线财富、生产、装备全部能进入强公平竞争。**  
则必须把相关资源的发放与消耗更多交给服务器，明显增加成本，并重新审视离线体验。

**你可以直接回复：`Q1-1，Q2-1`。**

主体是否已有、资质是否齐全属于需要核实的事实，不是产品设计拍板题，不在这里让你猜。

# ③ 立项要补齐的文档清单和先后顺序

**原则：文档为减少返工服务，不为凑页数。五周项目不要先写一本几十页“游戏百科”。**

文档里的所有“以后再做”，都要明确标成后续，不与当前开发混在一起。

## 第一批：开工前至第 2 天，先决定能不能做

| 文档 | 必要性 | 写到什么程度 |
|---|---|---|
| 产品立项书 | 必须 | 1–2 页：目标玩家、主卖点、验证指标、预算、止损条件 |
| 首版范围及 P0/P1/P2 清单 | 必须 | 每项有验收条件、工时、依赖；P0 必做，P1 有余量再做，P2 后续 |
| 平台与合规核查表 | 必须，补充项 | 双平台主体、资质、备案、广告、防沉迷逐项记录依据与责任人 |
| 里程碑、风险与预算表 | 必须，补充项 | 按周计划，列关键路径、缓冲和现金上限 |
| 核心循环图 | 必须 | 一张图：出钩→材料→制作/扩筏→新目标→继续出钩 |

## 第二批：第一周，支撑原型和关键规则

### 产品设计文档

| 文档 | 必要性 | 推荐深度 |
|---|---|---|
| 游戏设计总案 | 必须，轻量 | 约 5–10 页概述；不重复抄所有细节 |
| 各系统设计文档 | 当前系统必须，后续延期 | 每个当前系统约 1–3 页，写输入、规则、状态、异常、验收 |
| 数值总表 | 必须 | 物品、配方、价格、重量、浮力、经验统一编号 |
| 经济系统设计 | 必须 | 一张来源/去向图，加主要产消表与重复收益检查 |
| 成长曲线 | 必须 | 至少验证前十分钟、首日、到 20 级的节奏；49 级上限保留 |
| 新手引导流程 | 必须 | 按步骤写触发、文案、完成条件、跳过/中断恢复 |
| 界面流程图 | 必须 | 画清当前所有页面、返回路径和打断关系 |
| 广告位设计 | 接广告前必须 | 触发、奖励、频率、拒绝、无广告、重复回调处理 |
| 活动设计 | 后续活动开发前必须 | 现在先记录已定规则、时间、计分、公平与断线边界，不写大量奖励内容 |
| 社交分享设计 | 轻量必要 | 分享场景与素材；聊天、联盟详细设计后移 |
| 埋点方案 | 必须 | 只先收能回答关键问题的事件，不做“什么都埋” |

### UI 与美术文档

| 文档 | 必要性 | 推荐深度 |
|---|---|---|
| 风格参考板 | 必须 | 一页，包含海面、船体、物品、UI，标明来源 |
| UI 设计规范 | 必须 | 色值、字体、触控尺寸、按钮、弹窗、品质表现、错误提示 |
| 全部界面及弹窗清单 | 必须 | 当前版列全；后续仅列名称 |
| 交互流程图 | 必须 | 可与产品界面流程图合并，避免两份不一致 |
| 低保真线框图 | 必须 | 先画主界面、背包、制作、建造、设置 |
| 关键界面高保真图 | 必须，但只做关键页 | 主界面＋一个通用弹窗＋一个列表页即可建立模板 |
| 美术资源清单 | 必须 | 名称、尺寸、数量、优先级、来源、负责人 |
| 图集/切图命名规范 | 必须 | 一页规则，前缀、目录、尺寸、用途 |
| 动效说明 | 必须，轻量 | 必要反馈的时间、位移、缩放和低配表现 |
| 素材版权记录 | 必须 | 每个来源都有凭证，不能发布前再补找 |

## 第三批：第二周前，防止技术返工

| 文档 | 必要性 | 推荐深度 |
|---|---|---|
| 技术方案与模块划分 | 必须 | 一张架构图，明确哪些逻辑不依赖 Cocos |
| 平台适配接口表 | 必须 | 登录、广告、分享、存储、网络、安全区、隐私 |
| 数据结构设计 | 必须 | 当前存档、物品、船体；岛和员工先定义稳定编号与基本边界 |
| 配置表规范 | 必须 | 字段、单位、默认值、校验、导出方式、版本 |
| 存档与同步协议 | 必须，建议单列 | 保存时机、冲突、迁移、损坏恢复、换机、账号切换 |
| 服务器接口文档 | 有后端就必须 | 请求、返回、错误码、权限、重复请求如何处理 |
| 防作弊与信任边界 | 必须 | 一页先讲清“哪些信客户端、哪些只信服务器” |
| 随机与概率配置说明 | 有随机就必须，补充项 | 奖励池、概率、次数依赖、版本；公示与实际一致 |
| 资源目录与命名规范 | 必须 | 可与美术规范合并 |
| 分包方案 | 必须 | 两平台分别列预算、依赖、下载和失败处理 |
| 埋点、错误及日志规范 | 必须 | 事件编号、字段、隐私过滤、上报频率、保留策略 |

**随机记录至少能够核对：场次/开箱编号、配置版本、奖励池、消耗、结果。** 概率规则如果受保底或条件影响，公示不能只写一个误导性的单次概率。

## 第四批：第三至五周，支撑测试和发布

| 文档 | 必要性 | 推荐深度 |
|---|---|---|
| 测试计划与机型表 | 必须 | 主流程、异常、低端性能、网络、存档、双平台 |

| 防沉迷提示和限制说明 | 必须 | 与实际接入方案一致 |
| 平台宣传素材规格 | 必须 | 图标、截图、简介、宣传图逐平台建表 |
| 版本发布流程 | 必须 | 版本号、构建记录、测试、提交、灰度、配置回滚 |
