# 一、三条硬约束决定了目录长什么样

| 约束 | 事实 | 对目录的影响 |
|---|---|---|
| **Cocos 只能编译 `assets/` 下的脚本** | 引擎不会编译工程根以外任何 `.ts` | 所有客户端代码（含"纯逻辑"）必须在 `client/assets/` 里，不能像 Web 那样拆 `src/lib` |
| **微信主包 4MB / 总包 20MB**（部分类目已放宽至 30MB，以官方为准） | 引擎裁剪后约 1.5–2MB，留给首屏资源极小 | 目录必须按**发布边界**（分包）切，不能只按职责切 |
| **微信云函数每个目录独立依赖** | 上传时只打包该函数目录，不含仓库其他代码 | 后端必须"一份源码 + 构建时注入到各函数目录"，否则代码会复制 N 份 |

由此得出本项目的第一原则，与附件的"按运行边界分应用"同源：

> **按发布边界分包，按业务边界分模块，按职责分层，按真源抽共享，按生命周期隔离生成物。**

## 3.1 双维度组织：Bundle（发布边界）× Layer（职责边界）

这是本方案最核心的一个设计。单维度必然二选一：
- 只按职责分层 → 分包时你得挨个文件判断"这个进主包还是分包"，一定漏
- 只按分包分 → 逻辑和表现混在一个包内，测试没法跑，`import 'cc'` 会蔓延到业务规则里

## 3.2 必须死守的三条依赖规则（可用脚本检查）

```text
✅ 允许
  bundles/main/**            → 任何层
  bundles/mod-*/view/**      → bundles/main/scripts/{core,game,ui}/**
  bundles/mod-*/**           → packages/contracts/**

❌ 禁止（架构守卫直接报错）
  core/**                    → import 'cc'            ← 纯逻辑必须可跑在 Node
  core/**                    → adapters/**            ← 内核不许知道实现
  bundles/mod-a/**           → bundles/mod-b/**       ← 分包互引会重复打包
  ui/**                      → core/modules/**        ← UI 组件不许懂业务
  assets/**                  → 相对路径跳出 client/   ← 引用仓库外部文件
```

> 为什么 `core/` 放主包：Cocos 的规则是**主包代码可被所有分包引用，分包之间不能互相引用**。把逻辑内核放主包，各分包只装"自己的图和场景"，逻辑一份、资源多份，正好卡住 4MB。

## 4.2 关键实操：云函数怎么用上 `src/`

这是绝大多数人踩坑的地方。`cloudfunctions/api/` 上传时只打包自己目录，所以**不能在 `index.js` 里 `require('../../src')`**。

解法固定为一条（写进 `tools/build/cloudfunctions.mjs`）：

```text
pnpm build:cf
  → esbuild 打包 server/src + packages/contracts
  → 输出 server/cloudfunctions/api/dist/index.js（单文件，已内联依赖）
  → 各函数目录只留 index.js + package.json + dist/
```

好处：
- 源码只有一份，不存在"改了 3 处忘 1 处"
- 每个云函数体积可控（tree-shaking 后通常 <200KB）
- 换平台时 `adapters/http` 复用同一份 `src`

## 4.3 后端依赖方向（硬约束）

```text
adapters/*  →  modules/*/interfaces  →  application  →  domain
                                                  ↑
                                          infrastructure（只实现 domain/ports）

❌ domain → 云数据库 SDK
❌ domain → wx-server-sdk
❌ domain → Redis / HTTP
❌ interfaces → 直接操作 collection（必须过 application）
```

```text

│   ├── src/
│   │   ├── common/
│   │   │   ├── response.ts             # 统一封套 ApiResponse<T>
│   │   │   ├── error-codes.ts          # 错误码枚举（分段见下）
│   │   │   └── pagination.ts
│   │   ├── salvage/
│   │   │   ├── schema.ts               # ⭐ zod schema（真源）
│   │   │   ├── actions.ts              # action 名常量 + 类型映射
│   │   │   └── index.ts
│   │   ├── ...（每个域一个文件夹，与 client/core/modules、server/src/modules 同名）
│   │   └── config/
│   │       └── generated/              # ⭐ 配置表生成物：items.ts / recipes.ts / drops.ts
│   └── package.json
│

```

**为什么必须是 zod 而不是手写 interface**：手写 interface 只能约束编译期，云函数的入参是运行时的脏数据，必须运行时校验。用 zod 一份定义同时产出：
- TS 类型 `z.infer<typeof Schema>`（两端共用）
- 运行时校验 `Schema.parse(payload)`（服务端入口统一挂）
- 字段说明（`.describe()` 喂给文档生成）

**改一个字段只改一处**，两端编译不过就是提醒。这是"高效变更"的第一道闸。

# 八、前后端数据交互设计

## 8.1 传输形态：单入口 action 模式

不要每个功能一个云函数（几十个函数的依赖、冷启动、灰度、日志会把人拖死）。用**一个 `api` 云函数 + action 字符串路由**：

```text
client  wx.cloud.callFunction({ name:'api', data:{ action, payload, meta } })
                            ↓
server  adapters/cloudbase/index.ts → dispatch(action) → modules/<域>/interfaces/<handler>
```

只有三类例外才独立建云函数：`login`（要拿 openid，权限独立）、`job-*`（定时触发）、未来的大文件上传。

## 8.2 统一封套（写死在 contracts/common/response.ts）

```typescript
// 请求
export interface ApiRequest<T> {
  action: string;          // 如 "salvage.cast"
  payload: T;              // 由 zod schema 校验
  meta: {
    clientVersion: string; // 1.0.3
    configVersion: string; // 配置表版本，服务端比对
    saveVersion: number;   // 存档结构版本
    nonce: string;         // 防重放
    sign: string;          // 参数签名（可后置）
  };
}

// 响应
export type ApiResponse<T> =
  | { code: 0; data: T; serverTime: number; configVersion: string }
  | { code: number; msg: string; detail?: unknown };
```

**为什么必须有 `serverTime`**：离线收益、食物保质期、开锁每日限购、赶海场次全靠它，客户端本地时间不可信。

## 8.3 错误码分段（对齐后端分层，一眼看出是谁的问题）

```text
0       成功
1000–1999  参数/契约错误（interfaces 层 zod 校验失败）
2000–2999  权限/登录态（application 层）
3000–3999  业务规则拒绝（domain 层，如"货舱已满""开锁工具不足"）
4000–4999  系统/依赖故障（infrastructure 层，DB 超时等）
5000–5999  风控/作弊判定（复算不一致、超理论值）
```

客户端只需按段处理：1xxx 提示"版本过旧请更新"、2xxx 拉起登录、3xxx 直接弹业务提示、5xxx 静默上报。

## 8.4 契约即真源：一份 schema，两端生效

```typescript
// packages/contracts/src/salvage/schema.ts
import { z } from 'zod';

export const CastHookPayload = z.object({
  hookId: z.string(),
  targetX: z.number().min(-1).max(1),
  targetY: z.number().min(-1).max(1),
  seed: z.string(),                 // 服务端下发（防作弊）
  clientTick: z.number().int(),
});
export type CastHookPayload = z.infer<typeof CastHookPayload>;

export const CastHookResult = z.object({
  hit: z.boolean(),
  itemId: z.string().nullable(),
  weight: z.number(),
  durability: z.number(),
  serverTick: z.number().int(),
});
export type CastHookResult = z.infer<typeof CastHookResult>;
```

客户端写 `callApi<CastHookPayload, CastHookResult>('salvage.cast', payload)`，服务端写 `dispatch({ 'salvage.cast': { in: CastHookPayload, out: CastHookResult, handler } })`。**改字段 → 两端红叉 → 不可能漏。**

## 8.5 版本协商（一人开发也必须做，否则你就没法灰度）

```text
服务端维护：
  MIN_CLIENT_VERSION   # 低于它直接拒绝（code 1001 提示更新）
  CURRENT_CONFIG_VER   # 配置表版本，客户端不一致时走"配置热更"拉新表
  SAVE_VERSION_WINDOW  # 支持 N-2 版本存档（老玩家不能丢档）
```

## 8.6 存档协议（这是最容易炸的地方）

```text
客户端：saveVersion + 乐观锁 rev
  ↓ 每 30s 或关键节点（关闭箱子/结算/下线）上报增量
服务端：全量快照（主）+ 增量日志（辅），rev 不匹配则返回最新快照让客户端重建
迁移：server/database/migrations/v{n}_to_v{n+1}.ts + client/core/modules/save/migrations/
   由 migrate(save, fromVersion) 串成链，从任意旧版本一次升到当前
```

**规则：存档字段只增不改不删。** 要"删"就标 `deprecated` 保留两个版本；要"改名"就新增字段 + 写迁移函数 + 老字段保留只读。

## 8.7 哪些必须服务端算（防作弊分层，直接对齐你已定的规则）

| 场景 | 客户端 | 服务端 | 说明 |
|---|---|---|---|
| 打捞命中判定 | 即时反馈 | 种子复算 | 服务端发 seed，客户端算表现，服务端用同 seed 重算入库 |
| 开箱 | 播动画 | 权威 | 箱子内容服务端生成，客户端只表现 |
| 开锁 | 实时手感 | 复算校验 | 客户端算进度，服务端校验步数/工具/时长是否可能 |
| 赶海排名 | 只展示 | 权威 | 分组、票价、奖励全服务端 |
| 玩家交易 | 只展示 | 权威 | 原子事务，服务端二次确认 |
| 离线袭击 | 只展示 | 权威 | 三限（损 30%/守军不死/最多 2 波）在服务端落地 |
| 广告奖励 | 请求 | 校验回调 | 平台侧回调校验，客户端自报不算 |

# 九、增删改查如何高效变更（核心问题）

## 9.1 先看清"为什么手工改一定漏"

一个业务字段在这套体系里通常有 **7 个副本**：

```text
Excel 表头 → JSON → TS 类型 → zod schema → 存档结构 → 数据库集合 → 文档
```

只要其中一处靠手写，就一定会漂移。所以目标不是"改得快"，而是**把 7 处压到 2 处（Excel + schema），其余全部生成**。

## 9.2 三道防线

| 防线 | 机制 | 拦住什么 |
|---|---|---|
| **类型即检查** | contracts zod → 两端 TS | 字段改名、类型改错、必填漏传 |
| **影响面自动列举** | `modules.manifest.json` + `npm run impact <关键词>` | 忘了改某个消费方 |
| **守卫脚本** | layer-boundary / orphan / root-clean | 依赖越界、孤儿文件、生成物入库 |

`modules.manifest.json` 长这样（由 `tools/gen/module-manifest.mjs` 扫目录生成，不手写）：

```json
{
  "salvage": {
    "client": "bundles/main/scripts/core/modules/salvage",
    "server": "src/modules/salvage",
    "contracts": "packages/contracts/src/salvage",
    "bundle": "mod-sea-shallow",
    "configTables": ["items", "drops", "shipwrecks"],
```

`npm run impact items` 会输出：**改了 items 表，影响 salvage/box/craft/merchant 四个域、两处存档字段、一个分包**。这比翻代码快 20 倍。

## 9.3 六种变更的标准作业单（照做，不靠记忆）

### A. 调数值 / 改平衡（最高频，一天十几次）

```text
1. 改 Excel（唯一真源）
2. npm run gen            → JSON + TS 类型 + 校验
3. 客户端热更/重进        → 配置版本号自动变，两端一致
4. git commit "balance: 铜锁价格 300→280"
```
> ✅ 只碰 1 个文件。若这里要改代码，说明数值没进配置表，是设计缺陷。

### B. 修改一个已有字段（改名/改类型）

```text
1. npm run impact <字段名>          → 看清谁在用
2. 改 packages/contracts/<域>/schema.ts（真源）
3. 跑 tsc                            → 客户端 + 服务端同时报错，逐个修
4. 若涉及存档：新增字段 + 写 migration，老字段标 @deprecated
5. 若涉及数据库：database/migrations/v{n}.ts（加默认值/回填）
6. npm run guard && npm run test
7. CHANGELOG.md + docs/07_release 记录
```
> 关键：**先改 schema，靠编译器找所有落点**，不要靠 grep 找。

### C. 新增一个接口

```text
1. docs/02_requirements/features/REQ-F-xxx.md（先有需求）
2. packages/contracts/<域>/schema.ts 加 payload/result
3. server/src/modules/<域>/application/<用例>.ts
4. server/src/modules/<域>/interfaces/<action>.ts 注册到 dispatch 表
5. client 调用：core/modules/<域>/application/<方法>.ts（走 INetwork port）
6. tests、guard、CHANGELOG
```
> 服务端 dispatch 表用 `Record<ActionName, Handler>`，**漏注册会编译报错**（用 `satisfies` 约束全部 action）。

### D. 新增一个功能模块（大改）

```text
1. docs：REQ-INBOX → REQ-F（含验收标准）→ SOL（方案）→ 必要则一份 ADR
2. docs/04_planning/current-plan.md 加里程碑
3. 建目录（固定 4 件套，两侧同名）：
   client/.../core/modules/<x>/{domain,application,index.ts}
   server/src/modules/<x>/{domain,application,interfaces,infrastructure}
   packages/contracts/src/<x>/{schema,actions,index}.ts
4. 决定分包归属：进 main 还是新建 mod-<x>（看表九）
5. 配置表：Excel 新 sheet → gen
6. npm run gen:manifest  → 更新影响面
7. docs/05_execution/tasks/TASK-xxx.md 拆原子任务
8. 打通一条端到端用例 → docs/06_validation 留 EVD
9. CHANGELOG + REL
```

### E. 删除一个功能（最容易留垃圾）

```text
1. docs：原 REQ-F 状态改 cancelled（→ docs/09_archive/cancelled/，不删）
2. 先删调用方（导出/路由/UI 入口），再删实现
3. 删 contracts 里的 schema 和 action 常量
4. 删配置表 sheet + 跑 gen（生成物自动消失）
5. 删存档字段？→ 不删，标 @deprecated + 保留两个版本
6. npm run guard（orphan 会报出残留引用）
7. 检查分包体积（删资源后跑 build:wechat 看主包是否变小）
8. CHANGELOG 写"移除"而非"修复"
```
> 顺序必须是**先断引用，后删实现**，反过来必然编译不过、必然有残留。

### F. 数据查询（新增一个列表/统计）

```text
1. 云数据库先建索引（server/database/indexes/）——不建索引的查询在大盘必超时
2. 服务端 query 用例（只读、不走 domain 事务）
3. 契约加 PaginationQuery 通用类型
4. 客户端加缓存层（core/modules/<域>/application 里做 TTL 缓存，避免反复打云函数）
```

## 9.4 变更记录的最小闭环

```text
代码变了 → CHANGELOG.md（对外人话）
        → docs/07_release/release-records/REL-xxx.md（发布事实）
        → 若改了契约/存档/配置结构 → 必须有一份 migration 或版本号递增
        → 若推翻了旧决策 → docs/03_solution/decisions/ADR-xxx.md 标 superseded
```

## 10.2 一人开发的裁剪：先建 6 个，其余"触发式"生长

## 10.3 "清晰"靠三件事

1. **ID 单一**：每个文档一个 ID，全项目唯一，且**和代码路径绑定**
   ```yaml
   ---
   id: REQ-F-042
   module: salvage              # ⭐ 直接对应 modules/salvage
   status: active
   owner: hark
   created: 2026-10-23
   ---
   ```
   `module` 字段让 `REQ-F-042 ↔ client/core/modules/salvage ↔ server/src/modules/salvage ↔ contracts/salvage` 四者天然对齐，`project-map.md` 可以自动生成。

2. **索引自动**：`document-index.md`、`task-index.md`、`project-map.md` 全部由 `tools/gen/docs-index.mjs` 扫 front matter 生成。手写的索引一定会过期。

3. **每个模块一份 README**：
   ```text
   modules/salvage/README.md
     ├ 一句话职责
     ├ 相关需求：REQ-F-042, REQ-F-043
     ├ 相关决策：ADR-007（种子下发）
     ├ 对外 action 列表
     └ 配置表依赖
   ```
   看代码的人从代码进文档，看文档的人从文档进代码，双向不断链。

## 10.4 "全面"靠一条链，不靠文档数量

附件里的追溯链落到本项目，一条真实例子串到底：

```text
REQ-INBOX-20261023-001  "玩家反馈钩子手感太硬"
      ↓ 分析
REQ-F-042  打捞手感：前 10 钩虚线引导
      ↓ 方案
SOL-012    虚线引导实现方案
      ↓ 决策（有分叉才写）
ADR-007    引导用本地演算而非服务端校验（理由：不涉及经济）
      ↓ 计划
current-plan.md  W2 任务
      ↓ 执行
TASK-031  实现虚线引导
      ↓ 验证
VAL-031   10 名新玩家首钩成功率 >70%
      ↓ 证据
EVD-031/  录屏 + 数据截图
      ↓ 发布
REL-0.1.0 + CHANGELOG
```

**判断文档是否"全面"的标准不是数量，而是"随便抽一条需求，能不能顺链路走到底"。**

## 10.5 防"文档腐烂"的三条硬规则

1. **能生成的不手写**：索引、配置字段说明、action 列表、目录树，全部生成。
2. **历史不删除**：废弃的进 `09_archive/`，状态改 `superseded`/`cancelled`，正文保留。
3. **每个文档有 `review: 2026-11-23`**：超过没更新的活跃文档，在 `document-index.md` 里标黄，每周扫一眼。

## 需要你拍板的两个点

**P1｜后端形态**
- A（推荐）：微信云开发（云函数 + 云数据库），抖音端走 `adapters/http` 转发到同一套 `src`
